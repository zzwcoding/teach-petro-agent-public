# 数据质量闭环与 LLM 修复调研（2026-09-28）

> 调研问题：真实企业 / 开源社区在数据接入管道中如何处理与修复数据质量问题？LLM 在其中接管了什么、接管不了什么？
> 服务于本项目的决策：dp3 质量闸（validate_batch → QualityReport + 剔除坏行后的 clean 数据，append-only 湖表）之上的坏行隔离区、问题单五态（分发→认领→整改→复核→关闭）、修正回流（修复=供给方改产物重新进料，靠新批次叠加不改历史）该怎么设计，以及 LLM 与人的分工边界。
> 方法：以官方文档（docs.*）/ GitHub 仓库 / 官方博客为一手来源，关键论断后附链接；标注「已核对原文」的条目为本次调研直接抓取原文核对过。查不到实锤的明确写「未找到公开依据」。

## 一句话结论（TL;DR）

1. **开源质检工具（GX / dbt tests / Soda / Deequ / Elementary）全部停在"机判→记录→通知"三拍**，没有一家在开源层做行级隔离与修复闭环；隔离表（quarantine）模式的主流官方背书是 Databricks Lakeflow expectations（`expect / expect_or_drop / expect_or_fail` + `_rescued_data` 分流），官方文档明确给出 quarantine 表代码模式。
2. **dbt 证明"阻断"与"留坏行"是两个正交机制**：`severity: error` 经 DAG 依赖阻断下游模型、`warn` 只记录；`--store-failures` 只是把失败行快照进 `*_dbt_test__audit` 表——审计快照，不是可重放的隔离区，不能直接抄。
3. **问题单闭环的最佳参照 = Soda Cloud incident + Metaplane incidents**：Soda 有正式 incident 实体（从失败 check 立单、必填 lead、状态流转、解决强制 resolution note、webhook/API 分发、AI RCA 结论可回写 incident）；Metaplane 在 Slack 内聚合告警成 incident、双向操作（re-run 复验按钮、resolve）、可开 Jira。**"修复后自动复验关闭"全行业只找到"手动 re-run 按钮 + 人 resolve"级实锤，未见全自动先例。**
4. **修复的主流姿势不是改历史而是重进料**：append-only 湖仓 + 修正批次叠加（ClickHouse ReplacingMergeTree 版本列、Kimball SCD2 修正记录、Visier restate 工作流、Google Datastream append-only）；与本项目"湖表不可变、修复=供给方重新进料"的既定方向完全一致，业内有充分先例。
5. **自动修复边界行业共识**：格式归一 / 确定性枚举映射 / 去重可自动；金额、财务口径、多解歧义绝不自动（Monte Carlo / Profisee / Soda 金融合规口径一致）；且自动修复只应作用于派生层，原始坏行永远保留 + 全程 audit log。
6. **LLM 落地三档，可信度递减**：监控/规则推荐（GA，Monte Carlo Monitoring Agent 号称 60% 接受率，人一键部署）＞ 异常归因解释（GA，MC Troubleshooting Agent、Anomalo AIDA、Soda RCA agent，效果数字均为厂商自述）＞ **修复执行（无任何 GA 产品**；MC 明确把 agent "read-only、不碰数据"当卖点）。"LLM 起草、人裁决"是 2024–2026 的行业实态。
7. **两家老项目出局**：Apache Griffin 已于 2025-09 退役进 Apache Attic，不再作参照；GX Cloud 2026-06-01 停服，GX Core 归 Fivetran 托管（Fivetran 2025-10 与 dbt Labs 合并，dbt/GX 现为同门）。凡依赖 GX Cloud AI 功能（如 ExpectAI）的案例一律作废。
8. **结论：需要人，但人的位置收窄为四点**——金额/口径类修复裁决、规则与阈值变更审批、问题单关闭抽查（审计位）、跨供给方协调。发现/分发/复验可全自动；归因 LLM 起草人确认；修复执行机器做、修复决策分类分级。

## 一、开源项目的处理模式

### 1.1 Great Expectations（GX）

- **机制**：Checkpoint 执行一个或多个 Validation Definition，然后按每个 Validation Result 执行一组 **Actions**（官方原文："A Checkpoint executes one or more Validation Definitions and then performs a set of Actions based on the Validation Results"）。
  - Actions 按 `notify_on` 五档触发：`all / success / failure / critical / warning / info`；严重度有优先级——结果混档时只有配置了 `warning`/`failure`/`all` 的动作会触发。
  - 当前官方文档列出的内置动作：`SlackNotificationAction`（可配 `notify_on="failure"`、`show_failed_expectations=True`）与 `UpdateDataDocsAction`（把结果渲染进 Data Docs 静态 HTML 站）；0.18 时代另有 Email / SNS / Opsgenie / MS Teams / PageAnomalyDictionary 等。
  - 官方支持自定义 Action——这是"失败后挂自定义逻辑"的官方钩子位（可用来写隔离表、建工单、触发重跑，但全要自己写）。
  来源：<https://docs.greatexpectations.io/docs/core/trigger_actions_based_on_results/create_a_checkpoint_with_actions>（已核对原文）
- **坏数据去向**：**GX 不管行**。它是管道外的验证+通知库：
  - 没有行级路由、没有 quarantine 概念、没有"失败阻断管道"的内置语义；
  - Result Format（SUMMARY/COMPLETE）只控制结果详略（含 unexpected 样本与 unexpected_index_list），不控制数据流向；
  - 失败后是否拦截管道取决于调用方代码或 orchestrator 集成（Airflow operator 让任务失败、CI 退出码）。
- **告警/工单集成**：Slack/email 通知 + UpdateDataDocs + 自定义 Action 接任意系统；**无内置工单实体、无 incident 流转**。
- **治理现状（2026，选型须知）**：Fivetran 宣布接手 GX Core 开源社区托管（约 2026-05）；GX Cloud（商业版，含 ExpectAI 等 AI 功能）宣布 2026-06-01 停止服务。来源：Data Kitchen《2026 Data Quality and Data Observability Commercial Landscape》<https://datakitchen.io>、<https://github.com/great-expectations/great_expectations>。

### 1.2 dbt tests

- **机制**：test = 一条返回"失败行"的 SQL，行数即失败数，与 `error_if`/`warn_if` 条件表达式比较（默认 `!=0`，支持 `>5`、`between 5 and 10` 等任意 SQL 比较）。
  - `severity: error`（默认）→ 满足 `error_if` 即 error → **`dbt build` 按 DAG 依赖跳过下游模型**（阻断语义）；`severity: warn` 直接跳过 `error_if`、永远只警告。
  - `--warn-error` 把**所有** warning（测试 warning、Jinja 警告、弃用提示等）升级为 error；`--warn-error-options` 可按类型选择性升级——即"warn 只记录还是拦截"由运行参数决定，不由规则本身决定。
  来源：<https://docs.getdbt.com/reference/resource-configs/severity>（已核对原文）
- **坏数据去向**：默认哪也不去（只有失败计数与日志）。`store_failures: true` / `--store-failures` 把**每个失败测试的失败行**写入 `{{ schema }}_dbt_test__audit`（可配）下以测试名命名的表。
  - 这是 dbt 世界最接近隔离区的东西，但它是**每次运行的审计快照**：无批次外键、无重放入口、下轮覆盖语义、与生产数据物理同库——只适合人看，不适合当隔离队列。
  来源：<https://docs.getdbt.com/reference/resource-configs/store_failures>、<https://docs.getdbt.com/reference/resource-configs/store_failures_as>。
- **生态**：`dbt-expectations`（GE 风格断言移植为 dbt generic tests；**calogica 原包已停止维护，由 metaplane fork 接续**，选型注意，来源：<https://github.com/calogica/dbt-expectations>）；`dbt-audit-helper`（`compare_queries / compare_relations / compare_all_columns / compare_and_classify_query_results`，迁移/重构时逐行比对新旧数据并分类 added/removed/identical/modified——现成的"修复前后对照"工具，来源：<https://hub.getdbt.com/dbt-labs/audit_helper/latest>）。
- **告警/工单集成**：dbt 本体零集成；告警靠 Elementary / 调度器 / CI，工单靠外部 ITSM。dbt 的定位就是把"记录与阻断"做扎实，流转全部外置。

### 1.3 Soda（soda-core + Soda Cloud）

- **机制**：soda-core 用 SodaCL 声明 checks，跑出 check results 推送到 Soda Cloud（聚合、仪表盘、异常检测、告警路由）。soda-cli 现统一管理 datasources/datasets/contracts/monitors/incidents（<https://github.com/sodadata/soda-cli>）。
- **事件流转（本次调研找到的最完整开源系问题单模型）**：Soda Cloud 有正式 **incident 实体**：
  - 在 check 页面"context menu → Create Incident"，填名称描述、可关联多条 check results；
  - **必须指定 lead（负责解决的人）**；状态随调查/解决过程演进，可按 lead / status / reporter / severity 过滤；
  - 后续新失败结果可继续挂到同一 incident（"If new results are failing, you can include them in the incident"）；
  - **标记 resolved 时强制填写 resolution note**（"to document what was done"）；
  - 权限模型为 Manage Incidents（建/编辑单需权限，可见者皆可看单）；
  - 对外经 webhook / Slack / MS Teams / Incidents REST API 分发（API 含发布 RCA 报告的操作）；
  - 官方 incidents 文档页还提到 **AI root cause analysis agent 可把 RCA 结论发布到 incident 上**。
  来源：<https://docs.soda.io/manage-issues/incidents>（已核对原文）、<https://docs.soda.io/reference/soda-apis/rest-api/incidents>
- **坏数据去向**：checks 是聚合级断言，不做行级隔离（个别 check 可返回失败样本行）。
- **告警/工单集成**：webhook/Slack/MS Teams + Incidents API；Jira 未在 incidents 页显式命名（经 API/webhook 外接）。

### 1.4 Deequ（Amazon）

- **机制**：Spark 上的"数据的单元测试"，批式三段：`compute metrics → verify constraints → metrics repository + anomaly detection`：
  - 指标落仓库，对历史指标序列跑 OnlineNormal 等算法检测突变；
  - 代码内声明（Scala/PyDeequ），无 UI、无流转、无告警内置。
  来源：<https://github.com/awslabs/deequ>、<https://aws.amazon.com/blogs/big-data/test-data-quality-at-scale-with-deequ>
- **坏数据去向**：无行级路由；产出 VerificationResult 与指标，由调用方决定后续。AWS 把这套思想产品化为 **AWS Glue Data Quality**（GQT 规则语言 + ML 规则推荐 + 异常检测，≥3 个历史数据点即可启动，来源：<https://docs.aws.amazon.com/glue/latest/dg/glue-data-quality.html>、<https://docs.aws.amazon.com/glue/latest/dg/data-quality-anomaly-detection.html>）。
- **告警/工单集成**：无内置；Glue DQ 结果接 EventBridge/CloudWatch 外发。

### 1.5 Elementary（dbt 包）

- **机制**：`dbt-data-reliability` 包随 dbt 运行收集工件/测试结果进 elementary 元数据 schema：
  - 提供 anomaly 测试族（volume / freshness / schema / dimension_anomalies / distribution 等按时间序列检测，配置执行方式与 dbt 原生测试完全一致）；
  - CLI `edr monitor / edr summary / edr send-report` 生成报告页并发告警。
  来源：<https://docs.elementary-data.com/data-tests/introduction>、<https://docs.elementary-data.com/oss/oss-introduction>、<https://github.com/elementary-data/dbt-data-reliability>
- **坏数据去向**：异常与测试结果进 elementary 元数据表（供报告与趋势分析）；**不隔离行**。
- **告警形态**：OSS 侧配置 alert channels（Slack / PagerDuty / email / webhook，可按 monitor 分渠道、分严重级 notify）；Cloud 侧托管告警与界面（另有性能告警等增值）。来源：<https://docs.elementary-data.com>（渠道配置 deep-link 未能直接抓取，渠道清单经官方站点+二次来源核验）。

### 1.6 Apache Griffin——已出局

- **2025-09 ASF Newsletter 宣布 Griffin 与 Apache Portals 退役进 Apache Attic**，2026-01 董事会纪要确认退役完成；站点转 attic 只读，无进一步开发与支持。**结论：不再作为参照。** 来源：<https://attic.apache.org/projects/griffin.html>、ASF Plus One Newsletter（2025-09）。

### 1.7 平台级参照：Databricks Lakeflow expectations（隔离模式唯一官方文档化背书）

- **三动作**：`expect`（保留坏行并计数，行照进目标表）、`expect_or_drop`（丢弃坏行+计数）、`expect_or_fail`（失败即断管道）——官方 expectations API 把"对坏行的处置"显式分为 retain / drop / fail 三档并记指标。
- **`_rescued_data` 模式**：schema 演进接不住的字段落入 `_rescued_data` 列；官方 advanced patterns 给出"valid 视图（`_rescued_data IS NULL`）+ invalid 视图分流到两张目标表"的完整代码模式——**官方明确建议把失败行单独落表留证，而不是悄悄丢弃**（"route rows that fail validation to a separate table to preserve dropped records for investigation"）。
  来源：<https://docs.databricks.com/aws/en/ldp/expectations>、<https://docs.databricks.com/aws/en/ldp/expectation-patterns>、<https://docs.databricks.com/aws/en/lakehouse-architecture/reliability/best-practices>
- 开源社区同型实践：Spark "fail-fast vs quarantine zone" 双模式（<https://medium.com/towards-data-engineering/fail-fast-or-quarantine-two-data-quality-patterns-every-spark-engineer-should-know-111598f31ada>）；流式 DLQ（Kafka/SQS 死信队列 + 指数退避重试 + 幂等消费）。
- **Bigeye 对行业做法的归纳**（一手博客）：粗粒度熔断（circuit breaker，整条管道停）vs 细粒度（inline fixup / drop / quarantine）；**schema 级系统故障走熔断、行级质量问题走隔离**；隔离必须配监控，否则变沉默数据债。<https://www.bigeye.com/blog/strategies-for-handling-bad-data-in-data-pipelines>

**开源层小结**：共性 = 规则库 + 结果落盘 + 通知 Action；行级隔离靠管道自建（平台里只有 Databricks 把 quarantine 写进官方文档）；**问题单实体与流转是 Cloud 产品的差异化功能**，其中 Soda Cloud incident 与本项目"问题单五态"最同构（多出的是我们独有的"分发"一步——Soda 是人工 Create，我们有机判信号可自动建单草稿）。

## 二、商业可观测产品的闭环

| 产品 | 检测 | incident / triage | root cause | 修复/关闭（含"修复后自动复验？"） | 证据等级 |
|---|---|---|---|---|---|
| **Monte Carlo** | ML 自动铺 monitors；AI 驱动 incident 检测 + 影响分析 | 域导向告警路由；incident 带影响分析 | lineage + Queries 视图人工看；**Troubleshooting Agent（2025-04 发布、GA 计划 2025 Q2）**：数十个并行 subagent 测数百个假设、几分钟出 RCA，判断坏源数据 / ETL 失败 / 转换代码错 / 模型输出错；**声称 -80% 解决时间**；agent 明确 **read-only**（"never directly manipulate, change, or act upon your critical data"） | 无自动修复；**Monitoring Agent（GA）**推荐监控规则与阈值、人一键部署（自称数千条推荐、60% 接受率）；2025 底补 Operations Agent | 官方博客+产品页（已核对原文）<https://montecarlo.ai/blog-monte-carlo-observability-agents>、<https://montecarlo.ai/platform/agents> |
| **Metaplane**（已并入 Datadog） | 自动 monitors + 异常检测 | **Slack 内聚合**：相关 monitor 告警归并成一个 incident，Slack 消息**原地更新** + 每日线程提醒防重复打扰 | AI 辅助 RCA（列级 lineage 辅助定位） | **Slack 双向闭环**：告警消息带 "Re-run test" 按钮（**手动复验**是否已恢复）；可从 Slack resolve incident；Jira 一键开单回链 incident。**复验=人点按钮，非自动** | 官方博客（已核对清单）：<https://www.metaplane.dev/blog/announcing-data-incidents>、<https://www.metaplane.dev/blog/re-run-tests-from-a-slack-alert>、<https://www.metaplane.dev/integrations/jira> |
| **Anomalo** | 无监督 ML 全表自动监控（免规则配置，检测 missing/late/corrupted） | 异常即 incident，通知/升级 | **instant RCA**：指出表中哪个 segment/值分布造成异常，附样本与上下游 lineage（第三方评为此类最完善 RCA UI 之一） | 未找到"自动复验关闭"公开实锤；**AIDA**（2025-10-29 官宣，与 Google 合作的自然语言数据 copilot：问数、可视化、建 check） | 官方产品页 <https://www.anomalo.com>；AIDA 见 Anomalo 官方 LinkedIn；RCA 细节佐证 <https://datastackindex.com>（二手） |
| **Bigeye** | auto-thresholding（季节性自适应阈值）+ 规则验证 | 告警路由 PagerDuty / Slack / email | lineage 辅助定位 | 未见自动修复/关闭公开实锤 | 官方 docs 未直接核验，主要来自对比文（<https://datadrivendaily.com> 等）——**二手来源，谨慎引用** |
| **Databricks Lakehouse Monitoring** | Unity Catalog 内自动 profile，评估每表 freshness / completeness；anomaly detection 基于表 commit 历史建模预测下次提交 | 异常进系统界面 + 自动 dashboard | 依托 Unity Catalog lineage | 不做行级修复，无工单闭环 | 官方 docs <https://docs.databricks.com/aws/en/data-governance/unity-catalog/data-quality-monitoring> |
| **Snowflake** | **DMF 数据指标函数**：内置 NULL_COUNT / DUPLICATE_COUNT / FRESHNESS / ROW_COUNT 等 + 自定义 SQL DMF；默认每小时跑（可 cron / 触发式），结果落 `DATA_QUALITY_MONITORING_RESULTS` | 用 **Alert 对象**对 DMF 结果做阈值告警（email / webhook/通知集成） | 无 | 无 | 官方 docs <https://docs.snowflake.com/en/user-guide/data-quality-intro>（DMF 默认调度官方页已核对） |

**横向结论**：
1. incident → triage → root cause 三段全行业都有产品化；RCA 的形态都是"**证据链 + 建议**"（哪个表/segment/上游变更），没有一家把 RCA 结论直接当判决自动生效。
2. **"resolution 后自动复验关闭"没有任何一家做到全自动**——最实的两个半自动形态：Metaplane 的"人点 re-run 按钮 → 结果原地更新 → 人 resolve"，Soda 的"resolve 强制 resolution note 留痕"。ITSM 集成形态是"开单/回链"（Metaplane→Jira、Soda→webhook/REST API），不是"修复后自动关单"。
3. **可观测产品普遍不碰数据**（MC read-only 是卖点）——修复动作本身（改上游产物 / 重跑管道）全部留在客户侧工具链。这条对"修复=供给方改产物重新进料"的架构是行业级佐证。

## 三、修复模式盘点

### 3.1 隔离 → 重放/重处理

- **隔离表要素**（Databricks 官方模式 + Bigeye 归纳 + Theodo 框架综合）：
  - 原始 payload + 失败原因/规则 ID + 时间戳 + pipeline run/batch ID，供重放与审计；
  - **隔离区必须有量级监控与告警**（阈值升级、趋势监控），否则成为沉默数据债。
- **重放编排（Airflow 语义）**：
  - `airflow tasks clear -s <date> -e <date>`：清空区间任务实例重跑（UI Grid View "Clear Task" 同操作）；
  - `airflow dags backfill -s -e --rerun-failed-tasks`：区间内自动重跑此前失败实例；
  - 任务必须幂等（idempotent），重试配指数退避。
  来源：<https://airflow.apache.org/docs/apache-airflow/stable/cli-and-env-variables-ref.html>、<https://www.astronomer.io/docs/learn/rerunning-dags>
- 对应到管道内质量闸：修复完成后重进料 = 对坏批做定向重跑或新分区 backfill，让数据**再过一次同一套规则**，而不是绕闸补数——"隔离区的重放入口"就是闸的再次调用。

### 3.2 修正叠加 / 不可变修正（append-only 湖仓怎么做修复）

- **不可变存储的修正惯例**：不 UPDATE 历史，以修正批次/版本叠加：
  - ClickHouse 在不可变语义下用 `ReplacingMergeTree + 版本列`让修正数据按版本覆盖旧版（oneuptime 技术文）；
  - Google Datastream 以 append-only 模式把源库变更（含修正）作为新记录追加进 BigQuery（<https://cloud.google.com/blog/products/data-analytics/understanding-datastream-append-only-mode>）；
  - Visier 提供正式 restate 工作流（替换已加载文件重算，<https://docs.visier.com>）；
  - Microsoft Fabric 的 lake view 要求源 append-only、有更新/删除就退化为全量刷新（<https://data-mozart.com>）。
- **Kimball SCD2 修正记录（correction records）**：区分两类修正：
  - 真源数据错误（本不该为真）→ 修正历史行及其生效日期；
  - "当时如实、现需重述"→ **关闭旧行、以回溯生效日期开新行**，保留审计轨迹；
  - 迟到事实按生效日期重键。
  来源：Kimball Group 官方论坛 <https://kimballgroup.forumotion.net>
- **双时间轴（bitemporal）思想**：事务时间（何时入库）与有效时间（何时为真）分离，是"修正不改历史、重述出新版"的形式化；湖仓实践中等价于"修正批次 + 下游按有效时间重算"。
- **对本项目的意义**："修复=供给方改产物重新进料、新批次叠加、不改历史"正是业内不可变湖仓的主流做法，无需另造机制；**需要补的是修正批次与问题单的关联**（哪次进料是哪个问题的整改）——这是各家文档都不管、要自己设计的部分。

### 3.3 自动修复 vs 人工修复的行业边界

- **敢自动**（确定性、可机械验证、可回滚）：
  - 格式归一（电话/日期/大小写/单位）、确定性枚举映射、去重保首条、schema 演进的 `_rescued_data` 类字段整理。
  - 来源：Actian（"common patterns 如电话号码重格式化适合自动修复"）、Bigeye inline fixup、Databricks `_rescued_data` 官方模式。
- **绝不自动**（判断型/高风险/有合规责任）：
  - 金额与财务数值、口径/合规相关字段、存在多个合理修复的歧义修正（自动选一个=静默污染）。
  - 来源：Monte Carlo 与 Profisee 均强调财务数据修复必须人审（合规/审计/法律责任）、Soda 金融业自动化指南强调输入资本/流动性计算的数据必须过验证闸。
- **原则总结**（行业共识）：
  - 自动检测 + 仅确定性低风险自动修复 + **全部修复动作留 audit log** + 歧义一律转人工；
  - 自动修复的工程化位置在**派生层**（视图/下游规范化），不在入库原始层——原始坏行永远保留，这也是 `_rescued_data` 设计的潜台词。

## 五、结论：环节自动化矩阵 + 人守在哪

| 环节 | 自动化程度 | LLM 的位置 | 人守在哪 |
|---|---|---|---|
| 发现/机判 | **全自动**（规则 + 统计/ML 异常检测双轨，Deequ/Elementary/Snowflake DMF 模式） | 推荐新监控/新规则（MC Monitoring Agent 模式，人一键接受） | **审批规则与阈值变更**（唯一守门点，否则规则漂移无人负责） |
| 告警聚合与分发 | **全自动**（去重、归并 incident、路由 Slack/ITSM，Metaplane/Soda 模式） | 可写告警摘要 | 维护路由表与分级标准 |
| 归因/RCA | 半自动 | **LLM 起草**：并行假设验证 + 证据链（读报告+坏行样本+lineage）→ 建议 | **人确认结论**；RCA 是建议不是判决 |
| 修复决策 | 分类分级 | LLM 起草修复 SQL/方案，附影响面说明 | **分级裁决**：确定性低风险（格式/枚举/去重）可批自动；金额/口径/歧义必须人 |
| 修复执行 | 机器执行（重跑管道/新批次进料），**不改历史** | 不直接碰数据（MC read-only 是行业姿态） | 供给方协调（上游产物整改的动卡在上游系统与人） |
| 复验关闭 | 规则复验自动复核（re-run 过闸全绿才可关）；关闭自动 + **强制 resolution note** 留痕 | 无必要 | 重要级问题关闭人抽查（审计位） |
| 知识沉淀 | 自动（规则库/报告/文档页） | LLM 从历史问题归纳新规则候选 | 定期人审入库 |

**直接回答"还需要人吗"**：需要，但人从"修数工"收窄为**裁决者与守门人**，四个不可让渡的位置：
1. **金额/口径类修复的最终裁决**——合规与审计责任，全行业一致不敢自动（Monte Carlo/Profisee/Soda 口径一致）。
2. **规则库/阈值变更审批**——LLM 推荐可提效（MC 自称 60% 接受率意味着 40% 不被接受），入库必须人批。
3. **问题单关闭的抽查审计**——自动化关闭 + 人抽查 resolution note，防止"绿灯掩盖错误规则"（复验全绿只证"过了当前规则"，不证"规则本身对"）。
4. **跨供给方协调**——整改的执行主体在上游，管道侧只能隔离、通知、重验。

## 六、对本项目的落地建议

映射对象：dp3 质量闸（validate_batch → QualityReport + clean 数据，20 条规则机判）+ 坏行隔离区（缺口）+ 问题单五态（分发→认领→整改→复核→关闭，缺口）+ 修正回流重新进料（既定方向，湖表 append-only）。

### 6.1 直接抄（业内有官方背书的现成模式）

1. **隔离区 = Databricks quarantine 表模式**：
   - 坏行保留原始 payload + `rule_id` + `report_id/batch_id` + 失败原因，与 clean 数据在同一次闸内产出、同批落盘（append-only 隔离表）；
   - 隔离区带量级监控（超阈值自动升级问题单）；
   - **熔断与隔离分流**：schema 级/系统级故障走 fail-fast 整批拒收（circuit breaker），行级质量问题走隔离（Bigeye 归纳的行业分工，也匹配 20 条规则分级的现实）。
2. **问题单实体对着 Soda incident 建模**：
   - 从 `report_id` 的失败规则**自动生成问题单草稿**（Soda 是人工 Create，我们有机判信号可自动——这是比 Soda 更顺的一步）；
   - 必填 lead（认领态强制，抄 Soda）；状态流转可按 lead/status/severity 过滤；
   - **关闭强制 resolution note**（Soda 的强制字段直接抄）；
   - 后续相关失败结果可挂同一单（防止同一问题重复开单）。
3. **复核 = Metaplane re-run 模式的库内版**：复核动作 = 对该问题单关联的隔离区数据重跑 validate_batch（或供给方修正批次过闸），规则全绿才允许关闭；关闭由复验结果自动触发，重要级问题关闭需人确认。比 Metaplane 更强的一点：我们的复验是确定性规则重跑，不依赖人点按钮的主观判断——但仍保留人确认位（理由见第五节第 3 点）。
4. **修正回流 = append-only 修正批次叠加**：
   - 供给方改产物→新 batch 过闸→append 湖表，绝不做湖内 UPDATE（ClickHouse 版本列 / Kimball 修正记录 / Visier restate 的行业一致性背书）；
   - **问题单关闭条件 = 修正批次落湖且复验全绿**；问题单记录"整改批次 ID"，形成 问题→修正 的可追溯链；
   - 需要自研的只有这一处关联设计——业内没有现成品。
5. **规则库借鉴 dbt severity 语义**：
   - 同一规则两档阈值（`error_if`/`warn_if` 式条件表达式，支持非零/超界/区间）——error 级触发隔离+建单，warn 级放行进湖+记录+累积观察（供后续升降级决策）；
   - `--warn-error` 的思想（运行期可整体把 warn 升级为 error）对应我们"严进/宽进"两种入湖模式开关。

### 6.2 改造（有原型但要适配本项目）

1. **GX Actions 式"闸后动作钩子"**：validate_batch 之后挂 action list（写 QualityReport → 建/更新问题单 → 分发通知 → 更新报告页），动作只承载"记录与通知"，不承载修复——修复一律走供给方重进料；GX 的 `notify_on` 五档映射到我们的规则分级。
2. **LLM 按可信度分档接入**：
   - (a) 归因——LLM 读 QualityReport + 隔离区坏行样本 + 规则命中，起草 RCA 与修复建议 SQL，附到问题单，人确认（抄 MC Troubleshooting Agent"起草不落地"形态）；
   - (b) 规则推荐——LLM 从历史隔离区数据推荐新规则/阈值，人审入库（抄 MC 60% 接受率模式）；
   - (c) **LLM 永不直接写湖表**（read-only 姿态抄 Monte Carlo）。
3. **自动修复限定在派生层**：格式归一/枚举映射/去重做成 clean 之上的规范化视图（或 clean 产出时的白名单变换），原始隔离行永不动；金额/口径类规则命中一律不自动修。dbt-audit-helper 式"修复前后逐行比对"可作为复核报告的组成部分。

### 6.3 不抄（前车之鉴）

1. **不拿 dbt `--store-failures` 式审计快照当隔离区**：无批次外键、无重放入口、覆盖式语义，只适合人看；隔离区必须带批次外键与重放入口（"重放入口=再过一次闸"）。
2. **不抄 Apache Griffin**（2025-09 已退役进 Attic）；**不引 GX Cloud ExpectAI**（随 GX Cloud 停服作废，且仅第三方转述）；GX Core 只作思想参考（商业前景受 Fivetran/dbt 合并格局影响）。
3. **不抄"纯外部工单"模式**：问题单必须是库内一等实体（外键挂 report_id/batch_id，可机判复验、可自动关闭），Slack/webhook/Jira 只做分发通道——学 Soda：incident 在自己系统里闭环，外部只是通知。
4. **不做"全自动复验关闭"的激进版**：全行业都停在"复验按钮 + 人 resolve"；我们最多做到"复验自动通过 → 关闭草稿 → 人确认"，重要级强制人审——不要在关闭环节追求超越行业的自动化。
