# 输入形状：报告键 + 登记信息（报告号/报告名）清单——CLI 参数形状占位；

    for {key, report_id, report_name} in 报告清单:

### 主干二：解析与分块——三策略同场对比，两头防（W-F6-1 分块半程；卡 m6 策略可切换）

```text
伪代码 — app/rag/indexer.py:Indexer.run（m6；签名按卡逐字：run(pdf) -> ChunkBatch）

# 模块级私有配置（策略开关落点——卡面"固定/语义分块可切换对比"；环境可切，卡面签名不动）：
#   _CHUNK_STRATEGY ∈ {"fixed", "recursive", "semantic"}，默认 "recursive"（经典口径：生产系统最常用默认）
#   _CHUNK_TARGET = 512   # 目标块长（token，嵌入件 tokenizer 口径计量）——卡面 256–1024 区间的中位起点
#   _CHUNK_MAX    = 1024  # 硬上限
#   _OVERLAP_RATIO = 0.15 # 重叠 10–20% 区间的中位起点
async def run(pdf) -> ChunkBatch:
    # pdf 入参 = 登记报告对象（主干一）；doc_version 缺省取 1，增量时由主干五定位后 +1
    页块序列 = _parse_pdf(pdf.字节)
    # 主干判断①空文档闸：扫描件无文本层/加密页/损坏文件 → 页块序列为空——
    #   不抛错、不中断整批：返回空批 + 跳过原因（设计范围口径"解析失败/空文档→跳过并记录"）
    if 页块序列为空:
        return ChunkBatch(报告号, 块数=0, 跳过原因="解析产出零文本块")
    # 主干判断②策略分派：同一输入，三种切块器可切换对比——产出形状一致，下游零感知
    块序列 = dispatch(_CHUNK_STRATEGY)(
        页块序列, target=_CHUNK_TARGET, max=_CHUNK_MAX, overlap=_OVERLAP_RATIO)
    # 数据变形：（页码, 文本段）序列 → 块序列 [{块号, 原文, 起始页, tokens}]——
    #   块号规则承设计稿 08：报告号#页码#块序（"volve-completion-01#p14#c3"）；跨页合并的块标起始页
    #   tokens = _tokenize(块原文)（词级分词+停用词滤除，口径注释见主干四——m14 关键词路的语料）
    return ChunkBatch(报告号, doc_version, _CHUNK_STRATEGY, chunk_ids, 块数, 硬切计数, 跳过原因=None)
    # ChunkBatch 为数据形状（同设计稿 08 的 Hits 地位），非公开签名发明
```

```text

def _chunk_recursive(页块序列, target, max, overlap):
    # 主干判断：先按大边界（空行/标题行）聚段；段落攒进当前块直到接近 target；
    #   单段超 max → 降级句边界细切；单句仍超 max → 硬切并计硬切计数（病态长句不丢内容，只记账）
    当前块 = 空
    for 段 in 页块序列:
        if token_len(当前块 + 段) <= target:
            当前块 += 段                                  # 小段合并——块长向目标凑，不碎
        else:
            产出 当前块（附重叠尾句，见下）；当前块 = 段按句边界预切后逐句装入
    产出 末块
    # 数据变形：段落序列 → 块序列，每块 ≤ max、向 target 收敛
    # 重叠实现：相邻块共享尾部 1–2 句（≈ overlap 预算）——按句切重叠，不让句子在边界处腰斩
    #   （经典口径：重叠防"关键句子恰好在边界处被切断"；重叠在防什么、代价是什么 → 取舍 1）
    # 异常去向：空段/纯页码行跳过不产块；硬切计数进 ChunkBatch——账本不静默
```

```text

def _chunk_fixed(页块序列, target, max, overlap):
    # 滑窗：全文拼接后按 target 定步长（step = target − overlap）滚动切——
    #   完全无视段落/标题结构：一段代码、一张表格都可能被拦腰截断（经典口径）。
    #   本节保留它当对照组：同一份报告跑三种策略对比检索质量（设计稿 11 评估的原料）
    return 滑窗块序列

def _chunk_semantic(页块序列, target, max, overlap):
    # 语义切分：全文按句切开 → 句级嵌入（复用主干三同一嵌入件）→ 相邻句余弦相似度 →
    #   在相似度骤降点（语义断崖）下刀 → 块内合并至预算。
    # ★ 切分用的句级嵌入是"切分派生物"：算完即弃、不入任何索引——索引里只有正式块的向量
    # 代价：索引期多一整轮全文句级嵌入（这是"语义可切、默认不切"的成本依据，取舍 2）
    return 语义块序列
```

## 关键判断的取舍记录

1. **重叠 10–20% 在防什么、代价由谁付**——防的是一件事：关键句恰好在切块边界被腰斩（书原文口径），重叠让边界句在相邻块里有完整副本。代价有三笔，如实记账：①语料重复——共享句出现在两个块里，BM25 语料词频统计把共享句算两遍，命中词的 df 轻微抬高、IDF 略降（语料级统计的系统性小偏移，不改变排序大局）；②向量路两块近似重复，同一次查询可能双双进候选、占掉两个候选席——去重与取舍归设计稿 10 的融合/精排（本设计稿只保证块本身真实）；③存储与嵌入量净增 10–20%。换边条件：切块按句/段自然边界对齐（本设计稿递归策略已按句切）时，腰斩风险本身下降，重叠预算可收窄；固定滑窗策略则必须保留重叠——这就是对照组存在的意义。
2. **默认递归、语义可切不默认；关键词路走分词 BM25 不走 lexical_weights**——两个"选更简单的那边"同源：①语义切分质量更高（块内主题单一）但索引期多一整轮全文句级嵌入，且切分嵌入是即弃派生物——报告类文档有天然结构（章节/段落），递归按结构切已拿到大部分收益，语义切分留给无结构长文本（扫描 OCR 流）再开；②bge-m3 的 lexical_weights 与分词 BM25 是两个稀疏口径：前者权重语义更"神经"、但词频已折叠喂不进 m14 的 tokens 契约，后者词级可读、与设计稿 08 已验的 BM25Okapi 打分直接咬合。设计范围"稠密+稀疏双表示一次产出"由 encode 调用形状兑现（红线）；稀疏位在关键词路的实际落点是分词 tokens，lexical_weights 留作官方稀疏匹配分素材。换边条件：语料失去文档结构，或 m14 未来扩"词项权重索引"卡面时，两边各自换向（扩卡修订，接口面不动）。
3. **嵌入真身是 m6 本地 bge-m3 封装，不经 Gateway.embed（头部声明的展开）**——备选是走设计稿 07 的 `Gateway.embed`（petro-embed 别名，`POST /v1/embeddings`）。不选的硬理由：OpenAI embeddings 响应形状只有稠密位，设计范围验收要求的稀疏表示经该形状回不来；且设计范围红线与 W-F6-1 走查列把 encode 调用钉在 `Indexer.run` 路径内。边界规则第 1 行管"模型 API 端点外呼"，本地推理件零外呼不构成绕行（FlagReranker 同形先例：W-F6-3 就是 `Ranker.rerank` 直调）。代价：嵌入量不走网关记账口径，成本可见性落在离线索引的 span 打点与运行日志（调用方纪律，设计稿 17 装配起）。`Gateway.embed` 仍是 API 路线（text-embedding-3 类）的统一入口，本设计稿不接线不删除。换边条件：嵌入换 API 模型、或稀疏表示需要经网关消费时重新裁定——但稀疏需求不改则本地路线不变。
4. **"图 3 的孔隙度分布"纯文本分块注定答不好（事实性记录，为设计稿 10 拒答/多轮追问埋伏笔）**——链条三层：①解析层：PDF 的图是位图/矢量对象，`_parse_pdf` 只取文本流，图内数据点（孔隙度分布曲线的数值）从未进入系统，进系统的只有图题文字（"图 3 孔隙度分布"）；②分块层：图题文字按普通段落分块，与正文数字描述的关联被块边界切断（书口径：分块切断片段与原始上下文的联系是固有缺陷）；③检索层：查询"图 3 的孔隙度分布"向量路高概率命中图题块（字面/语义都近），但块里只有标题没有分布——生成层无据可引。这不是本设计稿的 bug，是纯文本管线的形状极限：设计稿 10 的拒答闸（W-F6-5）是这条链的兜底出口；§F6"不做什么"已声明多模态图表入库不做完整实现，原书 §超越扁平文本（结构化索引）是升级方向的原文出处。此处只存事实。增量更新的"删分两半"（BM25 物理删、向量路逻辑删）与物理清除的后续扩卡裁定，见主干五与头部声明②，不另立条。

## 锚点对照精要

**RAG基础·文档分块（分块三策略与块大小/重叠）**（卡 `m6` 锚点 K-B 第一项）
书：分块必不可少，原因有二——嵌入模型输入长度有限且整篇单向量多主题互相稀释；检索目标是只把相关部分注入上下文。三策略：固定大小切分（简单可预测、无视结构）、递归/结构感知切分（按自然边界递归降级，生产系统最常用默认）、语义切分（相邻句嵌入相似度断崖处下刀，质量高但多一轮嵌入计算）；起点参数 256–1024 token、重叠 10–20% 再实测调优。落点：本设计稿三策略全数落地可切换、默认递归；参数区间照书取中位起点；书预告的固有缺陷（"该公司"指代悬空在块外）在本设计稿以块元数据（报告名/页码/版本）做引用定位级的部分补偿，语义级补偿（上下文感知检索）不做。

**RAG基础·稠密嵌入**（卡 `m6` 锚点 K-B 第一项）
书：稠密嵌入把文本映进高维向量空间，语义相近则向量相近，常用余弦相似度度量"近"（关心方向不关心长度）；从 Word2Vec 静态词向量演进到 BERT/BGE-M3 的上下文感知表示，且书注明 BGE-M3 实际同时输出稠密/稀疏/多向量三表示。落点：本设计稿用的正是 bge-m3 的稠密+稀疏两路输出（书叙述只用稠密作例，我们比书多用了稀疏位但没动 multi-vector）；相似度度量上书讲余弦，我们入库走官方内积形状——归一化前提下两者等价（主干三口径注释），与设计稿 08 的 l2 排序单调相容。

**实验 3-4·ANN 索引（ANNOY vs HNSW）**（卡 `m6` 锚点 K-B 第一项，机制归属 m14）
书：ANN（近似最近邻）在海量向量中跳过逐一比对、经索引结构实现近似但极快的查找；表 3-2 对比 ANNOY（树：构建快、内存低、不支持增量需完全重建）与 HNSW（图：构建较慢、内存较高、查询精度极高、支持增量更新但长期插入后建议定期重建保持精度）。落点：设计稿 08 的 Chroma 集合底层即 HNSW（`configuration={"hnsw": {"space": "l2"}}`）；本设计稿增量更新的形态与书中判断同构——向量路长期 upsert 增量插入（HNSW 允许但留重建建议），BM25 路干脆每轮全量重建（重建式增量）；定期重建向量路属运维动作，不在六函数与本设计稿范围。
