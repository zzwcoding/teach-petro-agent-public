class SuggestionPool:
    def __init__(self, repository):
        self._repo = repository                 # m3 公开面：save_snapshot（建议池自己的资产）+ save_audit
                                                #   ——对 semantics/ 权威目录零写出口（结构保证，取舍 1）

    async def submit(self, source, evidence) -> suggestion_id:
        # ── 主干判断① 🛡️ 形状闸：按 source 校验证据形状——发现机制不同、入口契约统一 ──

        建议置信度 = 推导置信度(source, evidence)   # benchmark 0.95 档（有手算金标对照）/ checkup 0.90 档
                                                #   （确定性判据命中）/ runtime 按簇规模升档但封顶 0.70
                                                #   （实时有噪声——锚方案 三源行三短语，主干四）

        if 既有 := self._查指纹(指纹):

**为什么四字段是"统一"的全部**：三源的发现机制差异极大（跑批跑一次几十分钟、体检全量扫一遍、信号每秒都在发生），如果入池形状跟着机制走，池子就是三个清单的拼盘——分诊人要在三种格式间换脑子，"统一收口"就只剩口号。四统一字段把差异**压进两列**：source 列保留机制身份（分流可查），证据列保留机制细节（分源形状），其余列对分诊人只有一种读法。锚方案（DataBuddy 受控进化，AE 前沿方案报告 §⑤ 受控进化行）："三源信号统一建议池——监督源 Benchmark 慢准有基准 / 自检源 实体体检静态全量 / 交互源 Runtime 信号实时有噪声"——三个短语各管一源的气质，四字段把它们接进同一个入口。

## 关键判断的取舍记录

1. **"建议池只产建议不直接变更资产"是结构保证（落库面没有写语义资产的出口），不是提示词约定。** 备选：允许池子带一个"低风险自动应用"开关（比如补同义词这种"看起来安全"的变更）。否决理由：低风险变更的判据本身就是治理决议（同义词补错就是黑话复活闸的绕道——设计稿 35 捣乱输入 B 的同款事故由池子亲手犯）；且边界规则表 v3 增补行把"语义资产文件只能经 Lifecycle 变更包+五级 CI+Owner 审批变更"写成全库唯一通道，池子开任何直写口都是对该行的破坏。"不可表达优于被禁止"的工程含义：接口上没有的路不会被人走（捣乱输入 A 三层否决）。代价：一条建议从发现到落地要跨"池→确认→提案→门禁→合并"五站，慢。收益：每站都是责任锚点，"自动化止于提案，责任归于 Owner"（锚方案 运营机制行）从口号变成拓扑事实。换边条件：无（本节灵魂）。
2. **置信度分源分档（0.95/0.90/≤0.70），是排序输入不是真值度量。** 备选：统一置信度算法（比如全走频次统计）。否决理由：三源的"证据强度"本质不同——benchmark 有独立对照物（手算金标/门禁判据），错就是错；checkup 是确定性判据但判据是登记质量不是行为对错；runtime 频次高只说明问题常见，不说明结论对（40 次"检修产量"落空里模型猜的口径仍然没有任何人背书——交互源现场给出的教训）。分档把"哪源的话更可信"显式写进机制，分诊人不用自己重建这份判断。锚方案 三源行三短语（慢准有基准/静态全量/实时有噪声）就是三档的出处。换边条件：某源长期零误报且积压——上调该源档位与自动分诊比例，档位表进配置。
3. **聚类用归一化+指纹+频次计数，不引入向量检索或模型判重。** 备选：语义嵌入聚类（把落空问法embed 后按相似度聚簇）。否决理由：一是模型流量零新增是本节框架红线（确定性加权伪代码）的自然延伸；二是指纹聚类的**可解释性**是治理必需——分诊人要能问"这 40 次为什么算一簇"并得到"同归一词+同信号类型+同现场归一"的机械回答，嵌入簇给不了；三是真异写法（"检修的产量"/"扣掉检修的产出"）各自成簇反而诚实——它们该不该合并本来就该 Owner 看，不该聚类器猜（设计稿 22 模糊兜底开窄门的同款哲学）。代价：簇可能偏碎。收益：每簇可对账、可审计。换边条件：同义异形落空占比成为主要噪声——后续议"指纹归一化规则"扩条目，仍不引入模型。
4. **同对象多源不合并，聚合只在展示层。** 备选：池内按 subject 去重合并（"检修产量"只留一条，三源证据拼一条）。否决理由：三源证据链的出处互斥（金标 diff/判据红项/trace 现场），合并条目的"证据"字段将变成混合物，回查任何一源都要拆开——证据可查性是四统一字段里最不能牺牲的一列（三域冷启动"候选不带证据不收"的同款闸）；且多源同指本身就是高价值信号（"三个独立机制都说这里有病"），合并恰好把这个信号抹掉。落定：池内条目永不合并且幂等键含 source，triage 展示层按 subject 出"同指视图"。换边条件：无。
5. **四维权重与验收线（25/30/25/20、线 80）是设计档位，判据清单才是本体。** 权重出处=设计范围四维排序给定的确定性加权（锚方案四维实体体检评分——原始方案未给数值档，设计档显式声明），线 80 同为档位。之所以敢用拍脑袋的档位：四维判据全部机器可查、逐条可复算，权重变了对同一资产的重算结果仍然稳定可解释——体检的价值在"哪一维红了、红在哪个判据"，不在总分的小数点。取舍 5 的换边条件与置信度档位相同：真实运营攒出误报/漏报分布后调权重与线，判据清单不动。
6. **数据覆盖维引用设计稿 34 报告而不自己跑 SQL。** 备选：体检现场对生产库/模型物发起非空率统计。否决理由：一是"评估链路写问数主链路状态"的只读纪律（边界规则表 m18 主语行）虽不禁止读，但体检每卡现场查库会把静态全量扫描变成一场全库压测（20 卡×4 判据×8 表）；二是设计稿 34 CheckReport 的命中记录本就是数据事实的既有沉淀（设计稿 34 钩子："本节只在失败报告的建议栏留出口"）——复用它，"规则命中→问题单生成"的行业闭环（设定书 §4）才首尾相接：设计稿 34 出报告命中，设计稿 42 把命中转成带 Owner 的建议。报告缺失时判 0 分并标注"无覆盖证据"——缺证据按无覆盖算，fail-closed（设计稿 36 白名单同哲学）。换边条件：报告时效性成为误报主因——给报告加水位校验（读设计稿 34 报告的批次时间戳），仍不自己跑。
