### 主干一：GoldenStore.add——手算金标关卡（W-F15-1 的判据半边）

```text
伪代码 — app/eval/golden_store.py:GoldenStore（m18；签名=卡 m18）

class GoldenCase:               # 数据形状——入册单元（卡面注释：question×N 问法/golden_sql/golden_result(手算)/metric_ref/owner）
    case_id: str                # "gc-0001"（入册时分配；同原问指纹幂等，见 add 判断⑤）
    原问: str                   # 业务真实问题（外部调研：评测集"一定不能自己写"——原问必须来自真实提问）
    问法组: list[str]           # [原问, 扩写1, 扩写2, ...]——同一语义的 N 种问法（主干二扩写产物；W-F15-3 的跑批素材）
    golden_sql: str             # 人工撰写的参考解法——给评审人读的对照物（外部调研："必须带参考解法"）；
                                #   本节评估不跑它也不拿它判分（判分只认行集，取舍 1）
    golden_result: 行集 | None  # 🛡️ 手算金标行集——关卡判据本体（None 即拒收）
    数值容差: float             # 注册声明（如 0.01——聚合 ROUND 的尾差不算错）；缺省 1e-6
    顺序语义: bool              # 缺省 False=行集无序（多重集合比对）；True=按 排序键 声明逐位比（如按月份序列）
    排序键: list[str]           # 顺序语义=True 时的列名声明（主干三排序规范化读它）
    金标出处: str               # 🛡️ 只收"手算"——Excel 对台账独立算的；"程序算/BI 现算/模型算"一律拒收
    metric_ref: str | None      # 指标关联（m16 注册表内必须真实存在——add 判断④校验）
    owner: str                  # 责任人（出问题找谁修口径/修问法——badcase 登记时沿用它）
    source: {kind, parent_case} # 人工原题 | AI 扩写（扩写件记 parent_case 指回原题——金标同源可追溯）

class GoldenStore:
    def __init__(self, repository, registry):
        self._repo = repository                 # m3 公开面：save_snapshot（册子与索引落库）——零引擎内部触碰
        self._registry = registry               # m16 公开面：MetricRegistry.get（metric_ref 关联校验，只读）
        self._索引 = {}                         # 内存索引：metric_ref → [case_id]（装载期建，sample_fewshot 读它）
        self._册版本 = 0                        # 每次入册 +1——sample_fewshot 的锁键半边（主干四）

    async def add(self, case) -> case_id:
        # ── 主干判断① 🛡️ 手算金标关卡（W-F15-1 判据半边）——闸在入册口，坏资产进不来 ──
        if case.golden_result is None or case.金标出处 != "手算":
            raise GoldenCaseRejected(case.原问,
                fix_hint="先按台账/报表人工算出结果再入册——AI 算的、BI 现算的、模型跑 golden_sql "
                         "得来的都不是金标：拿被评系统验证被评系统是自证循环（见捣乱输入 A）")
        if not case.owner:                      # 主干判断②：无主资产不收（设计稿 22 口径文件缺 owner 拒装载同款哲学）
            raise GoldenCaseRejected(case.原问, fix_hint="每条 golden 必须有 owner——错例要有人认领")
        问法组 = 去重(case.问法组 or [case.原问])  # 主干判断③：问法组至少含原问且互异——重复问法会虚增矩阵
        if 首词(case.golden_sql) != "SELECT":      # 主干判断③'：参考解法完整性初检（只查形状——真跑归被评链）
            raise GoldenCaseRejected(case.原问, fix_hint="golden_sql 是给人读的参考解法，须是单条 SELECT")
        if case.metric_ref is not None:         # 主干判断④：指标关联必须真实（W-F15-1"按指标关联"）
            self._registry.get(case.metric_ref) #   m16 公开面只读——幽灵 metric_ref 拒收，册子不指向不存在的口径
        指纹 = 问法指纹(case.原问)               # 主干判断⑤：幂等——同原问重复提交返回既有 case_id，册子不翻倍
        if 既有 := self._查指纹(指纹):
            return 既有.case_id
        case_id = "gc-" + 日期序号()
        await self._repo.save_snapshot(f"golden:{case_id}", 序列化(case))
        await self._repo.save_snapshot("golden_manifest", 序列化(self._重建索引()))   # 索引快照随册更新
        await self._repo.save_audit({"类型": "golden 入册", "幂等键": case_id, "owner": case.owner,
                                     "金标出处": "手算", "问法数": len(问法组)})
        self._册版本 += 1                       # 版本只在入册边界推进——问的一生内不换血（主干四）
        return case_id
        # 异常去向：GoldenCaseRejected 是业务闸不是故障——调用方（入册脚本/人工）拿到 fix_hint 后走人，
        #   不重试不降级；册子不可达（m3 故障）结构化上抛——评估是旁路，失败不拦问数业务
```

**为什么是硬闸不是告警**：金标的公信力来自"独立于被评系统的人工对账"——外部调研，好评估任务的标准是"两位领域专家独立得出相同 pass/fail 结论"；另一条调研结论更直接："每题必须有手算的结果"。放一条"程序算的金标"进册，等于把模型的自信（或 BI 的口径）抄进答案页再拿它判模型——评估从证据退化成仪式。宁缺毋滥：册子薄而可信，厚而可疑不如无。

### 主干二：问法扩写——AI 只扩问法，不碰金标（W-F15-1 的数量半边：10 真实 × 5 问法 = 50 条）

```text
伪代码 — app/eval/golden_store.py:GoldenStore.扩写问法（m18 私有件；模型调用经 m2——边界规则第 1 行）

# 模块级私有常量 _EXPAND_TEMPLATE（冻结系统提示词）：把给定问题改写成 N 种说法——
#   只许改问法（措辞/语序/口语化），不许改语义要素：井号/时间窗/范围/指标词逐字保留；
#   输出 JSON 数组。扩写是"同一道题的不同念法"，不是"不同的题"
async def 扩写问法(self, case, n=4) -> [GoldenCase]:
    resp = await Gateway.chat(
        messages=[{"role": "system", "content": _EXPAND_TEMPLATE},
                  {"role": "user", "content": case.原问}],
        model_alias="petro-llm", stream=False)          # m2 网关非流式（设计稿 07 形状；扩写是批处理）
    扩写件 = []
    for 问法 in 从回复抽取 JSON(resp.content)[:n]:
        件 = {**case, "原问": 问法, "问法组": [问法], "source": {"kind": "AI 扩写", "parent_case": case.case_id}}
        #   ↑ 金标三件（golden_result/golden_sql/金标出处）与 owner/metric_ref 原样继承——
        #     扩写不产生新金标（外部调研"AI 扩写生成问法"；"每题必须有手算的结果"不因扩写豁免）
        件.case_id = await self.add(件)                  # 走同一个 add 闸——扩写件无金标同样拒收（防绕道）
        扩写件 += 件
    return 扩写件
    # 入册口径声明：W-F15-1 的"扩写至 50 题"按问法条目计——10 个 case × 5 问法 = 50 条；
    #   金标仍是 10 个（扩写共享原题金标）。扩写纪律由模板锁死+add 闸兜底：问法改了语义要素
    #   （时间窗变了）会让金标失配跑出假 fail——那是扩写的 bug，在评估报告里肉眼可查（走查推演 2 的对照）
    # 记账事实：扩写调用同过网关 spend 双写（设计稿 07）——10 题 × 1 次 ≈ 10 次调用，一次性成本
```

### 主干三：ResultGrader.compare——行集比对三出口（W-F15-2）

```text
伪代码 — app/eval/grader.py:ResultGrader（m18；签名=卡 m18：compare(expected, actual) -> pass | fail(diff) | inconclusive）

class GraderDiff:               # 数据形状——fail 的载荷：证据不是裸的"不相等"（坏例要能一眼看到错处）
    仅金标有: list[行]          # 排序对齐后金标侧多出的行
    仅实际有: list[行]          # 实际侧多出的行——"多了别的区块"这类错在这里现形
    超容差: list[{列名, 金标值, 实际值, 差值}]   # 数值同位不一致的单元格清单
    行数: {金标: n1, 实际: n2}

class ResultGrader:
    def compare(self, expected, actual):        # 参数只有两个行集——SQL 文本不是输入，文本比对在接口上不可表达
        # ── 主干判断① 列结构对齐：按列名（归一化大小写/空白）对位——SELECT 别名不同不算错，列对不上才是错 ──
        if 列名集(expected) != 列名集(actual):
            return inconclusive                 # 列结构不一致可能是口径/版本差异——评估器自己不确定时不装裁决，
                                                #   转人工比对（三出口的第三口：不猜）
        # ── 主干判断② 排序规范化（数据变形）：顺序语义=False（缺省）→ 两侧行各自转规范化元组后按全列排序，
        #   消除行序噪声——数据库不承诺无 ORDER BY 的行序，行集语义是多重集合不是序列；
        #   顺序语义=True → 按注册声明的排序键逐位对齐，错序即 diff（月份序列这类"次序即业务"的行集）
        金标行 = 规范化排序(expected, 顺序语义, 排序键)
        实际行 = 规范化排序(actual,   顺序语义, 排序键)
        # ── 主干判断③ 数值容差：数值列按注册声明的容差比——聚合 ROUND 尾差（98.6 vs 98.600001）不算错；
        #   字符串列归一化空白后全等比。容差内视为同值，超容差记入 diff
        # ── 主干判断④ 行对齐与裁决：排序后逐位对齐——
        if 金标行 == 实际行（容差内全等）:
            return pass                         # 行集一致即 pass——哪怕两段 SQL 一个字都不像（评产出不评路径）
        return fail(GraderDiff(仅金标有=差集左, 仅实际有=差集右, 超容差=数值扫描, 行数=计数))
        # 三出口语义：pass（行集一致）/ fail(diff)（行集不一致，带证据）/ inconclusive（列结构对不上、
        #   类型不可比——转人工）。没有第四种"差不多"：grader 的输出必须能被下游机械消费（稳/不稳的判据）
        # 边界对照：拒绝朴素 SQL 字符串匹配（外部调研 "not a naive string match"）在本卡是结构性的——
        #   compare 的签名里没有 SQL 参数，字符串匹配不是"被禁用"而是"不可表达"（取舍 1）
```

```text
伪代码 — app/eval/stability.py:StabilityRunner（m18；签名=卡 m18：run(case) -> [trial]）

class trial:                    # 数据形状——一次试验的现场（fail 时整包进 badcase）
    问法: str                   # 本 trial 用的问法（矩阵的行）
    重复序: int                 # 矩阵的列（同问法第几次）
    thread_id: str              # "eval:{case_id}:{问法序}:{重复序}"——一 trial 一干净会话（外部调研：
                                #   "每次 trial 用干净环境隔离状态"，上一 trial 的上下文不渗进下一 trial）
    grader 结论: str            # pass | fail | inconclusive（ResultGrader 三出口原样透传）
    sql 现场: str               # 生成的 SQL——只作现场附件供人读，不参与判分（取舍 2）
    diff: GraderDiff | None
    badcase_id: str | None      # fail/inconclusive 时登记所得

class StabilityRunner:
    def __init__(self, grader, 读快照, 被评执行器):
        self._grader = grader                   # ResultGrader 同卡注入（卡面 Adapter FakeGrader 走查时换入）
        self._读快照 = 读快照                   # m3 结果快照回读（只读公开面）
        self._被评执行器 = 被评执行器            # Seam：执行器是注入的可调用——评估依赖倒置，不 import 主链路；
                                                #   走查注入替身（固定轨迹+行集样本），脚本侧装配真实链公开入口
    async def run(self, case, 问法数=5, 重复次数=1) -> [trial]:
        # 关键字默认参=基线档位 5×1（对齐 W-F15-3"5 种问法"）；卡面签名主干不破（取舍 3）
        trials = []
        for 序, 问法 in enumerate(case.问法组[:问法数]):
            for 次 in range(重复次数):
                tid = f"eval:{case.case_id}:{序}:{次}"
                执行 = await self._被评执行器(问法, tid)     # -> {终态结论, 快照号, sql 现场}
                actual = await self._读快照(执行.快照号)      # 结果快照回读——评估只读，不写主链路任何状态
                结论 = ResultGrader.compare(case.golden_result, actual.行集)
                badcase_id = None
                if 结论 is fail:                             # W-F15-3：fail 自动登记 badcase（主干六）
                    badcase_id = await Badcase.register(query=问法, answer=执行.结果摘要,
                                                        expected=case.golden_result, owner=case.owner,
                                                        metric_ref=case.metric_ref)
                elif 结论 is inconclusive:                   # 不确定也不是稳——同样登记但标待人工比对
                    badcase_id = await Badcase.register(..., kind="inconclusive_待人工")
                trials += trial(问法=问法, 重复序=次, thread_id=tid, grader 结论=结论,
                                sql 现场=执行.sql, diff=结论.diff, badcase_id=badcase_id)
        return trials        # "稳"的判定在汇总件：all(t.grader 结论 == pass)——全 pass 才标稳（取舍 3）
                             #   inconclusive ≠ pass：评估器自己不确定的试验不能计入"稳"（不猜）
                             # 异常去向：执行器抛错（主链路结构化失败）→ 该 trial 记"执行失败"行并计数，
                             #   不中断整批（设计稿 11 跳过计数同款口径）；册/快照源不可达 → 结构化上抛
```

## 关键判断的取舍记录

1. **行集比对是唯一判据：排序键声明→列名对齐→数值容差→行对齐 diff；SQL 文本与 AST 在判据里结构性缺席。** 备选一"SQL 文本相似度"：被判走查推演 1 的 trial B 直接否掉——90% 相似的坏 SQL（漏一个 WHERE）正是最危险的假阴性，而 trial A 的子查询重写（40% 相似的好 SQL）会被误杀；备选二"AST 结构比对"：同样评的是路径不是产出，且把"合法变体"当错误是 code-based grader 的已知脆弱性（外部调研：code grader "fast, cheap, objective, reproducible，但对合法变体脆弱"）。多重集合语义（缺省无序，注册声明顺序语义才逐位比）来自数据库的本分：无 ORDER BY 的行序不承诺，把行序当差异是评估器在发明错误；数值容差同理——ROUND 尾差不是口径错误。三出口的第三口 inconclusive（列结构对不上）宁可转人工不猜：评估器输出必须能被"稳/不稳"机械消费，装出来的裁决比没有裁决毒。**换边条件**：行集结构比对覆盖不了的语义等价（行集同、但列含义张冠李戴）出现高频 case 时，补 model-based grader 做第二意见——确定性判据仍是第一道。
2. **"评产出不评路径"与 AST 安全闸的分工：安全校验拦路径，效果评分只看终态——两半合起来才完整，谁也不替谁。** 外部调研的告诫原文："it's often better to grade what the agent produced, not the path it took"。落地分工：`m17` 校验链管**路径合法性**（SQL 能不能跑、越没越权、新不新鲜——确定性闸，拦的是"不可用的产出"），本节 grader 管**产出正确性**（行集与手算金标一致否——确定性判分，评的是"可用的产出"）。两半的边界画在哪：安全闸不评"对不对"（放行的语句结果可能仍错——走查推演 2 问法 4 全程通过校验链、行集照样错），grader 不评"该不该"（行集一致的越权查询在安全侧就该被拦，轮不到评估放行）。**关键推论**：评估用例里必须保留"会 fail 的路径"——trial B 这类"看起来对"的样本是证据链的核心资产；全 pass 的评估集是单边评估（见取舍 4）。
3. **"稳"的判定取 Pass^k 语义（全 pass 才稳），试验矩阵参数化（问法 × 次数，基线档 5×1），inconclusive 不计入"稳"。** 同一问 5 种问法只要一种答错，业务上就是"不稳定"——书口径（设计稿 11 已引）：Pass@k（k 次至少一次过，能力上限）与 Pass^k（连续 k 次全过，业务可靠性）相差悬殊，油田考核场景要的是后者。矩阵两个维度各有含义：问法轴测"语义层与生成的鲁棒性"（同一道题换念法不能换答案——Genie 官方同样要求"测同一问题的多种问法"），次数轴测"生成随机性"（同问法重跑不该漂）；基线档 5×1 先把问法轴立起来（成本可控），次数轴留参数升级。卡面签名 `run(case) -> [trial]` 以关键字默认参扩档位、主干不破；"稳"的判定放汇总件而不放 runner 返回值——trial 列表是证据，稳定结论是从证据机械推导的（推导规则一行：all pass）。**换边条件**：评估集上百题后按 case 分层抽测（高频 case 全矩阵、长尾 case 抽 1 法），矩阵档位进配置。
4. **评测集建设纪律成文：业务真实题起步 + AI 只扩问法 + 手算金标必需 + 正负两边都要有。** 四件套的出处与落点：①"一定不能自己写"（外部调研 Q&A——自己写的评测集"太全面"但脱离真实问法）→ `add` 的原问字段必须来自真实提问，入册审计记录 owner；②"AI 扩写生成问法"（外部调研）→ 主干二只扩问法、金标同源继承、仍过同一道 add 闸（防止扩写变成绕过金标关卡的旁门）；③"每题必须有手算的结果"（外部调研）+ "20-50 个真实失败任务是好起点"（外部调研）→ 10 真实题 × 5 问法 = 50 条问法的数量口径，手算金标是硬闸（捣乱输入 A 的两批拒收就是这条纪律的执法现场）；④"One-sided evals create one-sided optimization"（外部调研）→ 本节的对冲是**双边证据**：golden 正例测"该对的要对"（跑批半边），m19 注入红队用例测"不该发生的别发生"（导出半边）——两边合进同一份导出物（主干七），任何半边单独漂绿都不算系统健康。**边界**：BIRD mini_dev 这类现成评测集（外部调研，500 题可本地跑）定位是题型参考库不进生产册——册子的公信力来自自家业务的手算金标，外来题没有老王的台账可对。

## 锚点对照精要

**golden SQL 与执行结果双重比对 + 生产金丝雀（外部调研）**：原文——OpenAI 内部数据智能体的评估是"策展的问答对 + 人工撰写的 golden SQL"，**同时比较 SQL 文本与执行结果数据**，由 Evals grader 打分（"not a naive string match"，并非朴素字符串匹配）；配套"unit tests that run continuously... canaries in production"（持续运行的单元测试……生产中的金丝雀）。落点：ResultGrader 只认行集（compare 签名无 SQL 参数——双重比对里"文本比对"那半边我们没有收：文本对错没有业务含义，行集才是产出，取舍 1）；promptfoo 导出即"持续单元测试"半边，`promptfoo eval -c` 的退出码让金丝雀可挂载。差异：OpenAI 的 canary 跑在生产流量旁，我们的跑批走评估会话（`eval:` 前缀 thread_id）——离线金丝雀，零生产干扰。

**outcome vs trajectory 与三类 grader（外部调研）**：原文——"Each grader evaluates some portion of either the transcript or the outcome"，outcome 的例子正是数据库终态；"it's often better to grade what the agent produced, not the path it took"；三类 grader 选型口诀"deterministic graders where possible, LLM graders where necessary, human graders judiciously"；"20-50 simple tasks drawn from real failures is a great start"；"One-sided evals create one-sided optimization"。落点：行集比对是 outcome 判据的教科书形态（不问生成器怎么写、只问数据库里算出来什么）；选型口诀落成本节与设计稿 11 的分工——有金标的问数侧用 code grader（本节），无金标的文本侧用 model grader（设计稿 11），inconclusive 转人工是 human grader 的审慎用法；50 条问法的数量口径与红队半边的双边对冲见取舍 4。

**Genie example SQL / benchmark questions 双用（外部调研）**：原文——example queries 让 Genie "match user prompts to verified SQL queries and learn from examples"；复核过的问题收进 benchmark questions "test and score your agent for overall accuracy"，还要**测同一问题的多种问法**。落点：golden 问答对"一鱼两用"（few-shot 引导半边 `sample_fewshot` 进生成冻结段 + 评估基准半边进跑批）就是这条产品化做法在本节的落形；5 问法矩阵是"同一问题多种问法"的机制化（主干五问法轴）。差异：Genie 的 example/benchmark 是产品内两套界面，我们是同一册子的两个消费口——资产只有一份，纪律（人工复核过才入册）天然一致。

**Q&A 评测集方法论（外部调研）**：原文——评测集"一定不能自己写"，自己写的"太全面"但脱离真实问法；正确姿势"业务给 10-20 个真实问题 + AI 扩写生成到 ~100 题"；"每题必须有手算的结果"；两阶段目标"先正确率（召回对问题 + 结果与手算一致），后降本与性能"。落点：主干一的硬闸（金标出处=手算，其余拒收）、主干二的扩写纪律（只扩问法继承金标）、10 题起步的数量口径，三条逐字对应；"先正确率"落成本节只评 pass/fail 不评成本延迟（网关记账那是设计稿 07/12 的事，不进质量证据链）。差异：该调研扩到 ~100 题，基线档 50 条（取舍 3 的 5×1 矩阵口径）——规模换边条件是册子运营起来之后，闸与纪律不随规模变。

**promptfoo（断言 + 红队，CI 友好）**（外部调研）：原文——promptfoo "Test your prompts, agents, and RAGs"，含红队/渗透/漏洞扫描；"适合放进 CI 当'持续金丝雀'（呼应前一条调研 '持续运行的单元测试……生产中的金丝雀'）"。落点：主干七的 yaml 三段顶层键（prompts/providers/tests + vars/assert）与 `promptfoo eval -c` CLI 序列按官方契约交付；红队半边不自己发明用例格式——借 `m19` 的 `RedteamCases.all()`（设计稿 25 真身），断言用 contains（拒绝话术指纹）+ not-contains（禁行痕迹）两件机械判。差异：该调研设想的是"越权红队用例管理"，本节把管理位让给设计稿 19 的用例表、只做导出位——用例一处维护，两个消费方（外发闸演练/评估导出）不写两份。

**BIRD mini_dev（题型参考，一句话）**（外部调研）：官方可本地跑的 500 题评估子集——本节定位为题型参考，不进生产册（取舍 4 的边界声明：册子公信力来自自家业务手算金标，外来题没有台账可对）。
