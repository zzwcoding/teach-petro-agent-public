### 主干一：引擎与会话工厂——方言接缝唯一入口（W-F3-1 的机制前半）

```text
伪代码 — app/db/engine.py:build_engine（m3，方言接缝唯一入口）

_engine: AsyncEngine | None = None                   # 模块级单例占位：引擎全应用只建一次（官方模式要点 1）

def build_engine(url: str) -> AsyncEngine:
    # 输入形状：连接串——不从调用方代码里硬编码，由部署环境注入后传入（外置的意义见主干四）
    global _engine
    if _engine is not None:
        return _engine                               # 重复装配直接复用——池是进程级资源，建两次等于泄漏一半
    _engine = create_async_engine(
        url,                                         # 方言+驱动全在串里：postgresql+asyncpg://… 或金仓路径（主干四）
        pool_size=10,                                # 常驻连接数：并发常态水位（官方形状）
        max_overflow=20,                             # 允许临时再借 20：峰值水位 10+20=30
        pool_pre_ping=True,                          # 借连接前轻量探活：拿到的不再是半夜被服务端踢掉的死连接
    )
    return _engine
    # 异常去向：url 方言段不被识别 / 驱动未装 → 引擎创建即抛——配置错误在装配期暴露，不拖到首笔请求
```

```text
伪代码 — app/db/engine.py:get_session_factory（m3）

_factory: async_sessionmaker | None = None

def get_session_factory() -> async_sessionmaker:
    global _factory
    if _factory is None:
        _factory = async_sessionmaker(
            build_engine(读环境变量数据库连接串()),       # 装配链：工厂首用时刻建引擎——连接串唯一来源=环境
            expire_on_commit=False,                    # ★ W-F3-1 断言的机关，意义见下段
        )
    return _factory
    # 装配期异常去向同 build_engine（方言/驱动错即抛）；应用关闭时 lifespan 末尾
    #   await build_engine(连接串).dispose() 释放池（官方模式要点 4），装配细节本设计稿不展开
```

**expire_on_commit=False 的意义**（默认 True 会发生什么）：commit 成功的一瞬，ORM 默认把实体全部属性标记"已过期"，之后任何一次属性访问都触发一条补查 SELECT 回库刷新——同步程序里这只是多一条查询；asyncio 程序里这是**隐式 IO**：补查是同步的懒加载，在会话 await 上下文之外触发就撞 greenlet 边界炸错。设为 False，提交后属性就是内存值：W-F3-1 断言"commit 后实体属性仍可读"由此成立，且与 `lazy="raise"`（捣乱 A）同属一套纪律——**asyncio 下不允许任何 SQL 藏在属性访问后面**。

**连接池参数与第 N+1 请求的下场**：池上限 = pool_size(10) + max_overflow(20) = 30。asyncio 下协程不占线程，池其实比线程模型更难打满；但**占用不取决于 CPU，取决于"谁攥着连接在 await"**——一个慢事务（await 里卡着没 commit）就白占一个坑。第 31 个并发借连接请求：不报错、不无限等，按 `pool_timeout`（官方默认 30 秒）等待；期间有空连接归还即刻复用；30 秒仍无 → 抛池超时错误（QueuePool 上限已到）。异常去向：Repository 把它翻译成结构化持久层异常上抛（主干二异常段），调用方按"下游不可用"降级——**池打满是显式超时失败，不是无限堆积拖垮事件循环**。这就是"短会话用完即还"纪律的代价收益账：会话攥越久连接占越久，池越容易见底。

```text

# 输入形状：业务对象 turn——thread_id="th-xiaoli-001"、seq=3、
#           question="N-2 井的完井方式是什么"、answer="…套管射孔完井…[Volve 完井报告 p.14]"
async def save_chat_turn(self, turn: Turn) -> None:
    try:
        async with self._session_factory() as session:   # ①短会话：进出即借还连接（用完即还纪律）
            session.add(turn)                            # ②数据变形：业务对象进会话，成为被管实体
            await session.commit()                       # ③提交：INSERT 落库；expire_on_commit=False
                                                         #    → 属性不失效，此刻读 turn.id/turn.answer 是内存值
        # ④退出 async with：session.close() → 连接归还池（W-F3-1 断言"连接归还池"）
    except IntegrityError as e:                          # 异常去向②约束冲突：thread_id+seq 唯一约束撞车
        raise PersistenceError("会话轮重复落账", cause=e)  #    → 结构化上抛，不吞错、不静默重试
    # 异常去向①连接失败：池超时/连不上 → DBAPI 层异常同样包装为 PersistenceError(下游不可用) 上抛，
    #   由调用方按降级路径处理——两个去向都不 return 半截数据、不写日志了事
```

```text

# 输入形状：thread_id="th-xiaoli-001"
async def get_session_history(self, thread_id: str) -> list[Turn]:
    async with self._session_factory() as session:           # 短会话：查完即还
        stmt = (
            select(Turn)                                     # 2.0 风格：select() 表达式，非 1.x Query（官方）
            .where(Turn.thread_id == thread_id)
            .order_by(Turn.seq)
            .options(selectinload(Turn.citations))           # ★ 急加载声明：加载意图前置到查询期
        )
        rows = (await session.scalars(stmt)).all()           # 一次往返取主查询
    return list(rows)
    # selectinload 机制（主干）：主查询出结果后，ORM 自动发第二条 SELECT…WHERE 关联键 IN (本轮全部主键)
    #   批量取回块元数据装进 citations——两条查询都在会话存活期内完成，之后零 SQL；
    # 出会话后实体脱离托管，但属性与 citations 都已在内存：随时可读——"无隐式 IO"的可观察行为；
    # 异常去向：连接失败同 save_chat_turn 去向①；查无记录返回空列表（历史本来可为空，不是异常）
```

### 捣乱输入 A：懒加载爆炸——`lazy="raise"` 的意义（W-F3-4）

```text
伪代码（时序推演，非代码）

前提：捣乱代码（某调用方草稿）在会话外摸关系——
      history = await repo.get_session_history("th-xiaoli-001")
      print(history[0].citations[0].report_name)      # ← 查询里没声明急加载，出会话后访问关系

世界一（同步 SQLAlchemy + 默认 lazy="select"）：
      属性访问触发补查 SELECT——能跑通，于是没人发现隐式 IO 与 N+1 查询，一堆隐藏 SQL 混进热路径
世界二（asyncio + 默认 lazy="select"）：
      补查是同步 DBAPI 调用——要么挂死事件循环（全部协程跟着停摆），要么在 greenlet 边界
      炸出难懂的栈（错误不在出事的业务行），排查靠猜
世界三（本节：lazy="raise"）：
      属性访问当场抛 InvalidRequestError，错误文本指名关系与"请用急加载"——
      异常就落在写错的那一行，捣乱代码在开发期被钉死
```

闸在哪：`app/db/models.py` 关系声明的 `lazy="raise"`——**设计闸**：它不拦数据、拦"写法"，把"忘了急加载"从运行期玄学（挂循环/难懂栈）变成确定性的显式抛错。合法加载通道只剩查询期 `selectinload`（或显式分步查询）。拦完数据去哪：异常上抛给调用方，按不可恢复错误折进事件帧错误路径（设计稿 01 帧协议）；数据本身无损——修正查询加上 `options(selectinload(...))` 即恢复。W-F3-4 验收写"被显式抛错拦下，而非挂死事件循环"正是此意：这道闸防的不是外部输入，是**自己人写出的隐式 IO**。

### 主干三：手机号加密落库全程（W-F11-1）

```text
伪代码 — app/db/encrypted_type.py:EncryptedField（m3 列类型；协议=官方 TypeDecorator 两钩子）

class EncryptedField(TypeDecorator):                  # 官方装饰器型列类型：包住真实存储类型
    impl = Text                                       # 存储形状：base64(iv‖cipher) 串 → 文本列
    cache_ok = True                                   # 官方缓存标记：列类型参与语句编译缓存时安全

    def process_bind_param(self, value, dialect):     # 写侧钩子：ORM flush 时对绑定参数逐值调用
        if value is None:
            return None
        return Crypto.encrypt_field(value)            # 委托 m11 公开接口（设计稿 03 主干一五步）：
                                                      #   明文 → base64(随机 IV‖密文)；此处只换数据不碰密钥
    def process_result_value(self, value, dialect):   # 读侧钩子：行加载时逐值调用
        if value is None:
            return None
        return Crypto.decrypt_field(value)            # 委托 m11：base64(iv‖cipher) → 明文
                                                      # 密钥错/载荷被改 → CryptoError 穿透上抛（设计稿 03 异常形状）
                                                      #   → 调用方凭异常类型定"读回失败"，不返回半截数据
```

```text
伪代码 — app/db/models.py:User.phone + app/db/repository.py:save_user/get_user（m3）

class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    username: Mapped[str]
    phone: Mapped[str] = mapped_column(EncryptedField)   # 密文列：调用方看到与写入的永远是明文
                                                         # 注意：此列不得加唯一约束——随机 IV 使同号两行
                                                         #   密文必不同，唯一约束既不生效也挡不住重复登记

async def save_user(self, user: User) -> None:           # 签名=卡面；主干同 save_chat_turn（短会话/两异常去向）
    async with self._session_factory() as session:
        session.add(user)                                # user.phone 此刻还是明文 "13912345678"
        await session.commit()                           # flush 期写钩子逐值加密 → SQL 绑定参数已是密文

async def get_user(self, user_id: int) -> User:
    async with self._session_factory() as session:
        return await session.get(User, user_id)          # 官方主键取值；行加载触发读钩子解密，
                                                         #   返回实体的 phone 已还原为明文
```

走查（W-F11-1 全程）：小李填 `13912345678` → `save_user` 提交 → 写钩子委托 `Crypto.encrypt_field`（随机 IV + CBC + base64，设计稿 03 主干一五步）→ INSERT 的绑定参数是一段 base64 串 → **库表 phone 列无明文**（用 SQL 客户端直查表验证——这是 W-F11-1"库中无明文"的观察口径）→ 之后 `get_user(user.id)` 行加载触发读钩子委托 `decrypt_field` → 实体属性还原 `13912345678`（"读回还原"）。加密发生在**列类型钩子层（flush 期）**：对 Repository 方法体、对调用方都透明——"哪个字段是密文"编码在模型定义里，不靠人记（取舍 3）。已知边界（承设计稿 03 付出项）：随机 IV → 密文列等值查询/等值 JOIN/唯一约束全部不可用，`get_user` 只按主键取。

## 关键判断的取舍记录

1. **asyncio 下禁隐式 IO：`lazy="raise"` + 急加载前置，不用 `awaitable_attrs` 兜底**——备选是保留默认 lazy="select"、需要时 `await obj.awaitable_attrs`（官方给的另一条出口）。不选它：隐式 IO 的触发点散在调用方任意一行属性访问，awaitable_attrs 要求每一处都记得改写成 await——漏一处就是挂循环或难懂栈；`lazy="raise"` 把违例钉死在出错行，急加载意图集中在查询期可 review。付出：查询写法更啰嗦（关系都要 options 声明）。换边条件：大集合只写不读的形态（如历史全量追加），换 2.0 官方 write-only 关系（sqlalchemy-async.md 列的第三条出口）。
2. **连接串外置（环境变量注入），不做配置中心**——方言切换是**部署期决策**：引擎创建那刻方言已定，不存在运行期热切，配置中心的动态下发在这里没有用武之地；连接串含密码，走环境注入（承设计稿 03 compose 契约）比多一个中心化依赖面更小。备选的换边条件：出现多租户多库动态路由需求时按模块卡修订流程扩卡，不在 m3 私加。
3. **加密做成列类型（TypeDecorator），不做仓储方法内手动加解密**——备选是在 save_user/get_user 里各写一行 encrypt/decrypt。不选：靠人记的加解密，新增敏感字段就漏一处，且从模型定义看不出"这列是密文"；列类型把加密编码进 schema，查询/插入对调用方全透明。付出：调试直查库全见密文、密文列等值能力全失（设计稿 03 已记的已知边界）。换边条件：出现"按加密字段检索"需求 → 按模块卡修订流程扩卡盲索引/确定性加密，不在列类型里私加。
4. **双跑验证从本节起，不推迟到迁库交付前**——接缝的成立靠"同一套用例两库持续全过"锁死；本节是接缝唯一入口诞生的设计稿，双跑用例与接缝同步落地成本最低；推迟到交付期，方言差异暴露时前面已积累十几篇设计稿的查询，回改面不可控。现实约束：金仓实例（PG 兼容模式 initdb）、官方方言包、对应架构驱动需在本节环境就位——**若环境缺位，属设计范围红线的"环境/前提冲突"，停下裁决，不用 PG 单跑蒙混过关**。

**docs/tech-stack/sqlalchemy-async.md · 2.0 语法风格与流式读取**（卡 `m3` 锚点）

**docs/tech-stack/guochan-db-os.md · ksycopg2 官方路径与装载方式**（卡 `m3` 锚点）
guochan-db-os.md：金仓官方 Python 驱动 ksycopg2 是 Python DB API 2.0 完整实现、具备异步通信能力（libpq 的 C 包装）；装载方式是驱动目录入 `sys.path` + `LD_LIBRARY_PATH` 指向 libpq 目录；提供 amd64/aarch64 双架构包（麒麟鲲鹏/飞腾场景取 aarch64）。asyncpg 对金仓**未找到官方支持声明**——金仓路径不能照抄 `postgresql+asyncpg`。落点：主干四切换两步（装包+换串）的依据。

**docs/tech-stack/guochan-db-os.md · 兼容模式 initdb 期固化**（卡 `m3` 锚点）
guochan-db-os.md：金仓可插拔架构，`initdb` 时按 `-m/--mode` 选定 PG/Oracle/MySQL/SQL Server 兼容模式，**初始化时固化、不能运行时切换**；兼容模式改变 SQL 语义（Oracle 模式下 `ora_input_emptystr_isnull` 等参数行为与 PG 不同）；官方案例 PG 迁金仓近百个 Python 服务零代码修改、只改连接串 host/port；默认端口 54321。落点：主干四设计要点与捣乱输入 B 全部站在这条上——"接缝一处"的成立前提是库初始化就选对模式。

**docs/tech-stack/guochan-db-os.md · SQLAlchemy 官方方言包与达梦对照**（卡 `m3` 锚点）
guochan-db-os.md：金仓与 PG 并非 100% 等同，SQLAlchemy 需用金仓官方方言或自行处理版本号探测问题。另按 W-F11-3 断言要求记一句达梦对照：dmPython 占位符 `?`、无 psycopg2 平移路径（F11 设计范围"不做什么"——达梦只讲不实现，金仓才是双跑对象）。落点：主干四把"装官方方言包"定为切换两步之一，版本探测误判记为禁止项（捣乱 B 末段）。
