### 主干一：TransformTest.suite——检查清单由契约生成，不是手写死

```text
伪代码 — app/modeling/tests_policy.py:TransformTest（m20；签名=卡 m20；纯内存套件，同步）

class CheckReport:               # 数据形状——一次检查的固定报告形状（设计范围"失败报告形状"的落点）
    检查: str                    # 五类之一："唯一性|非空|引用完整|值域|水位新鲜度"
    规则: str                    # 判据出处（"§4 规则 1"）——引用不发明（取舍 4）
    层: str                      # 哪层 fail——定位第一要素（W-F18-1 的"定位到层"）
    表: str                      # 哪张模型物
    键或列: str                  # 检查对象（grain 键 / 列名 / 外键对）
    判据: str                    # 机器可查判据（"count(*) = count(distinct …)"）
    实际: str                    # 观察值（"计数差=1"）
    定位样本: [str]              # 违规行样本（"N-02|2026-09-14 A/B 两行"，§A.2）
    级别: str                    # 严重=数据错 / 警告=窗内标注 / 提示=治理欠账（unknown）
                                 #   ——三级对齐提取件二 §三（陈绍凯：规则支持分级）
    建议: str                    # 查什么、找谁修——出口指问题单闭环，不自动修（取舍 5）

class TransformTest:
    def suite(self, layer) -> [check]:
        # ── 主干判断：检查清单由契约与协议生成——契约改了测试跟着改，两处永不漂移（取舍 1）──
        契约 = LayerPlan.describe(layer)             # 设计稿 32 公开面：防什么错清单=检查骨架
        checks = []
        for 表 in 契约.模型物清单:
            粒度 = GrainProtocol.已声明粒度(表)      # 设计稿 33 台账只读取用（同一台账同源——
                                                    # 读取口径备案见越界自查；未声明在此先报"提示"）
            checks.append(唯一性检查(表, 粒度.键))   # count(*)=count(distinct 键)——§4 规则 1
            checks.append(非空检查(表, 关键列(表)))  # 非空率≥99.5%——§4 规则 2
            checks.append(值域检查(表, 规则库值域))  # §4 规则 3/5：water_cut、open_days、折算密度
        if layer in ("intermediate", "marts"):
            checks.append(引用完整检查(layer))       # 外键自 intermediate 立约起可查——
                                                    # staging 无立约不查（设计稿 32 fk_ok 自证的测试化）
        if layer == "marts":
            checks.append(水位新鲜度检查())          # 🛡️ 仅 marts 层——收编 v2 freshness 语义（主干三）
        # 开放列：监控型与跨源型检查同报告形状挂载（判据仍引用规则库，设计演绎留位——判据表末两行）
        return checks
```

> **为什么逐层各有一份套件而不是全库一把跑**：卡 `m20` 签名是 `suite(layer)`——层是定位的第一要素。同一个唯一性判据，staging 层 fail 是"准入闸失灵"（管道来源），marts 层 fail 是"下潜污染"（上游层闸失灵+下游没拦），责任层与修法不同。测试逐层跑（staging→intermediate→marts 顺序），坏数第一次现身的层就是它该被修的层——**质量问题在进入下层前被拦**（W-F18-1 断言的"早拦便宜"在测试半边的含义，Kimball Ch6 §Clean 同源）。

### 主干四：三来源诊断法——同一坏数，三种根因，三种处置（W-F18-3）

## 关键判断的取舍记录

1. **测试判据与 SQL 闸同源，不是两套标准**。备选：测试单独维护一套判据（"更灵活"）。两套标准是漂移温床——闸改了测试没改，绿灯是假的；判据唯一出处=契约"防什么错"清单+GrainSpec 粒度键+§4 规则库阈值（第 0 步三出处），suite 由契约生成检查清单（主干一"契约改了测试跟着改"）。代价：契约表达力封顶了测试表达力（契约没写的错测试不查）——当前规模接受，开放列留位（判据表开放两例）。换边条件：无（这是本节灵魂）。
2. **水位语义收编只动指向，FreshnessStage 段代码零改动**。备选：为 marts 批次水位给 FreshnessStage 加新分支/新状态。设计稿 24 的 W-F14 走查把五段顺序、三态、容忍窗、unknown 语义锁死为行为契约——加分支=回退已锁语义。升级的真实语义是**承诺对象变了**（消费面只认 marts→承诺对象=marts 模型物批次），实现上只是登记键口径与水位源指向（主干三"变"清单两行）；测试侧把 v2 三态语义原样收编进 CheckReport 分级（严重/警告/提示对齐 stale 超窗/窗内/unknown）。换边条件：出现"水位承诺 SLA+破窗告警"需求（设计稿 24 取舍 2 已预留的换边）——那时登记行升格为带 owner 的水位合同，归设计稿 23 评估链回归半边。
3. **unknown 在测试半边同样"跳过并标注"，不判 fail**。备选：无登记=测试红（逼登记覆盖）。unknown 不是数据错，是治理欠账——判 fail 会把"登记没铺完"伪装成"数据出事故"，测试永远红=测试失聪（没人再看红灯）。收编 v2 语义（跳过并标注）+ 提取件二 分级（陈绍凯：严重/警告/提示——unknown 走"提示"级）+ 建议栏出口入问题单闭环——透明替代静默，与设计稿 24 取舍 2 同哲学、两个执行位同一答案。换边条件：登记覆盖完成后（推演设定不变），unknown 提示自然消失。
4. **阈值一律引用规则库，测试不发明判据**。备选：套件内硬编码 99.5%/24 小时/T-1。阈值是**治理定义**（§4 规则库=治理产物，Owner 维护）——硬编码进测试代码=把治理决策 cement 进管道，改阈值要改代码，恰是主干四第三支要拦的"定义漂移"的测试版。引用式判据（CheckReport.规则 字段指回 §4-×）让"改阈值"走治理流程（规则库变更），测试自动跟随。与主干四呼应：值域检查 fail 定位到"折算密度越带"是管道支，若有人想靠放宽阈值消红——那是治理支的裁决，不是管道支的修法。
5. **失败报告带"建议"但不自动修**。备选：测试发现问题自动触发修复（自动重跑/自动改数）。与设计稿 32"宁可不修，不可错修"（三档裁决第三档）同哲学：自动修的前提是判据 100% 可靠，而捣乱 A 证明闸本身会失灵——用会失灵的闸的测试去自动修，是拿防线的防线当防线。建议栏出口=问题单闭环（人裁决），管道支的重跑是幂等重放（重跑确定，不是自动改数）。换边条件：无。
6. **三来源诊断是人的决策树，不是自动根因分析**。备选：把诊断树写成自动路由（fail→修管道/全绿→自动报治理问题）。F18"不做可观测平台"；且第二/三支的分界（源系统凭证核对、口径裁决）本质是**人的核对动作**（对台账、问 Owner）——Kimball Ch9 原书也把 unknown unknowns 的检出交给"anomaly detection tools and human scrutiny"（工具+人），本设计收敛为：确定性测试拦第一类，决策树给人走查第二三类。自动化的部分（测试、同源水位）已尽，人的部分如实留人。

## 锚点对照精要

**Kimball Ch9 开篇（三来源定义——本节决策树的树干）**：原文——"We define three main areas where data quality issues can arise when you use data for analysis, decision-making, or machine learning: In the source system… / When you move data from a source system to a target system… / In the governance of data quality…"。落点：主干四三支划分（管道支=第二来源，源系统支=第一来源，治理支=第三来源）。差异：原书是问题空间分类（问题在哪发生），本设计稿是诊断程序（拿一个坏数怎么定位到其中一支）——分类升格为决策树，测试结果做路标。

**Kimball Ch9 §Data quality issues in source systems（源系统支与五类中三类的影子）**：原文——"you can test your assumptions about the source system. Simple tests on uniqueness, NULL values, or data freshness may suffice. Secondly, as the famous saying goes, 'Follow the money.' If there is an incentive for your source to over or under-report…, this will likely happen."。落点：唯一性/非空/水位三类检查的原文影子（五类里三类原书点名）+ 主干四源系统支的动机判据（完成率挂钩考核的表，虚高先查动机）。差异：原书把这些测试当"对源系统的假设检验"，我们把同一判据分层化——staging 层测管道兑现、对照源侧测采集假设，同判据两个执行位正是三来源定位的路标。

**Kimball Ch9 §Data quality issues in data infrastructure and data pipelines（管道支与测试的边界）**：原文——五型问题 Timeliness/Integrity/Completeness/Precision/Cleaning；"you can write tests and checks, even though you are uncertain about their future state; for example, whether a column has NULL values, unique values only, or if it is of type float or Boolean. These are what we call 'known unknowns.'"；Cleaning——"with every adjustment or addition you make, you also introduce the potential for errors"；转换宜幂等（idempotent）。落点：管道支处置（修管道重跑——幂等重放，设计稿 32 定序去重取舍 2 的另一收益）+ known unknowns 与 unknown 提示级的分界（NULL/唯一性这类可写测试的=五类主干；整数据集缺失类=unknown unknowns，Kimball 原文也交给异常检测+人审——本节收敛为问题单人审，取舍 6）。差异：原书五型没有独立的"引用完整/值域"条——这两类判据来自提取件二 26 项通用规则（关联非空/固定值域）与六维质量口径，AE 原书与油田治理规则库拼起来才凑齐五类（见下条）。
