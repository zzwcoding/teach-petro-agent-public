### 第 1 步：三条缓存铁律逐一走查（卡 m13/W-F12-1；机制事实锚 原书第二章 §KV Cache友好的上下文设计）

| 铁律 | 装配器里的落点 | 违反的后果 |
|---|---|---|
| 一 系统提示词与工具定义冻结——顺序也不能变 | system 恒第 1 条逐字节不变；tools 零排序透传（第 3 步） | 前缀从首个不同 token 起全部重算+全价计费 |
| 二 动态信息只追加末尾 | history 原序透传、dynamic 垫底 | 同样前缀失稳，且缓存变体数爆炸（取舍 2） |
| 三 标准 API 格式，不自行拼接 | 输出保持 {role, content} 结构；tool 消息带 tool_call_id | Chat Template 偏离训练格式——坏的是模型能力，缓存反而不是主要受害者 |

**铁律一的机制事实**：模型逐 token 计算 K/V，服务端 Prompt Cache 把跨请求的相同前缀直接复用已算结果；前缀匹配是**逐字节**的——"意思没变"不算数，差一个空格就是不同 token 序列，从首个不同 token 起全部重算。改动越靠前代价越大：Transformer 逐层串联，第 k 个 token 变，k 之前的缓存不受影响，k 起（含系统提示词余部、全部工具定义、整段历史）逐层重算——所以冻结纪律对"最前面"的内容最严，这正是系统提示词与工具定义被钉死在头部的原因。

**铁律二的机制事实**：追加不改动任何已有 token 的位置——前缀字节稳定，已积累的 K/V 全部可复用。"每轮都变的值"（时间、余额、计数）若进了前缀，每轮请求都产生一个新前缀变体，命中率恒零。动态元信息的正确去处是末尾：书里 Agent 状态栏的先例——状态摘要以 user 角色消息挂在上下文末尾、绝不改写开头的 system，"因为修改 system 会破坏整个前缀的缓存"。

**铁律三的机制事实**：结构化消息经 Chat Template 翻译成模型训练时见过的固定 token 序列；自行拼成 `"USER: … ASSISTANT: …"` 纯文本流的账要分开算——缓存不是主要受害者（拼接字节稳定照样命中），主要受害者是模型能力：角色边界靠猜、工具结果被误认成新提问、多步思考的草稿被误清。所以铁律三防的是能力不是缓存，与铁律一/二不互替。

**纪律的分工**（谁守什么）：装配器守**结构与顺序**——四段各就各位、tools 不重排、输出形状标准；**内容冻结是输入方的契约**——系统提示词当常量、工具描述不带动态值，调用方塞进来的抖动装配器拦不住（纯透传件，不做"静默修复"）。设计稿 14 生成节点的"few-shot 冻结前缀"就是输入方契约的同构实例。

### 第 2 步（主干一）：layout_messages 装配主干——四段进、一列出

```text
伪代码 — app/agents/prompt_layout.py:layout_messages（公开接口，00 号骨架登记 m13 签名；装配主干）

def layout_messages(system, history, tools, dynamic) -> messages:
    # 装配契约：四段输入 → 标准 API 消息列。tools 不是消息角色——随请求顶层 tools 字段由
    #   调用方发送；本函数对它只做"透传不改"（零排序零去重零改名，第 3 步的闸），故不出现在输出列。
    frozen_head = [{"role": "system", "content": system}]   # 铁律一：系统提示词永远第 1 条，逐字节不变
    grown_tail  = [*history, *dynamic]                      # 铁律二：历史原序透传，本轮新增垫在最末
    # 铁律三：全程不做字符串拼接——不产出 "USER: … ASSISTANT: …" 文本流；每条消息保持
    #   {"role", "content"} 结构，tool 结果带 tool_call_id、assistant 的 tool_calls 原样保留。
    # 走查不变式（走查断言，非运行时断言）：grown_tail 除末尾新增外，与上一轮请求逐字节相同
    #   → 服务端前缀匹配可复用到新增点为止——"缓存稳定命中"在装配层就是这个不变式
    return [*frozen_head, *grown_tail]

#   Gateway.chat(layout_messages(system, history, tools, dynamic),
#                model_alias="petro-llm", stream=True, tools=tools)
```

def _layout_naive(system, history, dynamic) -> messages:
    stamped = f"{system}\n当前时间：{now():%Y-%m-%d %H:%M:%S}"   # 捣乱点：动态内容进了前缀第二行

    #   信息一个字没少，位置差一段，代价差一个量级（取舍 1）

### 第 4 步（主干三）：长会话批量压缩——token 阈值判据（本节实现只落此处）+ 策略主干

```text
伪代码 — app/agents/prompt_layout.py:_needs_compression（阈值判据——设计范围明文"实现只留阈值判据"的落点）

def _needs_compression(history, window_tokens, ratio=0.8) -> bool:
    used = _estimate_tokens(history)          # 整列 token 估算（保守上界，不引入 tokenizer 依赖）
    return used > window_tokens * ratio       # 主干判断：用量越过窗口八成才触发——留 2 成余量给
                                              #   本轮新增与回答（口径取自书里实验策略六）
# 信号与风险同构（取舍 3）：要防的是"上下文体积"，触发信号就用体积，不用轮数。
# 调用点（消费方纪律，设计稿 17 起生效）：主循环每次装配前先问判据——True 才进压缩分支

def _estimate_tokens(messages) -> int:
    return sum(len(m.get("content") or "") for m in messages) // 2
    # 保守估算：字符数折半当 token 上界——中英混排粗估够用；阈值判据差 10% 不改变行为
    #   语义（0.8 与 0.75 触发时机几乎无差），不值得为此引入 tokenizer 依赖
```

```text
伪代码 — app/agents/prompt_layout.py:_compress_tool_results（策略主干——设计范围"实现只留阈值判据"，
         本段承载策略供后续消费，不在本节装配器内落地）

def _compress_tool_results(history, compressor) -> history:
    # 纪律一（时机）：只在两次模型调用之间做——绝不在单次调用中途改，中途改等于当场作废自己的前缀
    # 纪律二（对象）：只压 history 里的 role:"tool" 消息——system 与工具定义是冻结段，永不参与；
    #   压缩后的消息仍保留原 role 与 tool_call_id、只换 content——消息结构保持标准形状（铁律三不因压缩而破）
    targets = [m for m in history if m["role"] == "tool" and not m.get("compressed")]
    digests = compressor.summarize_batch(targets)   # 批量摘要：一次模型调用压完全部未标记的
                                                    #   （摘要调用经 m2 网关——消费方接线，非本节）
    # 纪律三（批量摊薄）：替换点之后的缓存反正要重建一次——一次性压完，把重建代价从
    #   "每轮一次"摊成"每个阈值周期一次"（书里结论：频繁压缩频繁破坏缓存，接近阈值再批量压）
    # 纪律四（替换冻结）：摘要字符串首次生成即冻结存档——会话重启恢复时逐字节还原，
    #   防恢复后的消息列与缓存中的字节流不一致（书里"替换字符串首次出现时就被冻结"的先例）
    return [_replace_or_keep(m, digests) for m in history]
    # 压过的消息替换为带 "[COMPRESSED]" 标记的冻结摘要——标记防同一结果被重复压缩（防重复保护）
```

压缩与铁律一/二的矛盾调和（机制事实，锚 原书第二章 §上下文压缩策略）：压缩确实改了历史中间——替换点之后的缓存会失效一次；但它发生在两次调用之间、只动 tool 结果、批量一次做完，是一次**有意识的权衡**：不压，上下文膨胀超窗任务直接失败；压，付一次局部缓存重建换长度可控、密度更高。滑动窗口那种"每轮滚掉最旧消息"是反模式——每轮都在改中间，前缀永不稳定，还会把后续要引用的关键工具结果滚丢；批量压缩+标记是它的替代解。

**走查收束**（两类调用方输入形状都过同一主干）：小李三轮会话（第 2 步推演）是 history 逐轮增长的形状；老王反思回边第二轮是"前缀与第一轮逐字相同、尾部多一条错误回灌"的形状——回灌消息是追加不是改写，冻结头原样命中，第二轮只付新增 token 的钱（这就是设计稿 14 few-shot 冻结纪律在会话级的机制收益）。装配器对两种形状无感知——它只认四段，不认业务。

## 关键判断的取舍记录

1. **冻结是字节级契约，不是语义级承诺——"改越靠前代价越大"由逐层机制决定**。系统提示词第二行加时间戳与在末行加，语义影响都是零，缓存代价差一个量级：第 k 个 token 变，重算范围=k 起的全部；系统提示词占着消息列第 1 位，它内部越靠前的位置失稳，全局重算面越大。备选"语义没变就没事"不成立——服务端前缀匹配是字节比对，不做语义对账；所以版本号可以进系统提示词（会话内不变，发版才变一次），时间戳不行（每秒变）。换边条件：无——这是推理服务的物理机制，不是实现选型；能选的只有动态信息放哪（铁律二的答案是末尾）。
2. **命中价约 1/10 的账：缓存经济性是架构约束，不是事后优化**。锚 原书第二章：Prompt Cache 命中部分的读价约为首次计算价的十分之一（Anthropic/DeepSeek/GPT-5 量级，各家启用与计费细节不同）。账面（第 2 步对照表）：六轮会话累计 10 200 vs 35 400 等效 token，时间戳装配贵约 3.5 倍且随轮数放大；TTFT 同向放大（prefill 体量 600 vs 7 400）。这解释了为什么"动态元素一律末尾"被做进装配器结构而不是留给调用方自觉：N 个二值动态条件进前缀=2^N 个缓存键变体（书里 Claude Code 先例：提示词的物理排列首先由缓存经济性决定，其次才是语义逻辑）——等慢了再改布局，每一处调用方都得动。换边条件：服务商缓存计费政策大改（命中价升到接近全价）时，铁律一/二的经济动机消失，但铁律三的能力动机仍在——纪律不撤，只是不再是钱的事。
3. **压缩触发信号选 token 阈值，不选轮数阈值——信号要与它防的风险同构**。要防的是"上下文体积超窗/信息密度劣化"，不是"对话到了第几轮"：一轮的体积方差极大（query_production_db 返回几十行数据 vs navigate_page 只回一条路由指令），按"每 10 轮压一次"触发，10 轮可能是 8K 也可能是 120K token——前者白付一次缓存重建，后者早已溢出失败。token 阈值（窗口的 80%，锚书里实验策略六口径）与风险同构，配合批量压缩把重建代价摊成每个阈值周期一次。换边条件：token 数完全不可估的环境才退化为字符数估算（本设计稿 _estimate_tokens 即保守折半，不引入 tokenizer 依赖）——判据口径差 10% 不改变行为语义，精度不值得花钱。
4. **装配器零排序权：顺序的唯一来源是注册表导出序**。捣乱输入 B 推演了动态排序是纯亏买卖；但"顺序稳定"靠什么保证？本节把它落在结构上——layout_messages 对 tools 只透传，顺序=Registry.tools_for 导出序=boot_register 注册序（进程内一次定序）。备选是在装配器里做"稳定排序"（按 name 字典序），看似更稳，实则把排序政策偷进了机制件：哪天注册表要按权限组排序就得来改装配器。排序政策归 m8 注册表一侧（m8 契约：导出即定序）；若未来真出现"必须按上下文相关性排工具"的需求，那是改模块卡的事，且得先跟取舍 2 的账对质。

## 锚点对照精要

**原书第二章 §Agent如何调用大模型 · 消息的四种角色**（卡 `m13` 锚点）
书：Chat Completions API 的核心是消息列表，四种角色——system（系统提示词，通常一条、放最前）、user（用户输入）、assistant（模型过往回复，含工具调用请求）、tool（工具结果，经 tool_call_id 与调用请求关联）；工具定义不是消息角色，是请求顶层的 tools 字段。"四种角色+tools 字段"恰覆盖上下文五个组成部分；"从 API 视角看上下文的构成"一节给出"静态前缀+轨迹"的结构——前面不能动、后面可以长。落点：layout_messages 的输出严格保持该结构，tools 由调用方随请求顶层字段发送；装配器的输出形状就是"静态前缀+轨迹"在 API 层的样子。

**原书第二章 §KV Cache友好的上下文设计**（卡 `m13` 锚点；W-F12-1/2 源）
书：KV Cache 缓存已算 token 的 K/V，Prompt Cache 把跨请求相同前缀的计算结果复用（命中读价约为首次计算的十分之一）；三条核心结论——系统提示词与工具定义一旦确定就不要改（哪怕一个空格；改动越靠前，延迟和成本影响通常越大）、动态内容放上下文末尾、使用标准 API 格式不自行拼接。四个有害模式：动态用户配置进前缀、工具定义按使用频率动态排序（每个工具数百 token，改序从首个变动的工具起全废；固定顺序对选工具能力几乎无影响）、滑动窗口破坏前缀一致性并丢关键工具结果、文本格式化破坏训练格式。"缓存作为架构约束"一节：提示词物理排列由缓存边界决定，N 个二值动态条件=2^N 个缓存键；大工具输出的替换字符串首次生成即冻结。落点：三铁律即三条核心结论的装配器化；四反模式各有一条结构性闸与之对应（第 1/3/4 步）；替换冻结写进压缩纪律四。

**原书第二章 §上下文压缩策略**（设计范围压缩策略源）
书：压缩与 KV Cache 看似矛盾实则互补——压缩发生在两次 API 调用之间（不在单次调用中途），system 与工具定义永不动，对象是历史中的 tool results；替换点之后缓存失效但之前仍有效，是有意识的权衡（不压则超窗任务直接失败）；频繁压缩频繁破坏缓存，最好接近阈值时批量压缩。实验策略六（自适应窗口化）三机制：prompt token 超窗口 80% 才触发、触发时一次性压缩全部未标记工具结果、[COMPRESSED] 标记防重复处理。生产分层压缩五层（工具结果预算控制/噪声直删/API 层微压缩/归档式摘要/全量压缩+熔断）。落点：判据取 0.8 口径、批量与防重复标记进纪律三/四；分层压缩的其余各层与压缩执行器不在本节（设计范围明文"实现只留阈值判据"）。

**docs/tech-stack/litellm.md · Router Session 亲和**（锚 docs/tech-stack/litellm.md，网关侧与 prompt cache 相关）
文：LiteLLM Router 可配 `optional_pre_call_checks: ["session_affinity"]`，按 `x-litellm-session-id` 头把同一会话钉在同一部署上——官方标注的适用场景即"多轮对话 / provider 侧 prompt cache"。落点差异：前缀缓存命中是两端合力——装配器（本节）保证请求前缀内容字节稳定；会话亲和（网关配置域，设计稿 07 config 契约面）保证同类前缀落在同一部署。本节不改网关配置，只记此锚供对账。
