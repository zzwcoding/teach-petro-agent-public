### 主干 A：dispatch 分派表——三分支路由与受理帧异步语义（卡 `m13` 公开接口第一行）

```text
伪代码 — app/agents/runtime.py:dispatch（m13 真身化；无 IO 纯路由，非 async；设计稿 01 第 3 步的 qa 分支换真）

def dispatch(agent_type, message, user) -> EventStream:
    thread_id = 解析会话线(message)               # 请求体透传位（设计稿 01 ChatPrompt.thread_id；
                                                  #   供给位与设计稿 18 会话上下文一并定形）
    match agent_type:                             # 分派表即路由真源：卡 m13"qa→run_qa_loop；
                                                  #   text2sql→run_text2sql；wenzhi→enqueue_wenzhi"
        case "qa":
            return run_qa_loop(message, user, thread_id)      # ★ 本节换真身（主干 B）
        case "text2sql":
            return echo_agent_stream(message, user)           # 替身保留：假节点轨迹帧
                                                              #   （设计稿 19 换 run_text2sql 桥接）
        case "wenzhi":
            return echo_agent_stream(message, user, 受理形状)  # 替身受理帧保留：agent 帧+done 帧、
                                                              #   零 token 流（设计稿 19 换 enqueue_wenzhi）

            raise 链路未知异常                    # 异常去向：端点兜底 internal_error 帧（设计稿 01 第 5 步）
```

三点路由纪律：

- **接缝不变**：chat_endpoint（设计稿 01）零改动——它只认 `dispatch(agent_type, ...) -> EventStream` 一个出口（卡 `m1` Seam 行），帧仍由端点逐帧 yield。换真身换的是 dispatch 返回的生成器本体，不是通道。
- **wenzhi 的异步语义**（设计范围路由注记"转队列即回受理帧"）：真身形状是 `m4.TaskQueue.enqueue` 后**立即**返回受理帧——运行时不等 worker，产物经事件缓冲异步回流（卡 `m13` enqueue_wenzhi 行）。本节不写 enqueue 调用（设计稿 19 交付，且边界规则第 4 行禁止 m13 import m15），只锁受理帧形状：替身按"agent 帧 + done 帧、零 token 流"出帧，设计稿 19 换真时帧形不变、只换来源。
- **W-F7-1 第一跳成立**：dispatch("text2sql") 分支此刻仍回假帧，但路由判断本身是真的——老王"那口井怎么样了"这类提问在 dispatch 就被分进问数分支（设计稿 19 起 goto 六节点图）；本节交付的是"第一跳的路由位"，不是问数链本身。

```text
伪代码 — app/agents/runtime.py:run_qa_loop（m13 真身；签名=00 号骨架登记 m13 第二行；主干判断/数据变形/异常去向三层不省）

# 模块级私有常量：
#   _QA_SYSTEM       系统提示词（冻结常量，设计稿 16 铁律一）：油田问答助手角色 + 带引用三纪律
#                    （据/引/界，设计稿 10 Generator._SYSTEM_TEMPLATE 同文）+ 工具使用边界一句
#   _MAX_LOOP_TURNS=8  单问工具循环轮次上限（取舍 2）

async def run_qa_loop(message, user, thread_id) -> 事件帧序列:
    # ── 第 0 段 会话状态：历史供给位（设计稿 18 cache-aside 接线；本节按"历史已就位"形状走查）──
    history = await 会话历史供给(thread_id)          # 占位：Cache.get → miss 回源 m3（设计稿 18 兑现）
    轮次 = 0; seq = 0; call_id = None
    try:
        # ── 第 1 段 检索前奏（m6 前两站直调，设计稿 10 主干一/三契约）──
        candidates = await Retriever.search(message, top_k=10)   # m6：双路召回→RRF 融合→账本充实
        ranked = Ranker.rerank(message, candidates, top_n=5)     # m6：跨编码器精排，降序 top-n
        # 异常去向：m6 结构化异常原样上抛（设计稿 10 不吞错不降级）→ 本函数 except 折 retrieval_error 帧
        tools = Registry.tools_for(user)             # m8：按角色过滤→官方 tools 数组（设计稿 12 主干二）
        # ── 第 2 段 装配（设计稿 16 契约）：冻结头 + 历史 + 动态尾巴——进循环前一次 ──
        #   数据变形：候选块→"[报告名 p.页码] 原文"块标头尾巴（设计稿 10 引用可定位的锚在装配层钉死）；
        #   候选空/全低分不硬塞也不拦——尾巴如实注明"本次检索无命中"（取舍 3：据的判定后移给模型软闸
        #   + 工具反馈，防检索低分误杀工具问题；设计稿 10 的零调用硬闸随 Generator 留在纯管道路径）
        检索尾巴 = 块标头列表(ranked) if ranked.候选 else ["本次检索无命中——报告库无据请明说，或改用工具"]
        messages = layout_messages(_QA_SYSTEM, history, tools,
                                   dynamic=[{"role": "user", "content": message}, *检索尾巴])
        # 设计稿 16 消费纪律：_needs_compression(history, window) 判据在此问一次——True 才进压缩分支
        #   （压缩执行器是设计稿 16 策略主干，本节只接线判据，不落地压缩）
        # ── 第 3 段 主循环：while 有工具调用且未终态 ──
        while True:
            轮次 += 1
            # 主干判断⓪ 终态兜底判据（取舍 2）：轮次上限 / 预算判据（设计稿 06 Metrics.over_budget 只读）
            if 轮次 > _MAX_LOOP_TURNS or Metrics.over_budget(单问预算):
                yield await 帧出口("token", 转人工话术(已试工具))     # 转人工是正常终态（设计稿 14 同型）
                yield await 帧出口("done", {"finish_reason": "loop_limit"})
                return
            # ── 模型调用：唯一出口 m2（边界规则第 1 行）；流式与 tools 同一调用（取舍 3）──
            stream = await Gateway.chat(messages, model_alias="petro-llm",
                                        stream=True, tools=tools)     # 工具清单每轮照带（设计稿 12 契约）
            # ── 数据变形：流式聚合——delta.content→token 帧即出；delta.tool_calls 按 index 归并，
            #    arguments 字符串片段逐段拼接（官方流式形状）；末块才带 finish_reason ──
            正文 = ""; 调用聚合 = []; finish_reason = None
            async for chunk in stream.token_stream:
                if call_id is None:                  # 首个 chunk：流建立即有响应头（设计稿 07 契约）
                    call_id = stream.call_id         # x-litellm-call-id——对账锚（设计稿 01 agent 帧 data）
                    yield await 帧出口("agent", {"call_id": call_id, "agent_type": "qa",
                                                 "thread_id": thread_id})   # 帧首：帧序不变（设计稿 01）
                if chunk.delta.content:
                    正文 += chunk.delta.content; seq += 1
                    yield await 帧出口("token", {"delta": chunk.delta.content, "seq": seq})
                if chunk.delta.tool_calls:
                    按 index 归并(调用聚合, chunk.delta.tool_calls)   # 官方：元素带 index，逐段拼接
                finish_reason = chunk.finish_reason or finish_reason
                await anyio.sleep(0)                 # 每轮必 await——取消语义兜底（设计稿 01 捣乱 B 铁律）
            # ── 主干判断① 模型回工具调用了吗（finish_reason=="tool_calls"）──
            if finish_reason == "tool_calls":
                messages.append(stream.assistant 消息原样)    # ★ 官方红线：含 tool_calls 的 assistant
                                                              #    消息原样入历史（content 可为空）
                for tc in 调用聚合:                            # 官方：0/1/N 按 N 处理（本分支 N≥1）
                    yield await 帧出口("tool_call", {"tool_call_id": tc.id,      # 设计稿 01 占形帧在此落地
                                                     "tool_name": tc.function.name,
                                                     "arguments": tc.function.arguments})
                    result = None
                    async for 项 in 带进度执行(tc, user):      # 主干 C：五步 + tool_progress 帧接线
                        if 项是帧: yield 项                    # tool_progress 帧边执行边出
                        else: result = 项                      # ToolResult（执行完成）
                    # ★ 官方红线：role:"tool" 回灌，tool_call_id 只取 result.call_id（钉死自 tc.id，
                    #   并行下不错配）；成功结果与结构化错误同一形状（设计稿 12 ToolResult 契约）
                    messages.append({"role": "tool", "tool_call_id": result.call_id,
                                     "name": result.name, "content": result.content})
                continue                    # 续循环：带着工具结果发二次请求（官方五步之第 4→2 步回环）
            # ── 主干判断② 终态：无工具调用 → 收尾 ──
            citations = 引用校验(正文, ranked)   # 设计稿 10 契约：[报告名 p.页码] 逐条对回候选集，
                                                 #   对不回的记"不可定位引用"账，不静默丢弃
            yield await 帧出口("done", {"finish_reason": "stop"})
            return                               # 终态判据达成：正常收尾关流（done 后永不再有帧）
    except GatewayError:                         # 设计稿 07：router 重试与 fallback 跑完仍败
        yield await 帧出口("error", {"code": "gateway_error",                     # 模型流中断→error 帧
                                     "message": "生成服务暂不可用，请重试",
                                     "recoverable": True})                        # 沿设计稿 01 协议关流
        return                                 # W-F1-3 语义：客户端收到 error 帧且流被取消，无悬挂协程
    except 检索异常:                             # m6 结构化上抛（设计稿 08/10：不造分不冒充命中）
        yield await 帧出口("error", {"code": "retrieval_error",
                                     "message": "检索服务暂不可用，请重试", "recoverable": True})
        return
```

循环结构三句话收束：**装配一次、轨迹只追加**——messages 在进循环前经 layout_messages 装配，循环内只做 append（assistant 原样、tool 回灌），字节层面与"每轮重装配+原样透传"产出完全相同（设计稿 16 走查不变式的循环内形态）；**判据两问**——每轮先问"没工具调用了吗"（终态）、再问"轮次/预算超了吗"（兜底）；**回灌即续**——tool 消息 append 后 continue，二次请求与首轮走完全相同的 Gateway.chat 形状。

## 锚点对照精要

**原书第一章 §ReAct循环（轨迹只增不改）**（卡 `m13` 锚点 K-A/K-E/K-H 组；任务指定回查点）
书：ReAct=思考→行动→观察三环节循环，想→做→看不断重复直到任务完成；Agent 的上下文=静态前缀（系统提示词+工具定义）+轨迹（用户消息/模型回复/工具结果，随交互增长），轨迹结构化让系统易于解释和调试，且轨迹只增不改。落点：主干 B 的 while 体就是"想（模型流）→做（Executor 五步）→看（tool 消息回灌）"的循环机械面；循环内对 messages 只 append（assistant 原样入史、tool 紧随其后），不改中间——与设计稿 16"grown_tail 除末尾新增外逐字节相同"的装配不变式是同一条纪律在循环层的形态。

**原书第一章 §编排模式（工作流 vs 自主）**（卡 `m13` 锚点）
书：自主 Agent 需要明确停止条件（任务完成/最大迭代次数/不可恢复错误），否则死循环或过度执行；工作流执行路径确定、提示注入或模型犯错影响面封在当前节点；实践常混合使用。落点：终态三判据（无 tool_calls/轮次上限/预算判据）即书里停止条件清单的逐条落形（取舍 2）；问答链是混合形态——循环拓扑、回灌纪律、帧桥接是运行时代码（工作流），"调不调工具、调哪个、调几次"由模型读描述契约自决（自主）。

**docs/tech-stack/openai-embedding.md · Function Calling 五步循环与回灌形状**（设计范围框架红线锚）
文：官方五步——带 tools 请求→收到 tool call→应用侧执行（API 本身不执行任何函数）→以 role:"tool" 消息回灌（tool_call_id 必须对应上一条 assistant 消息里的 id）、二次请求→收到最终回复或继续更多轮 tool call；含 tool_calls 的 assistant 消息必须原样入历史；新模型一轮并行 0/1/N 个调用按 N 处理；流式 delta.tool_calls 带 index、arguments 字符串逐段拼接、末块才有 finish_reason。落点：主干 B 的 while 体即五步的循环化（第⑤步"或继续更多轮"= continue 分支）；回灌三行（原样入史/N 对 N/call_id 钉死配对）与流式归并逐条按官方形状书写——设计范围红线"真实调用序列，不许概念性提及"的兑现位。

**原书第二章 §Agent如何调用大模型 · 无状态与消息结构**（卡 `m13` 锚点）
书：API 每次调用无状态，模型不记忆历史，Agent 框架必须每次把完整消息列表送回；system/user/assistant/tool 四角色加顶层 tools 字段覆盖上下文构成。落点：主循环每轮 Gateway.chat 全量重送 messages——工具轮的"记忆"不在模型里、在轨迹里，回灌消息就是下一轮的输入；tools 每轮照带（设计稿 12 契约）与"工具定义计入输入 token 计费"的账在此兑现，也是预算判据（取舍 2）必须存在的原因：上下文随轨迹逐轮变贵。
