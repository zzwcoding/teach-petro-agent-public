**"无写入路径"的三层守法各防什么**（捣乱输入 B 逐条推演）：第一层防手滑——编排代码里父块变量就在作用域里，但实参表达式从子块清单构造，"顺手把父块也写进去"没有可写的位置；第二层防改错——后人改造这段代码时把父块混进清单，哨兵 assert 在双写前当场炸（离线期暴露，不带病进库）；第三层防绕路——绕开 Indexer 另起炉灶喂索引，行为本身被边界规则表 v4 增补行定性为越界（评审合同，违反即评审必拦的红项）。WeKnora 的同构守法（引用块逐字，解释在正文）：WeKnora 入库时父块与子块同批写库，但**可检索批**按块类型过滤后单独收集——

internal/application/service/knowledge_process.go:560-561（同 commit，实测）：
    // Collect retrievable text chunks only. ParentChunkID only controls parent expansion after retrieval.
    // When ParentChunkID is empty, retrieval keeps the standalone child content without loading a parent.

正文解释：第一行的"into DB but NOT into the vector index"就是设计范围锚点说的"父块只入库不索引"原注释——入库（m3 侧）与入索引（m14 侧）从这句话起就是两条路；第二行交代索引批的构造纪律（"只收可检索的文本块"）与回捞语义的边界（"ParentChunkID 只管检索后的父块扩展"），并顺带定义了孤儿行为（"ParentChunkID 为空时检索保留独立子块内容、不加载父块"——主干三判断④的出处）。

    def __init__(self, repository):
        self._repo = repository                # m3 公开面（边界规则：只走 Repository 公开方法）

    async def fetch_parents(self, child_hits) -> [ParentChunk]:

        # 主干判断②去重收集：命中子块的 parent_id 逐个收，按父块号去重——
        #   兄弟子块双命中（p14#c3 与 p14#c4 同属 sec14）一父只捞一次

        if 父块号清单为空:
            return []
        # 主干判断③批查：m3 公开面一次带回（卡面签名 get_chunks_by_ids——设计稿 10 发现补，
        #   "含块原文与引用定位"——父块原文正走这个字段）
        父块行 = await self._repo.get_chunks_by_ids(父块号清单)
        # 主干判断④防御性过滤：批查接口不区分类型，回捞侧只收 chunk_type=="parent" 行——
        #   子块号误入清单（上游 bug）在这里被拦，不会把另一子块当父块拼进上下文
        父块行 = [行 for 行 in 父块行 if 行.chunk_type == "parent"]

        #   不报错、不造父块、子块独立内容照常出（WeKnora 原注释同语义：主干二引用块第二行）
        return [ParentChunk(父块号=行.块号, 原文=行.原文, 起始页=行.起始页, 结束页=行.结束页,
                            来源子块号=[命中.号 for 命中 in child_hits if 命中.parent_id == 行.块号])
                for 行 in 父块行]
        # ParentChunk 为数据形状（同 ChunkBatch/Hits 地位）：回捞结果的唯一载体，
        #   "来源子块号"回指命中者——主干四引用锚定位与走查观察都靠它

## 关键判断的取舍记录

1. **回捞策略三岔：父块替换 / 前后文拼接 / 携带式扩展——落定携带式。** 备选一"父块替换"（父块顶掉子块进候选集）：否决理由——引用断锚（W-F30-3 判据"引用仍指子块位置"直接不成立：候选的 page 变成父块起始页，句子级引用纪律失效），且父块进候选集=父块出现在检索结果集，INV 在检索侧破口；备选二"前后文拼接"（命中子块前后各捞邻块拼上下文，WeKnora 的 nearby 语义）：否决理由——上下文碎片化（拼两三段邻块仍是切片视角，拼不出章节全貌），且多命中时邻块重复拼接（两个命中子块互为邻居，同段进两份上下文）；落定"携带式扩展"：子块留候选席（引用锚不动、精排只烧子块成本），父块正文作为扩展段随候选进生成上下文（主干三/四）。换边条件：父块超窗（章节级父块接近上下文预算上限）时改携"父块节选"（以命中子块为窗心的父块切片）——判据归 RAGAS 上下文精确度（设计稿 11），本设计稿不预支。
2. **回捞时点收在 search 内、精排之前——检索接缝单一性压过回捞成本。** 备选：精排后对 top_n 回捞（回捞量从 top_k 降到 top_n，省批查次数）。否决理由：检索接缝在 `Retriever.search`、m13 的 qa 链只认 Candidates（卡 m6 Seam 明文）——父块扩展必须装进 Candidates 才能到生成侧，挂精排后就得改 Ranked 形状与精排签名，下游两处改动换"少捞几条"的小账，不值；且精排本来就只看子块原文（父块扩展字段对 reranker 透明），先捞不烧精排成本。落定：search 充实段一次批量回捞（主干四）。换边条件：top_k 与 top_n 差距大到批查成本可见（评估侧出数据）再议，接口形状不动。
3. **父块表落在 m3 既有公开面（chunk_type 行族），不为父块发明 Repository 新签名。** 备选：为父块立专签名（`save_parent_chunk`/`get_parents`）。否决理由：卡 m3 公开接口未扩父块方法——伪代码红线"公开签名逐字取自模块卡，不许自造"；且 `save_chunk_meta`/`get_chunks_by_ids` 两个既有签名的语义（块元数据存取/按号批查含原文）恰好覆盖父块存取，卡 m14 扩容注释"metadatas 带 chunk_type 区分"的 m3 存取对偶就是行族方案。落点声明见头部。换边条件：后续扩卡立专签名时，改动收在 ParentStore 一处（m6 消费方零感知——seam 的标准收益）；独立表 vs 行族的物理形状之争同归后续扩卡裁决，INV 判据不受影响（判据在"进不进 m14"）。
4. **子块参数沿用 512/1024/15%，不追 WeKnora 的 384 子块。** 备选：照抄 WeKnora 工程样本（child 384/overlap 384/5、parent 4096）。否决理由：卡 m6 的 256–1024/10–20% 是既有卡面契约（设计稿 09 已按中位起点落定），父子分块的升级点是**粒度分家**不是参数搬家——子块参数沿用意味着单级对照（设计稿 09 的 run）与父子对照（本节）的子块侧完全同参，检索质量对比才归因到"父块扩展"单一变量；WeKnora 父块 4096 量级取作父块窗上界的工程样本（主干一注），子块 384 属其嵌入配置适配，本设计稿不照抄。换边条件：RAGAS 评估（设计稿 11）出对照数据后按数据调参——参数是起点不是圣旨（设计稿 09 捣乱 A 同哲学）。
