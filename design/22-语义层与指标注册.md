### 主干一：注册表装载——yaml.safe_load 真实调用序列与启动快速失败闸（W-F13-4 的机制半边）

```text
伪代码 — app/semantics/registry.py:MetricRegistry（m16；签名=卡 m16）

import yaml                                     # PyYAML——官方 API，调用序列见 load 内

class MetricRegistry:
    def __init__(self, repository):
        self._repo = repository                 # m3 公开面注入（save_snapshot 落生效清单）——零引擎内部触碰
        self._by_id = {}                        # metric_id → MetricDef（装载后只含 approved）
        self._synonyms = {}                     # 归一化同义词 → [metric_id, ...]（一义多指标=候选组，W-F13-2 来源）
        self._manifest = {}                     # 生效清单（id→version/owner/status）——落库存档用

    async def load(self, dir) -> None:
        files = sorted(Path(dir).glob("*.yaml"))
        if not files:                           # 主干判断：目录空=口径资产没随版本管理交付——装配缺失
            raise SemanticRegistryLoadError("metrics 目录为空——口径文件未交付")
        by_id, synonyms = {}, {}
        for path in files:                      # 数据变形：YAML 文本 → 受检的 MetricDef
            raw = yaml.safe_load(path.read_text(encoding="utf-8"))
            # ↑ 官方调用序列：safe_load 只构造标量/列表/字典，不实例化文件里的任意 Python 对象——
            #   口径文件"是数据不是代码"的机制保证（对比裸 yaml.load 可执行任意标签，注册表绝不那么装载）
            校验口径结构(raw, path)              # 主干判断：八字段齐 / owner 非空 / status=approved /
            #   / version 为正整数——任一不过 → SemanticRegistryLoadError(文件名, 字段)（闸语义见捣乱 B）
            校验模板只读(raw["sql_template"], path)     # 首词 SELECT 的完整性初检——执行侧只读闸归 m7/m17，不重复造
            if raw["id"] in by_id:              # 同 id 两份=口径打架，装配期即死不留给运行时
                raise SemanticRegistryLoadError(f"{path.name}: 指标 id 重复定义")
            by_id[raw["id"]] = MetricDef(**raw)
            for term in raw["synonyms"] + [raw["name"]]:
                synonyms.setdefault(归一化(term), []).append(raw["id"])
        # 数据变形收尾：三级匹配的两级索引就绪（精确 id 索引即 by_id，同义词倒排即 synonyms）
        self._by_id, self._synonyms = by_id, synonyms
        self._manifest = {mid: {"version": d.version, "owner": d.owner}
                          for mid, d in by_id.items()}
        # 注册表落库（验收 5 前半）：生效清单快照经 m3 存档——事后可答"当时生效的是哪版口径"
        await self._repo.save_snapshot("registry_manifest", 序列化(self._manifest))
        # 异常去向：SemanticRegistryLoadError 原样上抛——调用方是应用装配点（m1 lifespan，设计稿 13
        #   boot_register 同款时机），收到即拒绝启动。对齐 m11 key_selfcheck 的闸语义：
        #   带病资产宁可不上线，也不带病接流量

    def get(self, metric_id, version="latest") -> MetricDef:
        d = self._by_id.get(metric_id)
        if d is None:
            raise MetricNotFound(metric_id)     # 注册表里没有 = 未收录或未发布（不是可重试错误）
        if version != "latest" and version != d.version:
            raise MetricVersionNotFound(metric_id, version)   # 只保 approved 最新版——历史版本在 git 里
        return d                                # "latest" = 当前生产版：文件是唯一真源，没有第二本账
```

### 主干二：lookup 三级匹配——精确 id → 同义词表 → 别名模糊（W-F13-1 的匹配半边）

```text
伪代码 — app/semantics/registry.py:MetricRegistry.lookup（m16；签名=卡 m16；纯内存读，同步）

class MetricCandidate:          # 数据形状——澄清帧的原材料（先看装什么，再看怎么装）
    metric_id: str              # "net_oil_output"
    name: str                   # "净产量（检修井剔除口径）"
    version: int                # 命中即锁版——一次提问的一生内口径不漂移
    matched_via: str            # "exact_id" | "synonym" | "fuzzy"——Resolver 判"直绑还是确认"的依据
    diff_note: str              # 口径差异摘要（装载期预拼的一句话）：本支与同组其他候选差在哪——
                                #   "剔除当月检修井后净计；开井日历口径不剔"（W-F13-2 澄清帧带的就是它）
    definition: str             # 完整定义——澄清帧展开用
    unit: str                   # 吨 / 方 / %

    _FUZZY_THRESHOLD = 0.75     # 别名模糊层的准入线（取值理由见本主干末段）

    def lookup(self, term, user) -> [MetricCandidate]:
        term = 归一化(term)                     # 数据变形：去空格、全角转半角——输入毛刺不丢命中
        if term in self._by_id:                 # 第一级：精确 id——治理者/上游按 id 点名，零歧义
            return [候选(self._by_id[term], matched_via="exact_id",
                         diff_note="按编号点名，无同组候选")]
        if term in self._synonyms:              # 第二级：同义词/指标名全等——治理时人工登记的说法
            ids = self._synonyms[term]
            return [候选(self._by_id[i], matched_via="synonym",
                         diff_note=组内差异摘要(i)) for i in ids]
            # 一义多指标（"有效产量"两支口径）在此自然成组——直绑与否交 Resolver 裁（主干三）
        # 第三级：别名模糊——词表没登记的说法，字符二元组 Jaccard 相似度兜底召回
        scored = [(jaccard_bigram(term, 别名), i)
                  for i, d in self._by_id.items()
                  for 别名 in d.synonyms + [d.name]
                  if jaccard_bigram(term, 别名) >= self._FUZZY_THRESHOLD]
        return [候选(self._by_id[i], matched_via="fuzzy",
                     diff_note=组内差异摘要(i)) for _, i in 排序去重(scored)]
        # 主干判断：模糊来源的候选即使只有一个也交确认——直绑只留给前两级，模糊 ≠ 确信（取舍 1）
        # user 参数：本节只用全局同义词表；入参预留作用域扩展（外部调研：同义词加在 agent 作用域，
        #   不污染全局元数据——个性化同义词/默认口径是它的后续落点）
        # 异常去向：零候选返回空列表——"没找到"是正常业务态不是错误，未命中路径在 m7 主干五送审
```

**阈值 0.75 的意思**：字符二元组 Jaccard ≥0.75 基本只剩同词变体（"月产液"vs"月产液量"）。词表的活（完成率/达标率）词表干，模糊层只兜"登记时没料到的说法"——阈值放低会把大量似是而非的词拽进澄清帧，澄清就从"偶尔确认"贬值成"每问必烦"。

### 主干三：Resolver.bind 三出口——直绑 / 澄清 / 默认+标注（W-F13-2 的裁决半边）

```text
伪代码 — app/semantics/resolver.py:Resolver.bind（m16；签名=卡 m16；纯内存判断，同步）

class MetricRef:                # 数据形状——绑定凭据，State 的 metric 格里装的就是它
    metric_id: str              # "net_oil_output"
    version: int                # 1——命中即锁版
    default: bool               # False = 用户裁决/唯一直绑；True = 默认口径（结果必须带标注）
    note: str | None            # default=True 时的标注原文："默认口径：有效产量（开井日历口径）——未按
                                #   检修井剔除口径计算"

class ClarifyNeeded:            # 数据形状——澄清帧载荷，m7 折进 interrupt 出图
    candidates: [MetricCandidate]   # 各带 diff_note 口径差异摘要
    default_id: str                 # 默认口径候选——澄清帧"按默认口径出数"按钮指向它

class Resolver:
    def bind(self, candidates, user_choice=None) -> MetricRef | ClarifyNeeded:
        if not candidates:                      # 防御：调用序闸——零命中走 m7 未命中路径，不进本函数
            raise ValueError("bind 不收空候选")
        确信 = [c for c in candidates if c.matched_via in ("exact_id", "synonym")]
        if user_choice:                         # 出口三：用户已裁决（澄清帧回流的选择）
            picked = 取候选(user_choice)         # 具体选择 → 该支；"默认"/空恢复 → 默认判据选支
            if picked.metric_id == 默认判据(candidates).metric_id:
                return MetricRef(picked.metric_id, picked.version, default=True,
                                 note=f"默认口径：{picked.name}——{'、'.join(未计入的修饰词)}未计入")
            return MetricRef(picked.metric_id, picked.version, default=False)
        if len(确信) == 1:                      # 出口一：唯一确信命中直绑（W-F13-1——零打扰）
            return MetricRef(确信[0].metric_id, 确信[0].version, default=False)
        # 出口二：多候选（或模糊来源候选）——澄清帧交用户裁决，不替用户猜口径
        return ClarifyNeeded(candidates=candidates,
                             default_id=默认判据(candidates).metric_id)
        # 默认口径判据：修饰词最少的候选 = 基础口径（并列取 id 序首个）——检修剔除/商品折算这类
        #   差异在数据模型里就是"多加一个修饰词"，最少修饰词即最朴素的口径
        # "不选按默认口径出数并标注"（W-F13-2 后半）在出口三兑现：标注写明默认是哪支、没算什么——
        #   宁可交代不足，也不冒充精确（外部调研澄清交互：用户说不清 → 默认口径出数并标注）
```

### 主干六：Lifecycle 状态机——draft → in_review → approved(version+1) / rejected（W-F13-3）

```text
伪代码 — app/semantics/lifecycle.py:Lifecycle（m16；签名=卡 m16；🛡️ 人工关卡）

class Lifecycle:
    def __init__(self, registry, repository):
        self._registry = registry               # 写回 YAML 后调 registry.load 重载（进程内即时生效）
        self._repo = repository                 # m3 公开面：save_snapshot（提案载荷）+ save_audit（登记/决议）

    async def propose(self, draft) -> proposal_id:
        校验草稿(draft)                          # 前置闸（外部调研轮 4"编译校验/冲突检测"的朴素版）：
            # 必备字段齐、sql_template 首词 SELECT、name/synonyms 与现有指标重名重义 → 打回不收
        if 指纹已待审(SQL 指纹(draft)):           # 幂等：同一未命中反复发生不重复入库
            return 既有 proposal_id
        proposal_id = "pr-" + 日期序号
        await self._repo.save_snapshot(f"proposal:{proposal_id}",
                                       序列化({**draft, "status": "in_review"}))
        # ↑ 提案载荷经 m3 通用快照面落库（待审库）；metrics/ 一个字节都不写——
        #   "未审核候选绝不进生产模板"的物理保证：生产真源里根本没有这个文件
        await self._repo.save_audit({"类型": "指标提案登记", "幂等键": proposal_id,
                                     "来源问题指纹": SQL 指纹(draft), "状态": "in_review"})
        return proposal_id                       # 状态机：draft（模型产出）→ in_review（登记完成）；
                                                 #   approved/rejected 只能由人工决议触达

    async def approve(self, proposal_id, reviewer) -> MetricDef:
        payload = 反序列化(await self._repo.get_snapshot(f"proposal:{proposal_id}"))
        if payload is None:
            raise ProposalNotFound(proposal_id)              # 异常去向：审核台传错号，结构化上抛
        if payload["status"] != "in_review":
            raise ProposalNotInReview(proposal_id)           # 幂等闸：重复审批 / 已拒提案再批都进不来
        # 审批人身份由调用方传入（卡面 Seam 明文）——本卡不鉴权，审计只负责记录
        version = 生产同 id 现版本 + 1 if 已收录(payload) else 1      # 版本 +1 写回（验收 3 的"+1"）
        metric = MetricDef(**{**payload, "version": version, "status": "approved"})
        写回口径文件(metrics / f"{metric.id}.yaml", metric)   # 口径即代码：发布 = 新版本 YAML 进版本管理
        await self._registry.load(metrics_dir)               # 重载：进程内立刻可命中（后续提问可命中）
        await self._repo.save_audit({"类型": "口径审批", "幂等键": f"{proposal_id}:v{version}",
                                     "reviewer": reviewer, "决议": "approved", "版本": version})
        return metric
        # 拒绝半边：rejected 由审核台同形调用落档（status=rejected 留待审库+审计行）——
        #   拒了也是治理记录，可查"为什么曾有这个提案"

    def template_for(self, metric_ref) -> sql_template:      # 纯内存读，同步——命中路径热调（每问一次）
        d = self._registry.get(metric_ref.metric_id, version=metric_ref.version)
        if d.status != "approved":                           # 🛡️ 防御闸：待审/拒绝版本零出模板
            raise MetricNotApproved(metric_ref.metric_id)    #   与"生产目录无非 approved 文件"构成双保险
        return d.sql_template
```

## 关键判断的取舍记录

1. **唯一命中直绑不弹确认——对调研轮 4"弹窗确认"的收窄**。该轮的现场做法是"命中 → 弹窗确认后走固定模板"。全盘照抄会把每次问数都变成两次点击：高频查询的摩擦成本远超确认收益。本设计稿收窄为——精确 id/同义词全等的唯一命中直绑零打扰；模糊来源与多候选才进人审（确认的身价留给真正的不确定，Genie verified queries 同样无逐次确认）。代价：同形异义的同义词误绑不会被确认拦住。换边条件：评估数据显示同义词误绑发生——在 MetricDef 上加 per-metric confirm 开关，而不是全局弹窗。
2. **SQL 走固定模板，不每次重生成**。备选是"把指标定义当提示词素材，每次让模型现写 SQL"。固定模板赢在三处：一次人工审核 N 次复用零漂移、零生成成本、零 KV 前缀重建；自由生成每次都在赌模型这次没选错字段——调研轮 4 的原始故障就是"同一指标每次问出来都不一样（概率性选不同字段）"。模型仍干它擅长的：意图识别（m7 既有节点）与未命中时的口径草拟（主干五）。换边条件：模板覆盖不了的长尾问题占比暴涨——用设计稿 23 评估链的 badcase 数据说话，而不是现在就上"半模板半生成"的混合形态。
3. **口径 YAML 即代码，不存指标库**。备选是指标入 m3 建表+管理界面。落 YAML+版本管理的理由：口径变更天然走 diff/评审/回滚，与代码评审同构；YAML 是 dbt SL 与 OSI 的行业交换形状，未来接语义层标准零迁移；m3 只落审计与生效清单快照（追溯半边），不承载真源——真源唯一才谈得上一致。代价有二：approve 写文件要求应用进程对 metrics/ 有写权（部署期声明）；"latest"只保当前版，历史版本去 git 里翻。换边条件：出现指标运营团队、多产品消费、需要 API 化治理时——那是引入 dbt SL/MetricFlow 类件的换边点，不是自研指标库。
4. **State 增 metric 一格 + 澄清走 interrupt，不出图反问**。MetricRef 要从选表节点流到生成节点，图内唯一合法通道是 State——卡面七字段增一格，属设计范围"接线消费 MetricRef"的授权面（建议在卡面 State 行补记）。澄清不走意图闸那种"goto=END 出图、用户重问一题"：选口径是"同一问的中途确认"而非"信息不足"——interrupt 挂起在检查点上（设计稿 15 同款机制零新发明），选择回流同一问的一生，会话上下文不重装配、KV 前缀不重建；老王不选的空恢复路径恰好承接"不选按默认口径出数"。

## 锚点对照精要

**dbt Semantic Layer 一致性（外部调研）**：原文——指标定义若在 dbt 里变更，"it's refreshed everywhere it's invoked and creates consistency across all applications"，一次定义处处刷新。落点：走查推演 4——一致性不靠同步广播，靠"引用结构上没有旧副本"：消费方只持 metric_id 引用，模板每次现取当前 approved 版。差异：dbt 的刷新发生在其 SL API 后面，我们把"刷新"压平成一次 `registry.load`（单进程规模还不需要 SL API 这层壳）。

**MetricFlow 编译（外部调研）**：原文——指标定义被 "compiled into a dataflow-based query plan, then optimized and translated into engine-specific SQL"，多跳 join、比率/累计指标由编译器处理。落点差异：我们的 sql_template 是人写的整句 SQL（审核时人眼看过），不做查询计划编译——油田口径的 join 形态稳定（日产表 join 井档案），编译器的收益撑不起它的复杂度。换边：比率/累计类复杂指标多起来、join 需要按指标自动推导时，才值得引入 MetricFlow 类件（与取舍 3 同源）。

**Genie metric view / verified queries / 注释纪律（外部调研）**：原文——metric view "pre-define metrics, dimensions, and aggregations" 是 agent 的首选载体；example/verified queries 让 agent "match user prompts to verified SQL queries"；同义词加在 agent 作用域、不污染全局元数据。落点：YAML 指标≈metric view 的极简版（预定义聚合与维度参数）；verified metric≈verified queries 的指标化（以指标为粒度而非单条问答）；同义词进 YAML 全局表，lookup 的 user 入参预留作用域扩展（留口不展开）。

**轮 3 黑话→语义对象（外部调研）**：原文——用户说黑话（有效销售额/老客复购）而系统无同名字段，第 3 轮把"自由解释"收敛为映射到受治理的语义对象（Jargon → governed object）。落点：lookup 三级匹配序就是这条映射的实现——黑话先进同义词表（人工登记），没登记的走模糊兜底，兜底也不中才轮到 AI 候选。差异：该调研用向量库做语义映射，我们词表+字符二元组就够（五个指标的规模）——资产多了再换 Knowledge Indexer，lookup 接口不变。

**轮 4 verified metric 闭环 + 澄清交互（外部调研）**：原文——轮 4 命中走固定 SQL 模板（LLM 只做意图识别，不重新生成），未命中走 AI 候选 → 编译校验/冲突检测/人工审核 → 发布写回；Q&A 里三个候选指标"各算一遍、把结果差异摆给用户选"，用户说不清按默认口径出数并标注；修饰词本质上定义了不同指标。落点：Lifecycle 状态机与"修饰词最少=基础口径"的默认判据都从这里来；propose 的前置校验对应其"编译校验/冲突检测"的朴素版。差异两处：命中即弹窗确认被收窄（取舍 1）；澄清帧摆的是口径差异摘要（装载期预拼的一句话）而非"各算一遍"的结果对比——各算一遍等于每次澄清付三次查询的钱，摘要零成本。换边：候选差异细到肉眼难辨时，澄清帧升格为预览对比。

**curated descriptions + 澄清默认值不阻塞（外部调研）**：原文——OpenAI 内部数据智能体的六层上下文专设 "Curated descriptions：领域专家策展的业务口径描述"层；澄清策略是"含义不明时主动提出澄清问题；用户不响应则套用合理默认值，不阻塞继续执行"。落点：YAML 的 definition/owner 字段就是策展描述——且 ours 强制 owner，无主口径不得生效，比"描述"多一道问责锚；"默认口径出数+标注"就是"不阻塞"的兑现——数照出，但把"这是默认"写在结果上，用透明化替代静默。
