### 第 0 步：段表、预算形状与 SemanticContext（协议的静态面）

> 瀑布的灵魂不是某一段，是**判定序**：便宜的确定性先花，昂贵的相似度后花；每级都有早停条件——"该级已给出消费所需的全部材料"就叫命中，命中即停，剩余预算不花（DataBuddy §方案节："显式锚定优先、逐级升级、可早停"）。

| 级 | 输入 | 干什么 | 输出 | 早停条件（答案已齐？） | 预算消费 |
|---|---|---|---|---|---|
| S0 固定边界 | question, user, budget | 落身份/会话/口径版本/ACL 四要素 | boundary | 永不停（边界不是检索级） | 零检索调用 |
| S1 显式锚定 | 问句文本 | 锚语法解析 | [ExplicitAnchor] | 锚命中 ∧ 目标对象可定位 → 跳过 S3–S5 | 零检索调用 |
| S2 对象装配 | 锚/候选对象名 | 引用闭包+任务裁剪 | assembled 材料 | 闭包齐 ∧ 锚命中 → 早停 | 闭包条数 ≤ budget.assembly_items_max |
| S3 确定性检索 | 指标词（归一化） | 收编 v2 三级匹配 | [MetricCandidate] | 前两级唯一命中 ∧ 材料齐 → 早停 | 纯内存读 |

### 主干一：Waterfall.retrieve——段管线骨架与预算裁剪

```text
伪代码 — app/agents/text2sql/retrieval_protocol/waterfall.py:Waterfall.retrieve（m21；签名=卡 m21）

class Waterfall:
    @staticmethod
    def 段表():                      # 纯 Python 段管线（框架红线）：段是普通异步函数的有序列表，
        return [S0 固定边界, S1 显式锚定, S2 对象装配, S3 确定性检索,   # 不是图、不是框架 pipeline——
                S4 混合召回, S5 受限图扩展, S6 资格与歧义, S7 回读权威源]  # 顺序即判定序，见第 0 步表

    async def retrieve(self, question, user, budget) -> SemanticContext:
        ctx = SemanticContext(verdict=None, trace=[])
        for 段 in self.段表():                        # 数据变形：ctx 逐级增材料——只增不改（段间零隐藏耦合）
            ctx = await 段(ctx, question, user, budget)
            ctx.trace.append(段.落款(ctx))             # 每级留痕：走到哪、停在哪、花了多少——S8 的原料
            if ctx.verdict in ("clarify", "reject"):
                return ctx                             # 出帧终态：澄清/拒答即瀑布出口，后续段不再执行
            if 段.答案已齐(ctx):                        # 早停判定（各段自报，判据见第 0 步表）：
                ctx.verdict = "pending"                #   是"材料够出答案"不是"走到最后一级"——
                break                                  #   S1/S3 命中即停，S4–S5 的预算一分不花
        if ctx.verdict is None:                        # 走完段表仍无裁决 → S6 兜底裁决（不会发生：
            ctx = await S6 资格与歧义(ctx, question, user, budget)   # S6 必给三出口之一，防御性兜底）
        return ctx
        # 异常去向三层（伪代码通用约定）：m16 结构化异常（注册表未装载）上抛——装配缺失非查询错误；
        #   m14 IndexStoreError 上抛折错误帧；权限缺身份（user 为空）在 S0 即出拒答帧——不猜不假名
```

**预算如何裁剪消费**：budget 不是瀑布的性能调优开关，是**协议的破产条款**——每级只许花自己那格预算：S2 装配材料超 `assembly_items_max` 就按"与意图三要素的相关度"裁掉尾部（任务裁剪，主干三）；S4 召回 `vector_top_k` 与设计稿 14 选表 `_SCHEMA_TOP_K=5` 同量级；S6 澄清帧候选超 `candidates_max` 时按默认判据截到上限并在帧上写明"另有 N 支未列出"。**早停与预算的关系**：级别越靠前越便宜——S1 零检索调用、S3 纯内存读、S4 才有向量计算与 IO；多数问题停在便宜级，是协议省钱的机制而不是巧合。预算花尽仍无候选 → S6 拒答，不硬凑（"宁拒答不硬凑"，取舍 3）。

### 主干二：S0 固定边界 + S1 显式锚定——Anchor.parse（W-F21-1 的机制半边）

```text
伪代码 — app/agents/text2sql/retrieval_protocol/stages.py:S0/S1（m21；Anchor.parse 签名=卡 m21）

async def S0 固定边界(ctx, question, user, budget):
    # 主干判断：边界四要素一次落定，后续段只读不写——"固定"指本问一生内不变（命中即锁版的瀑布版）
    if user is None:                                   # 无身份不服务——ACL 闸收在入口
        return ctx 带 verdict="reject"（拒答帧："会话身份缺失，请重新登录"）
    ctx.boundary = {"user": user,                      # 谁——身份由桥接层经 config 注入（设计稿 19 形状），
                     "session": 当前会话号,             #   本段只读，不鉴权（鉴权归 m1 auth_verify 既有闸）、
                     "manifest_snapshot": 生效清单号,   #   不做信任打标（归 m19）——S0 只读身份，不越界代劳
                     "acl_note": 角色(只读)}            # 口径版本=设计稿 22 registry_manifest 快照号——S7 核验的比对基线
    return ctx

def Anchor.parse(text) -> ExplicitAnchor | None:       # 纯函数：只认语法，不查库（查库是 S2/S7 的事）
    for 前缀, kind in [("@metric ", "metric"), ("@entity ", "entity")]:
        if text 以 前缀 开头:
            return ExplicitAnchor(kind=kind, raw=text[len(前缀):].strip())
    if text 被指标编号格式全匹配（如小写下划线 id 形）:  # 第三种：Stable ID 直引——治理者/上游按编号点名
        return ExplicitAnchor(kind="stable_id", raw=text)
    return None                                        # 无锚不是错误——自然语言走 S3/S4，协议不歧视无锚问句

async def S1 显式锚定(ctx, question, user, budget):
    anchor = Anchor.parse(question)
    if anchor is None:
        ctx.trace.append("S1 无锚——按自然语言下探")
        return ctx                                     # 不早停：确定性层（S3）还没机会
    ctx.anchors = [anchor]
    ctx.candidates = [候选(锚名=anchor.raw, matched_via="anchored")]
    # 主干判断（W-F21-1）：锚命中即早停——S3/S4/S5 不进执行轨迹，检索预算零消费。
    #   但"早停"早的是**检索级**，不是校验级：S2 装配、S6 资格、S7 回读一个不少——
    #   显式锚定给的是"直达权"，不是"免检权"（捣乱输入：锚到废弃叫法，S7 照拦）
    return ctx
```

**为什么锚语法只有三种**（取舍 1）：@metric/@entity/Stable ID 恰好对应三域权威源的可点名键——指标名、实体名、资产编号；锚是**协议的语法**不是模型的约定——解析在纯函数里逐字符完成（前缀匹配+编号格式全匹配），模型没有解释权，也就没有漂移空间。老王那句"@metric 产量完成率"过 S1 的代价是一次字符串前缀比较；同一句走自由路径要付 S4 的嵌入+召回——这是"显式锚定直达"的机制含义（走查推演 1）。

```text
    if ctx.verdict == "clarify":                         # 歧义闸衔接（设计稿 22 interrupt 形状原样，桥接零改动）
        choice = interrupt(ctx.clarify)                  # 挂起出澄清帧——选择回流本节点幂等重跑（读操作）
        # 卡面签名 Waterfall.retrieve(question, user, budget) 三参数逐字不动；澄清恢复需要把老王的选择
        #   送回 S6（否则重跑二次出同一澄清帧）——恢复通道以关键字参数随节备案（State 增格同款备案纪律）：
        #   位置签名零变化、缺省 None 即纯检索；设计稿 40 五段化时该值并入裁决载荷，备案可撤
        ctx = await Waterfall.retrieve(state["question"], user=config 取当前用户,
                                       budget=协议默认预算, 用户裁决=choice or "默认")
        #   重跑=瀑布第二次完整走段（S0–S7 读操作零副作用）——S6 收用户裁决走 bind 出口三，
        #   重跑路径同样过 S7 核验（恢复路径没有免检特权，W-F21-4 对所有路径成立）
    if ctx.verdict == "reject":                          # 拒答帧（设计稿 14 信息不足闸同款图路径闸）：
        return Command(update={"result": ctx.拒答帧载荷}, goto=END)   # 拒答是终态，生成/执行不在轨迹上
    return {"tables": ctx.schema_hits, "metric": ctx.metric_ref,
            "semantic_context": ctx}                     # State 增 semantic_context 一格（随节备案：
    #   设计稿 22 metric 格同款先例——格是设计范围授权的接线面；设计稿 40 五段化时此格升格为 SemanticContext 段）
    # 异常去向：与设计稿 14/22 同款——装配缺失上抛、可纠正回灌、权限拒理由入轨迹，本层不吞
```

## 关键判断的取舍记录

1. **锚语法只收三种，且解析是纯函数**。备选是"让模型识别锚意图"或扩到 @playbook/@term 全域前缀。收敛到 @metric/@entity/Stable ID 的理由：锚的价值在**零解释**——前缀比较与编号格式全匹配没有模型参与，就没有漂移；@playbook 类触发已有设计稿 37 意图匹配承载，重复设锚是两套触发序打架。代价：用户写错前缀（"@metrics"）静默降级为无锚路径——可接受，无锚路径仍是完整瀑布；换边条件：评估数据显示锚拼写失误率显著，S1 加"近似前缀提示"帧，而不是放宽解析。
2. **S2 只收集不裁决，裁决权归 S7**。备选是装配期发现禁用词就地拦下（省两级）。走到底的设计理由：协议的可读性来自"每级一件事"——S2 是材料员、S6 是资格审、S7 是权威源；装配期拦截会让"废弃叫法"的裁决散落在两级，话术与留痕各写一遍。代价：废弃锚多走两段纯内存读（纳秒级）。真成本在一致性：拦下话术只有一个出口（S7），设计稿 35 的替代帧语义零复制。
3. **预算耗尽宁拒答不硬凑**。备选是预算耗尽降级放行（带标注出数）。拒答的理由：无候选的"降级出数"等于让模型自由发挥——这正是瀑布要关掉的门（对照设计稿 10 无据拒答闸同款哲学）；而标注放行只适用于"有候选有默认"的歧义态（设计稿 22 语义，S6 已承接）。两者不冲突：有依据可默认，无依据须拒答。
4. **模糊有候选时不下探 S4**。备选是模糊与召回候选合并进澄清帧（信息更全）。不合并的理由：模糊层（词表近邻）与召回层（语义相似）是两种不确定，混进一帧让用户在"词没登记"与"语义相近"两类候选间连线，认知负担大于收益；且确定性层已给出可确认候选时，协议的原则是先让便宜的确定性闭环。换边条件：澄清-放弃率数据显示用户在模糊候选帧找不到想要的——再评估合并帧。
5. **SemanticContext 先以数据形状收尾，TypedDict 化归设计稿 40**。设计范围"明确不讲的"边界在此：本设计稿的 ctx 已经是五段第二段的**字段全集**（第 0 步钩子预告），设计稿 40 做 TypedState.assemble 时零字段废弃、只加类型——先跑通协议再类型化，避免两稿互相等。
