### 主干一：State 定义——状态归属图，reducer 决定"怎么合并"（图骨架契约之一）

```text
伪代码 — app/agents/text2sql/graph.py:State（m7；形状=设计稿 00 登记表 m7 类型行 + 卡 m7 State 行）

from typing import Annotated, TypedDict
from operator import add                       # 官方惯用法：Annotated[list, add]（锚 LangGraph 官方文档 能力面表）

class State(TypedDict):
    question: str                    # 老王的原始提问："上个月产量最高的三口井"
    intent: dict                     # 澄清产物：{entities: {井号/时间范围/指标}, missing: [...], sufficient: bool}
    tables: list                     # 选表产物：命中表的 DDL 摘要（m14 schema 集合检索所得）
    sql: str                         # 当前轮生成的 SQL
    error: dict | None               # 上一轮结构化错误（回灌原料；成功轮为 None）
    attempts: Annotated[list, add]   # ★ 尝试轨迹：每轮校验结论追加一条——目录骨架所称 AttemptsReducer
                                     #   即 operator.add 的列表拼接语义（不另造类）
    result: dict | None              # 终态：行数据+解释+图表建议，或反问/转人工话术
```

**reducer 是什么、没有它会怎样**（官方口径：锚 LangGraph 官方文档"reducer 决定节点返回值如何合并进状态，默认是覆盖"）：

- LangGraph 节点的返回值是**部分更新** dict，不是全量 State——图按每个键的 reducer 把它合并进当前快照；键上没挂 reducer，合并语义就是"新值顶旧值"。
- attempts 若写成普通 `list`（无 reducer）：对它的一切写都是**整键覆盖**——verify_result 每轮返回 `{"attempts": [本轮]}`，上一轮记录被顶掉，轨迹永远只剩一条，`len() ≥ 3` 的熔断判据永不触发，循环只能靠官方 `recursion_limit`（默认 1000）兜底——"重试上限闸"名存实亡。这就是"两个节点同写"的第一种死法：**顺序写，后写覆盖先写**（哪怕写的是同一节点的前后两轮）。
- 第二种死法是**并行写**：同一 super-step 里两个节点各返回一份该键的更新、而键没有 reducer——官方对无 reducer 键的并发更新按错误拒绝（InvalidUpdateError：一个键一步只收一份更新），图宁可停也不替你猜合并语义。本节布线是串行链（无并行节点）踩不到它，但 reducer 仍不可省：attempts 的消费方要求**跨轮累积**，覆盖语义直接毁掉闸。
- 为什么是 list 不是 `Annotated[int, add]`：int 也能累加，但列表保留每轮的结构化记录（SQL 指纹/错误码/判定）——捣乱 B 的重复指纹检测要读上一轮 SQL、转人工话术要附"已试轨迹"、排障要看每轮判定，三处消费方都不只要总数。

### 主干二：build_graph——官方调用序列布一张六节点图（图骨架契约之二/三）

```text
伪代码 — app/agents/text2sql/graph.py:build_graph（m7；签名=设计稿 00 登记表 m7 首行；调用序列形状=LangGraph 官方最小调用序列）

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

def build_graph() -> CompiledGraph:
    builder = StateGraph(State)                          # 官方建图入口：State 为 TypedDict
    builder.add_node("clarify_intent", clarify_intent)   # 节点=异步函数：入参 State，返回部分更新 dict
    builder.add_node("retrieve_schema", retrieve_schema)
    builder.add_node("generate_sql", generate_sql)
    builder.add_node("check_sql", check_sql)             # 🛡️ 本节直通替身（主干八；设计稿 15 换真闸）
    builder.add_node("run_query", run_query)             # 经 m8 执行器；审批位直通（设计稿 15 换真）
    builder.add_node("verify_result", verify_result)
    builder.add_edge(START, "clarify_intent")            # 静态边：图入口（START 为虚拟节点）
    builder.add_edge("clarify_intent", "retrieve_schema")   # 澄清通过→选表（不足在节点内 goto=END，主干三）
    builder.add_edge("retrieve_schema", "generate_sql")
    builder.add_edge("generate_sql", "check_sql")
    builder.add_edge("check_sql", "run_query")
    builder.add_edge("run_query", "verify_result")
    # ★ 唯一的条件边=反思回边（卡 m7：add_conditional_edges(route_after_verify)，主干七）：
    builder.add_conditional_edges("verify_result", route_after_verify,
                                  {"generate_sql": "generate_sql", END: END})
    checkpointer = InMemorySaver()      # 开发内存版（重启即失）；生产换 AsyncPostgresSaver——
                                        #   官方仅提供 Postgres/SQLite 实现，金仓适配无公开文档属自研改造点（锚 LangGraph 官方文档 选型与版本）
    return builder.compile(checkpointer=checkpointer)
```

```text
伪代码 — 调用方（m13 run_text2sql，设计稿 19 接线）的运行形状（官方形状；本节只锁形状不接线）

graph = build_graph()
config = {"configurable": {"thread_id": "th-laowang-001"}}   # 会话号=线程号：一次提问的一生
final_state = await graph.ainvoke({"question": "上个月产量最高的三口井"}, config)
# 断点续跑：checkpointer 在每个 super-step 边界保存线程状态快照——进程中断后同 thread_id 再 invoke，
#   图从最近检查点恢复，**未完成的节点整节点重跑**（官方幂等约束：节点副作用必须设计为幂等，锚 LangGraph 官方文档）。
#   本节各节点的副作用只有 m3 快照写（成功终态一次，落库幂等由快照键保证）与网关调用（可重放）——
#   整节点重跑无重复副作用累积；设计稿 15 的 interrupt 挂起/恢复（W-F7-6）就站在这套检查点上
```

**为什么必须按会话号恢复**：老王这一问可能跨一次网关超时、一次进程重启——没有 checkpointer，State 只活在单次 ainvoke 的内存里，断在执行节点就整问作废，人工审批挂起（设计稿 15）更无从谈起。InMemorySaver 与 AsyncPostgresSaver 的换边收在 compile 一处参数，图布线零改动。

### 主干三：意图澄清节点——信息不足先反问，不硬生成（W-F7-1）

```text
伪代码 — app/agents/text2sql/nodes/intent.py:clarify_intent（m7；签名=设计稿 00 登记表 m7）

from langgraph.types import Command

# 模块级私有常量 _INTENT_TEMPLATE（冻结系统提示词——抽槽位+判充分性，输出 JSON）：
#   任务：判断数据查询提问是否含齐三要素——井号（哪口井）、时间范围（哪段时间）、指标（什么数据）。
#   输出 JSON：{"entities": {...识别到的要素...}, "missing": [...缺的要素...], "sufficient": bool}
async def clarify_intent(state) -> dict | Command:
    resp = await Gateway.chat(                       # 经 m2 网关（设计稿 07 契约形状，非流式）
        messages=[{"role": "system", "content": _INTENT_TEMPLATE},
                  {"role": "user", "content": state["question"]}],
        model_alias="petro-llm")
    intent = 解析 JSON(resp.content)                 # {"entities", "missing", "sufficient"}
    if intent.sufficient:
        return {"intent": intent}                    # 部分更新：静态边放行去选表
    # ★ 信息不足闸（W-F7-1）：反问话术直接写成终态，goto=END 出图——官方形状：Command 在节点内
    #   合并"状态更新+路由"（锚 LangGraph 官方文档 能力面表）。卡面只点名 route_after_verify 一条条件边——
    #   闸的出口用 Command 收进节点，图布线保持卡面原样（取舍见主干三末段）
    反问 = "您想查哪口井？想看哪段时间的什么数据？（例如：上个月 N-2 井的日产油量）"
    return Command(update={"intent": intent,
                           "result": {"kind": "clarify", "text": 反问, "missing": intent.missing}},
                   goto=END)
    # 节点幂等（卡面注）：本节点唯一副作用是网关调用——中断恢复整节点重跑=重问一次模型，无副作用累积
    # 异常去向：GatewayError 原样上抛（设计稿 07：重试与 fallback 跑完仍败）——折错误帧归设计稿 19，本层不吞
```

**为什么反问是"闸"而不是"提示词求模型别生成"**：模糊提问在图上根本走不到 generate_sql——不是软约束（提示词里写"信息不足请不要生成"），是硬路径（反问分支 `goto=END`，选表/生成/执行不在执行轨迹上）。这换来工作流模式的原生安全属性：执行路径确定，模型犯错或被提示注入，影响面被封在当前节点内部。

### 主干四：选表节点——200 张表怎么砍到提示词装得下（W-F7-2 第 2 站）

```text
伪代码 — app/agents/text2sql/nodes/schema.py:retrieve_schema（m7；签名=设计稿 00 登记表 m7）

_SCHEMA_TOP_K = 5          # 进提示词的表结构预算：top_k 张，不是全库

async def retrieve_schema(state) -> dict:
    # 主干判断①：能走到这里=意图闸已放行（三要素齐备）——本节点不做充分性判断（职责单一）
    # 数据变形①：问题 → 查询向量。嵌入统一走 m2 网关（设计稿 07 变形段契约：Gateway.embed），
    #   与 schema 集合写入侧同一嵌入模型同维（同源闸，锚设计稿 08/09 维度纪律）
    查询向量 = (await Gateway.embed([state["question"]]))[0]
    # 数据变形②：m14 schema 集合近邻检索——schema 集合=设计稿 08 同一封装下的另一 collection
    #   （锚设计稿 08 总览图注）；消费方只见 Hits，Chroma 集合对象零直触（边界规则第 8 行）
    hits = VectorStore.query(查询向量, top_k=_SCHEMA_TOP_K, where=None)
    # 主干判断②：命中为空=表结构文档没装载（装配缺失），不是"可纠正错误"——结构化上抛，
    #   不走反思回边重试（重试改变不了集合为空）
    if not hits:
        raise SchemaStoreEmpty("schema 集合为空——表结构文档未装载，属装配缺失非查询错误")
    tables = [{"table": 命中表名(h), "ddl": 文档原文(h)} for h in hits]   # DDL 摘要原样带回
    return {"tables": tables}
    # 异常去向：m14 IndexStoreError（服务不可达）结构化上抛——调用方折错误帧，本层不吞错不重试
```

**为什么 few-shot 示例要冻结**（KV Cache 机制事实，锚 m13 卡三铁律 + W-F12-1"命中价约 1/10"）：模型服务端对请求的公共前缀做 KV 缓存——Prefill 按 token 逐个算，前缀**逐字相同**才可复用，命中部分的输入计费约为未命中的 1/10。若按当前问题**动态挑选**示例（向量检索 top-3 之类），每次请求的前缀都不一样：缓存全失配、每轮全价重算。反思回边恰恰最吃这个：第二轮调用里除尾部多一条错误回灌，其余前缀与第一轮逐字相同——冻结示例让第二轮只付"新增 token"的钱。动态示例的收益（示例与问题更相关）在"3 条覆盖三类形态"的固定示例面前很小，代价（缓存全失+行为不可复现）很大。

```text
伪代码 — app/agents/text2sql/nodes/verify.py:verify_result（m7；签名=设计稿 00 登记表 m7；空/错→结构化错误回灌）

_MAX_ATTEMPTS = 3    # 设计范围：连续 3 次修正仍失败→熔断（W-F7-5）

async def verify_result(state) -> dict:
    执行 = state["result"]                                  # run_query 带回的 ToolResult
    本轮 = {"round": len(state["attempts"]) + 1,             # 轨迹经 reducer 累加——len 即当前轮次
            "sql": state["sql"], "fingerprint": 指纹(state["sql"])}   # 指纹=SQL 规整化文本哈希（主干七/捣乱 B）
    # ── 主干判断①校验分流：ok=False→执行报错族；row_count==0→空结果族；否则通过 ──
    if 执行.ok and 执行.row_count > 0:
        # 分支④校验通过（W-F7-2 终态）：
        await Repository.save_query_snapshot(快照(state))    # m3 公开面（设计稿 04）：问数结果快照（节点副作用，幂等）
        return {"result": {"kind": "answer",
                           "rows": 执行.rows,
                           "解释": 经 m2 生成(结果摘要),      # 读数翻译成业务话：上月日产油量最高的三口井是……
                           "图表建议": "柱状图：横轴井名、纵轴日产油量"},
                "attempts": [{**本轮, "verdict": "通过"}]}
    if not 执行.ok:
        错误 = {"error_code": 执行.error_code,             # m8 三分法结构化错误码（设计稿 12 主干四）
                "message": 执行.content,                   # 数据库报错原文（如 Unknown column 'oil_rate'）
                "hint": f"可用表结构：{摘要(state['tables'])}"}   # ★ 把正确列名的线索一并带回（见本段末）
        verdict = "失败"
    else:
        错误 = {"error_code": "empty_result",              # 分支②空结果：查询合法但零行——错误语义不同：
                "message": "查询成功但返回零行——检查时间范围与表选择是否过窄",   #   怀疑过滤条件/选表，不是 SQL 语法
                "hint": f"命中的表：{表名清单(state['tables'])}"}
        verdict = "空结果"
    # ── 异常三层之第二层（权限拒）：理由入轨迹，零重试——回灌重试改变不了权限 ──
    if not 执行.ok and 执行.error_code == "permission_denied":
        return {"result": {"kind": "answer", "text": 执行.content},   # 拒绝理由作为正常应答出图
                "attempts": [{**本轮, "verdict": "权限拒"}]}
    # ── 主干判断②无进展检测（捣乱 B）：本轮 SQL 指纹与上一轮相同——回灌也教不会，提前熔断 ──
    上一轮 = state["attempts"][-1] if state["attempts"] else None
    if 上一轮 and 上一轮["fingerprint"] == 本轮["fingerprint"]:
        return {"result": 熔断话术(state["attempts"] + [{**本轮, "verdict": "无进展"}]),
                "attempts": [{**本轮, "verdict": "无进展"}]}
    # ── 主干判断③重试上限闸（W-F7-5）：含本轮已达 3 次——熔断转人工（异常三层之第三层判据，本节兑现）──
    已试 = state["attempts"] + [{**本轮, "verdict": verdict}]
    if len(已试) >= _MAX_ATTEMPTS:
        return {"result": 熔断话术(已试),                  # 话术含已试轨迹摘要：人工接手有完整现场
                "attempts": [{**本轮, "verdict": verdict}]}
    # ── 异常三层之第一层（可纠正）：结构化错误回灌，条件边回生成（主干七）──
    return {"error": 错误, "attempts": [{**本轮, "verdict": verdict}]}   # ★ 单元素列表→reducer 追加（主干一）
```

**为什么结构化回灌比"你错了重来"有效**：模型自纠靠的是**新信息**——回灌内容 = 报错原文（哪列不存在，数据库自己说了）+ hint 里的正确 DDL（正确的列名就在眼前），第二轮是"读题改错"；"你错了重来"零新信息，模型只能从同一分布里重新采样，最坏同一错 SQL 连环（捣乱 B 就是它的实录）。形状对齐 m8 回灌契约（role:"tool" + JSON）还有一层协议语义：这是工具侧报错、有据可查，不是用户在指责——模型该做的动作是"按工具反馈修正参数"。锚 原书 §5 的原文判断：工具层错误不终止会话、把错误变成模型的输入，喂回的错误越具体，自我纠正的成功率越高。

## 关键判断的取舍记录

1. **用 LangGraph 显式状态机，不用"能循环的 Chain"或提示词软约束**——三件 Chain 给不了的东西：**状态归属**（State 是图的一等公民，reducer 在键上声明合并语义，节点只交部分更新——循环多轮后"谁写了什么、怎么合并"可追溯可声明）；**持久化**（checkpointer 按 thread_id 存 super-step 快照，断点续跑与设计稿 15 审批挂起都站在它上面，Chain 的循环状态活在一次调用的内存里）；**人在回路**（interrupt/Command(resume) 是官方原语不是应用层补丁）。加上 LangGraph 官方教程的论据：预置 agent 靠 system prompt 约束"先查表再执行"，LangGraph 把每步拆成专用节点**强制**执行顺序——本节的信息不足闸同理是图路径（goto=END），不是提示词请求。换边条件：单轮、无状态、无审批的纯生成场景，一次 LLM 调用或线性 Chain 足够（锚 原书 §1"从简单到复杂"：能一次调用解决就不要上 Agent 系统）。
2. **错误回灌用结构化 tool 消息（报错原文 + 可用表结构 hint），不用"你错了重来"**——模型自纠靠新信息：报错原文指出哪列不存在、hint 给回正确 DDL，第二轮是读题改错（主干六）；空泛重试零新信息，只能重采样，最坏同一错 SQL 连环——指纹闸因此成为必需的配套（捣乱 B），这是"回灌形状"与"熔断判据"两个设计的耦合点：回灌越具体指纹闸越少触发，回灌偷懒指纹闸就得提前干活。形状对齐 m8 回灌契约（role:"tool"+JSON）保持协议语义一致：工具侧报错，不是用户指责。换边条件：错误码足够细且下游能保证错误自解释时，可降为错误码+文档引用——结构化形状不变。
3. **attempts 用 `Annotated[list, add]` 追加轨迹，不用 int 计数、也不靠节点读改写**——int 也官方支持（`Annotated[int, add]`），但消费方要的不只是总数：指纹检测读上一轮 SQL、转人工话术附已试轨迹、排障看每轮判定，列表轨迹一次满足三个消费方。也不把"怎么合并"散进节点（各自读 state 再写 attempts+1）：两个节点同写就互相覆盖，并行写被官方直接拒绝——reducer 把合并语义声明在 State 一处，这是"状态归属图"的具体含义。付出：轨迹随轮数线性涨（上限 3+熔断，有界）。换边条件：轮数上限大幅放大（几十轮级）时才需要轨迹裁剪策略进 State。
4. **熔断判据住 verify_result、路由函数保持薄；转人工话术作为正常 result 出图，不抛异常**——备选：判据与话术全塞 route_after_verify。不选：卡面把"attempts≥3 熔断转人工"写在 verify_result 注释里；路由函数保持纯函数（只读 result 有无）可单测可复现；话术要拼已试轨迹（写逻辑），混进路由会让它变成第二个业务节点。话术走 result 而非异常：转人工是**正常终态**（用户收到一句人话+现场摘要），错误帧语义留给真故障（网关全败、schema 集合空）——两族失败的用户观感与监控口径都不同。换边条件：终态种类增多（部分成功/降级应答）时，给 result.kind 加枚举而非加路由分支。

## 锚点对照精要

**docs/tech-stack/langgraph.md · 官方 SQL Agent 教程节点同构**（卡 `m7` 锚点 K-A/K-E）
文：官方 SQL Agent 教程节点为 list_tables→call_get_schema→get_schema→generate_query→check_query→run_query，run_query→generate_query 回边构成修正回路，并在 SQL 执行前用 interrupt 做人工审核；预置 agent 靠 system prompt 约束行为，LangGraph 拆专用节点可强制工具调用、控制度更高。落点：六节点与该教程一一同构（澄清+选表≈list_tables/call_get_schema、generate/check/run 对应同名环节、verify→generate 回边≈修正回路）；差异两点——反问澄清闸在图首（官方教程无）、熔断判据在节点+路由（官方靠 recursion_limit 兜底）。

**docs/tech-stack/langgraph.md · StateGraph/reducer/checkpointer/节点幂等**（同锚）
文：reducer 决定节点返回值如何合并进状态、默认覆盖；自定义 reducer 用 `Annotated[list, add]`；checkpointer 在 super-step 边界保存线程状态（InMemorySaver 开发/PostgresSaver 生产，线程经 configurable.thread_id 定位），无 checkpointer 则无法 interrupt/恢复；节点中断恢复时**从头重跑整个节点函数**，副作用必须设计为幂等。落点：主干一/二是这三条的逐条落形——本节唯一可变成本键（attempts）恰好押在 reducer 语义上：覆盖还是累加，决定重试上限闸是否存在。

**docs/tech-stack/langgraph.md · recursion_limit 与 Command**（同锚）
文：recursion_limit 是 config 顶层键（1.0.6 起默认 1000，超限抛 GraphRecursionError），防死循环；`Command(update=..., goto=...)` 在节点内合并"状态更新+路由"，`Command(resume=...)` 是唯一可作为输入的 Command 模式。落点：反问闸出口用 Command(goto=END)（卡面只点名 route_after_verify 一条条件边，闸收进节点、布线保持卡面）；recursion_limit 是熔断之后的官方兜底，自研上限 3 次远小于默认 1000 步。

**原书 §1 · ReAct循环**（卡 `m7` 锚点 K-A）
书：ReAct=思考→行动→观察三环节循环，想→做→看不断重复直到任务完成；Agent 的上下文=静态前缀（系统提示词+工具定义）+轨迹（用户消息/模型回复/工具结果，随交互增长）；轨迹结构化让系统易于解释和调试。落点：反思回边是"做→看→再做"的结构化形态——但轨迹不打转在消息历史里，而是摊开在 State 七字段上（sql/error/attempts 各归其位），attempts 列表就是"试过什么"的轨迹账本；generate_sql 的冻结前缀对应"静态前缀"，错误回灌对应"观察入轨迹"。

**原书 §1 · 编排模式**（卡 `m7` 锚点 K-E 编排状态机）
书：工作流=通过预定义代码路径编排 LLM 与工具、执行路径确定性，优势是严格流程控制与安全（提示注入或模型犯错最多影响当前节点内部）；自主 Agent 需要明确停止条件（任务完成/最大迭代次数/不可恢复错误），否则死循环或过度执行；实践常混合使用。落点：问数是混合形态——六节点拓扑与流转是代码写死的（工作流），修正轮里"怎么改 SQL"由模型读错误自决（自主成分），attempts≥3 与指纹闸就是书里的显式停止条件。

**原书 §5 · 故障四层分类与恢复分级**（卡 `m7` 锚点：原书故障四层分类与恢复分级）
书：故障按位置分 API/工具/上下文/控制流四层，工具层最危险的一种是"工具反复返回同一错误而模型不加改变地反复重试"；工具层错误不终止会话、把错误变成模型的输入——喂回的错误越具体，自我纠正成功率越高；检测要看模式——对"工具名+参数"算重复调用指纹，相同指纹反复出现即无进展循环；终止层面每条恢复路径都要有上限，阈值来自生产统计而非拍脑袋（书例：连续 3 次是"绝大多数已恢复"与"继续基本无望"的经验拐点）。落点：结构化回灌=第一条；SQL 规整哈希即指纹闸=第二条；attempts≥3=第三条（熔断转人工即"升级人工"分级）。
