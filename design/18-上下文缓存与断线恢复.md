```text
伪代码 — app/api/chat.py:断点续推（m1 断点续推分支的私有 helper；主干判断/数据变形/异常去向三层不省）

async def 断点续推(thread_id, last_event_id) -> 事件帧序列:
    try:
        frames = await EventBuffer.replay_since(thread_id, last_event_id)
        # m4 公开接口（设计稿 02 主干三）：XRANGE min="(游标" max="+"——
        #   "(" 排他下界 → 严格大于游标：已收帧一帧不发（不重）；ID 升序返回 → 补发天然保序（不乱）；
        #   ReplayGap / CacheUnavailable 两个结构化异常都从这层出来（设计稿 02 契约）
    except ReplayGap:                                   # 异常去向①：游标早于 MAXLEN 裁剪窗口（捣乱输入 A）
        yield 帧("error", {"code": "replay_gap", "recoverable": True,
                           "message": "会话中断较久，部分内容已过窗口，请重新提问"})
        # 不静默续推（不从最早存活帧冒充断点）、不静默发空（不冒充"没丢"）——话术显式关流；
        # 控制话术帧不过缓冲：与 internal_error 同类，端点侧帧无续推意义、不占裁剪窗口
        return
    except CacheUnavailable:                            # 异常去向②：缓冲不可达——宁可重问，不冒领"已续上"
        yield 帧("error", {"code": "replay_unavailable", "recoverable": True,
                           "message": "断线恢复暂不可用，请重新提问"})
        return
    for f in frames:
        yield f                                         # 补帧 18..N 逐帧过线（帧自带 id，游标自然推进）
    if frames and frames[-1].event not in ("done", "error"):
        # 主干判断：补发尾部无终态帧 = 生成侧已随旧连接断开被取消（设计稿 01 取消语义：检测到断开即停，
        # 每帧都是算力钱，不为死连接续跑）→ 缓冲里就只有这些帧
        yield 帧("error", {"code": "replay_truncated", "recoverable": True,
                           "message": "回答在断线时被截断，请重新提问"})
        # 显式截断通知优于静默关流（前端无从判断"完了没有"）；也优于补发后续接重生成（取舍 3）
    # frames 为空（游标恰为末帧，如断线发生在 done 之后）：不补任何帧、流即关——
    # "没有要补的"是合法结局，客户端手里已有完整回答
```

```text
t5  尾部含 done → 截断分支不触发 → 流自然关。第三问的落库与覆盖回填在 t1 已完成
    （先库后缓存），所以第四问无论冷热缓存，历史里都有第三问——
    上下文缓存管"下一问记得"，事件缓冲管"这一问不丢"，两套机制各管一摊
```

对照支线（检测到的断开）：若断开被服务端察觉（客户端主动断开/代理超时发 RST），设计稿 01 取消语义生效——CancelledError 注入最近 await 点，生成协程终止，缓冲止于取消前最后一帧。此时重连补发的尾部无 done，`replay_truncated` 话术显式收场——不静默、不重生成（取舍 3）。

### 捣乱输入 B：缓存与库不一致——双写顺序取舍与最终一致窗口

三个不一致现场各走一遍（时序推演）：

```text
伪代码（时序推演，非代码）

【现场一：并发赛跑，迟到回填盖新值】（设计稿 02 捣乱 A 的会话侧复现）
t0  请求甲读上下文 miss → 回源读库得 v1（2 轮）——回源耗时中
t1  请求乙第三问收尾：save_chat_turn 落第 3 轮（库=v2）→ Cache.set(v2, ex=300) 覆盖回填
t2  请求甲的回填迟到：Cache.set(v1, ex=300) —— v1 盖掉 v2，脏读窗口在此刻闭合
t3  窗口有界：最多存活到 TTL（≤300 秒）过期，或下一次写路径覆盖回填——先到者收口
t4  表现：窗口内的提问拿到少一轮的历史，模型"忘了刚才说的 F-1 井"——
    追加型上下文可容忍缺最后一轮（不产生错乱，只产生遗忘）；不启用延迟双删（取舍 2）

【现场二：写库失败（双写断一半的第一种）】
t0  第三问收尾：save_chat_turn 抛 PersistenceError（连接池超时/约束冲突）
t1  收尾双写段捕获：缓存不覆盖 → 缓存与库此刻一致地旧（都少这一轮）
t2  对账：本轮问答只存在于"已送达客户端的帧"里；对账日志留痕（thread_id+seq 可定位缺口）
t3  最终一致：TTL 过期后回源，回源的也是旧值——上下文"连续地"少这一轮，
    不会出现"过了 5 分钟突然忘一轮"的翻转怪象
t4  反例对照：若此刻仍覆盖缓存（cache=v2、库=v1），缓存过期后回源翻回 v1——
    同一轮内容"先记得、后蒸发"，比稳定遗忘更难解释；库是真源（取舍 2 的核心）

【现场三：写缓存失败（双写断一半的另一种）】
t0  第三问收尾：save_chat_turn 成功（库=v2）→ Cache.set 抛 CacheUnavailable（Redis 不可达）
t1  捕获后忽略：库已提交=真源无损；加速失效只损失下一问的命中
t2  自愈：Redis 恢复后下一问 miss → 回源 v2 → 回填——无需任何补偿动作
```

一致性的总结账：**先库后缓存 + 覆盖回填 + TTL 封顶**——双写断在任何一半，状态都向"旧值"收敛（丢账可对账补、不产生脏账）；双写全成时的脏窗口（现场一）被 min(剩余 TTL, 下一次写) 有界化。备选顺序"先缓存后库"的病在 t4 对照行：失败方向不收敛，缓存会短暂承认库不承认的数据。

## 关键判断的取舍记录

1. **自增编号只在 EventBuffer.append 出口一处生成；Last-Event-ID 类型取 str 的对账。** 会话内事件编号必须 三处同值：SSE `id:` 行（客户端凭它回传）、缓冲条目（重放凭它排他）、游标比较（缺口判定凭它）——编号在任何第二处生成（主循环计数器、端点拼装）都会造出"有号无帧/有帧无号"的第三态，重放就重不对齐。`XADD … *` 的流 ID（毫秒-序号，同流严格递增）让编号与帧在 append 这一个出口**原子地**同时出生，设计稿 17 帧出口再把它与出帧绑定——三态不存在。连带决定：客户端回传的 Last-Event-ID 就是这个含 "-" 的复合串，故端点头类型取 `Annotated[str | None, Header()]`——官方教程行与 W-F1-4 走查列的 `int` 字样与缓冲真形冲突，本设计稿按机制真形写并记录对账（若对账后坚持 int，代价是给缓冲自造纯数字单调源，放弃流 ID 天承担，见取舍 1 开头的三处同值约束）。降级自洽：append 失败 id=None → id: 字段省略 → 客户端游标不动，续推分支天然不触发；代价是降级窗口内的帧无号亦不可补（在线推流优先的已知损失，设计稿 17 取舍 4 同源）。换边条件：换非 Streams 的缓冲实现（内存环等）时才需要自造单调源。
2. **双写顺序=先库后缓存，覆盖回填，失败向旧值收敛。** 库是会话历史真源（卡 `m3`），缓存只是 TTL 生命期内的加速副本——副本断供的损失上限是"多查一次库"，真源断供的损失是"历史永久缺轮"。备选"先缓存后库"：缓存先承认了库不承认的数据，断一半时出现"记得又蒸发"（捣乱 B 现场二 t4）。半败走"不覆盖"而非"补偿重试"：收尾段在用户答案已送达之后，重试只会拖慢 done；丢账用对账日志兜底。加强选项"延迟双删"备而不用（专清迟到回填，代价多一次写+延迟调度）——追加型上下文可容忍缺最后一轮；若业务要求上下文强一致，在卡 `m4` 补失效接口后启用（设计稿 02 同款纪律，不在设计稿层私扩公开面）。
3. **重连分支只补发、不续跑、不重生成。** 补发尾部含 done 时若续接重生成，同一回答双份送达双份计费；尾部无 done 说明生成侧已被取消（设计稿 01 取消语义是有意设计：每帧都是模型算力真金白银，不为死连接续跑），此时显式 `replay_truncated` 话术优于静默关流（前端无从判断是"完了"还是"断了"）。备选"断线继续生成、结果全存缓冲待任意时刻来取"——那等于把问答链改造成问智式异步任务（生成与连接彻底解耦，worker 化），是架构级变更，且"生成期间用户已走远"的场景里模型算力照烧；若产品真要"离开再回来答案还在"，正路是问智模式的异步化，改模块卡。换边条件：token 单价降到可忽略、或问答链本身 worker 化时，重连分支可升级为"补发+续推活任务"。
4. **缓存 TTL 与会话长度解耦：固定 300 秒滚动保鲜，不随会话长度走。** 会话可以活数小时："TTL=会话长度"意味着每个活跃会话的全量历史常驻 Redis（内存占用随会话数×历史长度无界增长），且脏读窗口随会话变长而放大（捣乱 B 现场一的窗口=TTL）。短 TTL 的账：活跃会话（提问间隔<5 分钟）靠每次覆盖回填重置 `ex=` 滚动保鲜，全程命中零回源；闲置会话过期，下次提问付一次毫秒级回源重建——回源成本（一条 selectinload 查询）与内存占用相比便宜得可以定期重付。换边条件：回源变贵（历史带大体积引用、或上下文压缩后仍巨大）时，先延长 TTL 并配容量上限，再不行才考虑"缓存写穿+事件失效"的强一致方案。

**docs/tech-stack/redis-minio.md · Streams 流 ID 与 XADD "*"——断线重连的编号来源**（卡 `m4` 锚点：XADD/XREADGROUP/XACK/XAUTOCLAIM）
文：Redis Streams 官方形状 `XADD key [MAXLEN ~ n] * field value`——`*` 自动生成 ID（毫秒-序号），MAXLEN≈ 裁剪防无限增长。落点：断点续推的游标就是这个自动 ID，设计稿 02 已定形"不自己维护计数器，流 ID 天然承担"；本节把它接到 SSE `id:` 行与 Last-Event-ID 回环上（取舍 1 的"一处生成"即站在这条官方语义上）；`_id_gt` 的数值序比较（设计稿 02 交付）是缺口判定不漏闸的前提。

**docs/tech-stack/redis-minio.md · 官方无缓存抽象——cache-aside 应用层自封**（卡 `m4` 锚点）
文：调研结论明记，redis-py 本体只提供裸命令客户端（get/set 带 `ex=` TTL、SET NX EX 锁形状），未检索到官方 cache-aside helper，缓存模式需应用层自行封装。落点：Cache 三函数是设计稿 02 对裸命令的最薄封装，miss 回源与降级直读两个分支一直留在调用方（m4 叶子卡不 import m3）——本节就是在调用方把这两个分支接上主循环（主干 A），回填用一条 `SET ex=` 原子带 TTL 亦是设计稿 02 已锁的机制。

**docs/tech-stack/fastapi-sse.md · SSE 断连生产解法：Last-Event-ID + ServerSentEvent id 字段**（卡 `m1` 锚点；设计范围框架红线）
文：FastAPI 0.135.0 起原生 SSE——`ServerSentEvent(data/event/id/retry/comment)` 控制 SSE 各字段；断线续传的官方解法是读 `Last-Event-ID` 请求头（`Annotated[... , Header()] = None` 形状）从上次位置重放；15 秒 keep-alive ping comment 防代理断连、防缓冲头开箱即用不手写。落点：主干 B 的读头与 id: 写线逐点对位——生产解法的两半（客户端回传游标、服务端按游标重放）分别落在端点头参数与断点续推 helper；头类型 str 与教程行 int 的差异已在取舍 1 对账。

**docs/tech-stack/fastapi-sse.md · StreamingResponse 取消坑点——续推机制的另一半**（卡 `m1` 锚点）
文：流式生成器内必须有 await（哪怕 `await anyio.sleep(0)`），否则客户端断开时无法取消，流可能继续跑。落点：检测到的断开→取消→缓冲止于取消前（replay_truncated 分支的前提）；反向的机制事实也在这条坑点里——静默断网（无 FIN/RST）服务端写而不觉，取消不触发，帧继续落缓冲，这正是主干 B 主走线"断网 30 秒补到完整回答"的成立条件；两端点每轮 await 的铁律（设计稿 01）本节零改动继承。

**原书第二章 §Agent如何调用大模型 · 无状态与消息结构**（卡 `m13` 锚点）
书：API 每次调用无状态，模型不记忆历史，Agent 框架必须每次把完整消息列表送回。落点：历史供给位是主循环的刚需而非优化项——没有它第三问的"刚才的 F-1 井"无从谈起；cache-aside 省的是回源的数据库查询，不是模型的 token 账（每轮 Gateway.chat 仍全量重送 messages，KV Cache 语义见设计稿 16——本节的"缓存"与会话上下文缓存是两层，别混）。
