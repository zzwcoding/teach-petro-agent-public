### 主干一：四步法逐步推演（StarModel.design 的步序即纪律）

```text
伪代码 — app/modeling/grain.py:StarModel（m20；签名=卡 m20；纯内存，同步）

class ModelSpec:                 # 数据形状——四步走完的建模产物
    process: str                 # 步 1 产物：业务过程名（"daily_metering" 日产计量）
    grain: GrainSpec             # 步 2 产物：粒度声明（协议对象，不是事后补的字符串）
    dimensions: [DimSpec]        # 步 3 产物：维度清单（井/日期）
    facts: [FactSpec]            # 步 4 产物：事实度量清单（产液/产油/压力）
    形状: "star"                 # 星型形状自证：事实居中、维度为辐条（Kimball Ch5 §The star schema）

class DimSpec:                   # 维度描述——主键 + 属性清单（层级拍平 + 可读属性）
class FactSpec:                  # 事实描述——度量清单（含可加性标注）+ 外键清单（指向维度）

class StarModel:
    def design(self, process) -> ModelSpec:
        # 四步法：业务过程→grain→维度→事实（Kimball Ch5 §Designing a dimensional model
        # in four steps 原序——"This is done iteratively"，迭代的是过程数量，不是步序）
        步 1: 选业务过程     # 一次只选一个（见下）；process 不是"一个主题域"，是"一次可计量的业务事件"
        步 2: 断言粒度已声明 # 🛡️ GrainProtocol.断言已声明(事实表)——未声明在此止步（主干二）
                            #     不是"先建维度后补声明"：步序即纪律
        步 3: 定维度         # 从过程量出 who/what/where/when → 维度候选；层级拍平、代码配可读文本
        步 4: 定事实         # 只收数值度量与维度外键；全表同粒度；文本上下文退回维度
        return ModelSpec(process, 步2.grain, 步3, 步4, 形状="star")
```

**步 1 选业务过程——为什么一次只选一个**（Kimball Ch5 §Defining business processes to model 原话："The dimensional model strives to describe these business processes one at a time… Selecting one business process helps to delimit a specific design objective and makes choosing a level of grain easier"）：一次只选一个，粒度才有唯一答案。油田生产库 8 表天然是过程清单（设定书 §A.1–A.8）：日产计量（§A.2）/注水（§A.3）/检修（§A.4）/措施（§A.5）/化验（§A.6）/设备状态（§A.7）/月度结算（§A.8）。反例先行：把采油和注水挤进一张"生产总表"——注水行没有产油、采油行没有注入量，列一半是空，grain 直接打架（注水事件的"每行"是井×日注水量，计量事件是井×日产液产油——两个测量事件两种表）；今天的答案是**只选"日产计量"**（设定书 §A.2 ★核心事实源，采集谱系=日度，提取件一 §二）。

**步 2 声明粒度——原子粒度优先，"罐装货选一罐"落地油田**（Kimball Ch5 §Finding the grain）：grain 就是"每行是什么"，它必须**先于**维度与事实被声明（原话见锚点精要）。原子粒度优先（原话："Starting with atomic-grained data is highly recommended, taking the data to the finest level possible at which the chosen business process captures data"）。罐装货原文（Kimball Ch5 §Finding the grain）：供应商给超市送罐装货，粒度可以是托盘（pallet）、批次（batch）或六连包（six-pack），但要支持所有聚合，就用原子单位——**一罐**（one can）。落地油田：日产计量的最细记录是"单井·日"计量行（提取件一 §1.1：产油量计算粒度=单井（日）/区块（月）/油田（年）——单井日是最细一级的油田证据），故 grain=**井×日**（设定书 §A.2 PK well_id+prod_date 的既成形状，本节升格为协议声明）=油田的"一罐"；月·区块·油田报表都是换装筐（走查推演 2）。

**步 3 定维度——给度量补上下文，50-100 属性正常**（Kimball Ch5 §Determining dimensions）：维度表存测量事件的文本上下文，原话是谁/什么/何时/何地/如何/为何（"who, what, where, when, how, why"）。日产计量的答案：who=井（dim_well）、when=日期（dim_date）；where（平台/区块/油田）拍平进井维度。维度属性多不是病，原话："it is not unusual for a dimension table to have 50 to 100 attributes"——本设计 dim_well 只列 8 个（设定书 §A.1 全字段），当前规模不追属性数，追两个设计点：**层级拍平**（井→平台→区块→油田反规范化，取舍 1）与**代码配可读文本**（well_type 的 EW/IW 是分析员看不懂的代码，原话要求"meaningful words rather than codes"，代码与可读描述符并存——EW→"采油井"、IW→"注水井"两个属性并列，设定书 §A.1 well_type 取值）。日期维度 dim_date：date_key/年/月/日——聚合轴，§5 合法 join 白名单点名 oil_production_daily ⋈ date_dim ✓（设定书 §5，日期维度的权威依据）。

**步 4 定事实——事实只存度量**（Kimball Ch5 §Identifying facts）：事实表存业务过程的性能度量，原话三纪律——①"all rows in a fact table must maintain the same level of aggregation or grain"（全表同粒度，防双算）；②"a measurement event in the physical world corresponds to a single row"（物理世界一次测量事件=一行）；③"The most valuable facts are numeric and additive"（数值、可加最值钱）。落地：产液（方）/产油（吨）/油压（MPa）三度量（卡 m20 油田锚定"产液·产油·压力"）全部来自计量事件本身；open_days（开井小时，§4 规则 5 值域 [0,24]）与 plan_output_t（配产，完成率分母）是同事件的伴随度量（设计稿 32 SQL 已在）；班次 report_shift（A/B/C）**不在**事实里——去重后一井一行，班次是清洗期的事（设计稿 32 staging），文本型上下文一律退回维度（Kimball Ch5 原话：textual information's natural place is inside a dimension）。事实表形状：长而窄（long and narrow，Kimball 原话）——行多列少，外键≥2（well_id→dim_well、prod_date→dim_date）即事实表判据（composite key）。

### 主干二：粒度协议本体——未声明建模被拒（W-F17-2 的本体）

```text
伪代码 — app/modeling/grain.py:GrainProtocol（m20；签名=卡 m20；纯内存协议，同步）

class GrainSpec:                 # 数据形状——一次粒度声明的全部内容
    table: str                   # 被约束的模型物名（"fct_daily_metering"）
    grain: [str]                 # 粒度键清单（["well_id","prod_date"]）——"每行是什么"的机器可查形态
    人话: str                    # 同一粒度的业务话术（"一行=一口井一天的一次日产计量"）
    原子否: bool                 # 是否原子粒度——按业务过程量出，不是拍脑袋（主干一步 2）

class GrainProtocol:
    _declared = {}               # table -> GrainSpec（协议台账：只进声明，不进模型）

    def declare(self, table, grain) -> GrainSpec:
        # 🛡️ 立约：把"每行是什么"从嘴上落到纸上（Kimball Ch5：binding agreement on the design）
        if not grain or not table:                    # 捣乱入口 0：空声明不是声明
            raise GrainEmpty()        # 拒——"'回头再定''看着办'不是粒度，粒度是具体到键的承诺"
        if table in _declared and _declared[table].grain != grain:
            raise GrainConflict(table)                # 捣乱入口 1：同表改口
                                      # 拒——改粒度=换这张表的语义，走新表新声明，不许原地偷换
        return _declared[table] = GrainSpec(...)      # 纯登记声明本身，零副作用

    def 断言已声明(self, table):                       # 协议的牙齿——design 步 2 调用
        if table not in _declared:                    # 捣乱入口 2：没立约就想建模
            raise GrainUndeclared(table, 话术=(
                "粒度是'每行是什么'的约束性协议：它约束这张表的每一行必须同义，"
                "维度与事实都要对齐它才成立。这张表还没有 grain 声明——"
                "先 declare（粒度先行），再建模；不声明就建出来的表，谁也说不清"
                "一行算一次计量还是一天算一次，双算与漏算由此而生。"))
```

> **为什么叫"协议"不叫"登记"**：Kimball Ch5 §Finding the grain 原话把 grain 声明称为 "a binding agreement on the design"（对设计的约束性合同）——合同是**约束双方的**（维度与事实的每个候选都要对齐它），不是事后补的台账（台账没人查，协议次次拦）。设计范围 🛡️ 的意义：把"粒度先行"从方法论美德降维成入口闸——美德靠自觉，闸靠拒绝。

```text
伪代码（时序推演，非代码）——捣乱输入 A：先建维度后补 grain——违规路径被拒（W-F17-2）

t0  新同事："维度最好想——先把 dim_well/dim_date 画出来，grain 回头补个登记就行。"
t1  StarModel.design("daily_metering") 起手即走步序：步 1 选过程通过 → 步 2 先问协议：
    GrainProtocol.断言已声明("fct_daily_metering")
t2  协议查 _declared——空 → raise GrainUndeclared，报错话术=上文全文
    （"粒度是'每行是什么'的约束性协议……先 declare，再建模"）——design 在步 2 止步，
    维度与事实一张表都还没画，拒绝发生在形状长出来之前
t3  为什么不"先建后补"（三条，Kimball Ch5 §Finding the grain 逐条翻译成油田话）：
    ① grain 是判据不是备注——维度属性怎么取舍全由粒度裁：井维度要不要放班次 A/B？
      查粒度——grain=井×日，班次被去重掉（设计稿 32），它连属性都当不上；没有 grain，
```

## 关键判断的取舍记录

1. **星型不雪花：维度反规范化、代码配可读文本**。备选：层级拆子表（井→平台子表→区块子表→油田子表，即雪花）。Kimball Ch5 §Determining dimensions 原话是裁决依据——"the modeler should resist the urge to normalize… If we added subtables, the star shape would transform into a snowflake"（忍住规范化的冲动；加子表，星型就变成雪花）。判据：分析查询要 join 少（Kimball review 原话：joins needed gets reduced since relevant data are grouped together）+ 名字要可读（EW 配"采油井"并存）。代价：层级变更要重算维度、行内冗余（§A.1 渤海油田行内冗余在此升格为设计）。真实油田两派并存——提取件一 §二 陈海娜：油厽数仓采用"星形模型与雪花形的混合设计"；本项目取**纯星型**：问数自由聚合时 join 数决定成败，混合设计的复杂度当前规模收不回。换边条件：层级天天变+维度行数爆炸——那时才值得谈混合；与设计稿 32 取舍 5 同向（那里讲 Enrich 层为什么拍平，这里讲建模四步里维度设计的裁决，同一结论两个高度）。
2. **grain 先于维度与事实，且是"协议"不是"登记"**。备选：grain 当元数据登记、建模完成后补录。协议=约束性（binding agreement，Kimball Ch5 §Finding the grain 原话）——未声明即拒，不是"提醒补上"。为什么这么硬：维度取舍与事实取舍**全部以 grain 为判据**（主干二 t3 ①），没有 grain 的建模不是"先做后补"而是"无从做起"；补登记是把约束降级成台账——台账只在审计时翻，协议在 design 入口次次拦。换边条件：无（这是本节灵魂，🛡️ 的意义所在）。
3. **原子粒度优先，不预建聚合表**。备选：按已知报表预建"区块×月"宽表。依据：Kimball Ch5 §Finding the grain（atomic：finest level possible）+§Data reusability（原话："It is always preferable to store non-aggregated data and only perform calculations as needed"）。预聚合赢一次查询快，输在每次新口径都要回源头重算——原子事实天然支持任意聚合；规模账：120 口井×365 日≈4.4 万行/年（设定书 §1），当前规模聚合成本可忽略，秒级 1 万 RTU 是实时库的事（§2.1 五层链路各管一段，不进仓库原子层）。换边条件：某聚合口径被高频消费且原子聚合实测过慢——建聚合 marts（Kimball Ch6 §Enrich Aggregate），原子事实不动。
4. **油压照进事实，标注半可加**。备选一：油压进维度（它是数值不像描述）；备选二：从事实剔除。判据（Kimball Ch5 §Identifying facts）：事实=测量事件的直接测量，油压是日产计量事件当场量出的数（提取件一 §1.5 油压：单井，日——压力类里唯一贴合井×日粒度的）——它是事实；但 SUM 无物理意义（MPa 是强度量），标注半可加（semi-additive，Kimball 原话：analysts must employ counts and averages）——分析侧用 avg/last，求和是错的。剔除更错：压力类指标就挂不上了（§1.5 油压是单井日指标卡）。维度备选一也错：维度属性是约束/分组/标签用（Kimball §Determining dimensions），没人按"油压=3.1 的井"分组后取井清单做主用法。换边条件：无。
5. **一次只建一个业务过程：日产计量先行**。备选：一张"油田生产总表"把采油/注水/检修全装下。Kimball Ch5 §Defining business processes 原话："one at a time… delimit a specific design objective and makes choosing a level of grain easier"——多过程挤一表，grain 直接打架（注水行无产油、检修行无计量，主干一步 1 反例）。注采受效关系（注水井→受效油井多对多、属性=劈分系数 Σ=1，设定书 §5——"业务规则驱动建模"的实证）属于"措施评估"过程的建模素材，**下次选过程时再走四步**（四步法本身迭代：Kimball 原话 "This is done iteratively"）；受效关系的本体登记归 m16 本体域（设计稿 36），本节不碰三域。换边条件：无（新过程=新一次四步，不是老表加列）。

## 锚点对照精要

**Kimball Ch5 §Designing a dimensional model in four steps（四步法原序）**：原文——设计维度模型四决策 "Choosing the business process / Defining the grain / Determining the dimensions / Identifying the facts"，"This is done iteratively"。落点：主干一 design 步序（步序即纪律）与 ModelSpec 四段。差异：原书四步是团队工作坊式迭代（模型组建团队、与业务对齐命名），我们把它固化成 design 的步序协议——步 2 之前不许进步 3，设计收敛点在"顺序"本身。

**Kimball Ch5 §Defining business processes to model（一次一个过程）**：原话——"The dimensional model strives to describe these business processes one at a time with a set of fact and dimension tables. Selecting one business process helps to delimit a specific design objective and makes choosing a level of grain easier." 落点：主干一步 1 + 取舍 5。差异：无实质——油田 8 表就是过程清单的现成版本。

**Kimball Ch5 §Finding the grain（grain 先行与原子优先——本节灵魂）**：原话三段——"Declaring the grain is the same as defining the meaning of each row of one table. It acts as a binding agreement on the design, ensuring consistency and clarity…"；"The grain must be declared before selecting dimensions or facts, as every potential table needs to be in line with the grain."；"Starting with atomic-grained data is highly recommended, taking the data to the finest level possible at which the chosen business process captures data." 罐装货类比原文：粒度可以是托盘/批次/六连包，"if we want to be able to support all of these aggregations, we should use the atomic unit, that is, one can"。落点：主干二协议话术（"每行是什么的约束性协议"逐字对 binding agreement）+ 走查推演 2 托盘/批次/六连包/一罐的油田版 + 步 2 grain=井×日。差异：原书"最细"以业务过程捕获数据的最细级为准——油田的"最细"证据是提取件一 §1.1 计算粒度谱系（单井（日）为产量类最细），故"一罐"=井×日而非传感器秒级读数（那是实时库，§2.1，另一个过程）。

**Kimball Ch5 §Determining dimensions（维度=上下文，反规范化警示）**：原话四点——维度存 "who, what, where, when, how, why" 的文本上下文；"it is not unusual for a dimension table to have 50 to 100 attributes"；"dimension tables are usually denormalized using many-to-one relationships. If we added subtables, the star shape would transform into a snowflake."（含 "resist the urge to normalize"）；代码应换成可读词，须保留的代码"应与用户友好的文本描述符并列成不同属性"（codes displayed as distinct dimension attributes alongside the corresponding user-friendly textual descriptors）。落点：主干一步 3（who/when 出井/日期维度、where 拍平、EW↔采油井并列）与取舍 1。差异：原书 50-100 属性是常态，本设计 dim_well 8 属性——当前规模不追属性数，追"层级拍平+可读并列"两个设计点。

**Kimball Ch5 §Identifying facts（事实三纪律与形状）**：原话——"all rows in a fact table must maintain the same level of aggregation or grain. Creating fact tables with a singular level of detail helps avoid the inaccurate double-counting of measurements."；"The most valuable facts are numeric and additive. The fundamental principle of dimensional modeling is that a measurement event in the physical world corresponds to a single row in the related fact table."；事实可半可加/不可加，此时用计数与均值；"Fact tables are usually long and narrow"；外键≥2、复合键即事实表判据；"Fact tables embody many-to-many relationships, whereas all other tables are deemed dimension tables." 落点：主干一步 4（三主度量+伴随度量、班次退场、长而窄）+ 主干二捣乱 B（单一粒度防双算）+ 取舍 4（油压半可加）。差异：原书事实三分法（transaction/periodic snapshot/accumulating snapshot）只点不展开——日产计量属 periodic snapshot（周期快照：每日计量一次），本设计一句带过。

**Kimball Ch5 §The star schema（星型形状与可扩展性）**：原话——"Its simple shape resembles a star with the fact in the center and the dimensions in the point ends"；可扩展性："new facts can be introduced to the model as long as their granularity is consistent with the rest of the fact tables in the existing model"（新事实随粒度一致即可添）、加维度只要每行事实表能定位到该维度唯一值。落点：ModelSpec 形状="star" 自证 + ASCII 画法 + "更多维度随过程添"注记。

**Kimball Ch5 §Ralph Kimball and dimensional modeling / §Choosing a data model（为什么分析世界选 Kimball）**：原话——Kimball 把维度建模整理成数仓主流技法；"The dimensional model or star schema is more suitable for analytical purposes, such as drilling down on data, generating reports, and performing aggregations or calculations"；3NF 适合事务系统（"to analyze normalized data, one may have to perform lots of joins"）；"the snowflake schema that is derived from the star schema"（雪花是星型的派生）。落点：取舍 1/3 的背景——星型 vs 雪花 vs 3NF 的适用边界。差异：原书还有 Inmon 3NF 与 Data Vault 两路，本项目 m20 职责=AE 世界观载体（卡面原文），两路只作取舍背景不展开。

**提取件一取材对账**：§1.1 产量类（产油量计算粒度=单井（日）/区块（月）/油田（年）——"最细一级"的油田证据，锚定步 2 与走查推演 2；产水量=水驱关键指标——产液/产水量伴随度量的佐证）；§1.5 压力类（油压"单井，日"MPa——三主度量之一贴 grain 的证据；压力恢复速度 d(P)/dt 为"区块/油藏"粒度——捣乱输入 B 的对照组）；§二 采集与数据链路（日度采集谱系=A2 生产日数据——步 1"计量事件=日"的链路佐证；陈海娜"星形模型与雪花形的混合设计"——真实油厂数仓建模现状，取舍 1 的行业对照）。

**设定书取材对账**（取材锁）：§2.2（8 表字典入口+单位换算表——产油吨是设计稿 32 staging 折算出口的既成口径）；§3 指标 1（产量完成率公式与粒度=月/区块·油田——走查推演 2）、指标 14（抽油机时率——open_days 挂载例）；§5（合法 join 白名单 oil_production_daily ⋈ date_dim ✓ / ⋈ fluid_test ✗——日期维度权威依据与捣乱 B 裁决；受效关系劈分系数 Σ=1——取舍 5 的"下一个过程"素材）；§3 指标挂载与 §5 受效关系两条均已落（受效关系按边界只作业务素材不讲本体域）；§A.1（井维度属性与层级、EW/IW 与 current_status、行内冗余注记）；§A.2（grain=井×日 的主键证据、★核心事实源、班次/双值行/open_days 值域素材）；§A.3/A.4/A.5（注水/检修/措施=候选业务过程清单）；§A.6（化验频次不齐——捣乱 B）；附录 A 头（:block_name 兼容注记——走查推演 2 t4 已备案）。本设计稿业务事实全部落在上述清单内，无凭空发明。
