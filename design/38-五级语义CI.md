### 主干一：validate_change 总装——五级判定序与 gate_report 形状（本设计稿灵魂的骨架）

```text
伪代码 — app/eval/semantic_ci.py:SemanticCI（m18；签名=卡 m18 版本 3 扩容节逐字）

class GateReport:               # 数据形状——门禁裁决的最小单元（设计范围硬性红线：级/项/结论/修法 四元组）
    级: str                     # "L1".."L5"——五级命名逐字取方案节（锚 DataBuddy 五级语义 CI 全表，
                                #   AE 前沿方案报告：L1 Schema 合法性→L2 引用与本体一致性→
                                #   L3 指标/SQL/安全→L4 治理/权限/兼容→L5 行为与检索回归）
    项: str                     # 判据名："缺 owner"/"闭包断裂"/"循环引用"/"废弃引用"/"只读"/"粒度声明"/
                                #   "零分母保护"/"参数化"/"Owner 审批"/"敏感字段"/"破坏性变更"/"golden 全量"/"负样本"
    结论: str                   # "绿" | "红"；L5 试验级透传设计稿 23 三出口：绿/红/不确定（不确定不算绿，转人工）
    修法: str                   # 可执行建议 + 收件人（谁改）——设计稿 24 fix_hint 收件人纪律：修法给到能改的人手里
                                #   （Owner 路由按设定书 §1 责任链：产量口径→开发室/措施→采油工艺所/
                                #   经营→销售计量站/平台语义→阿强+数据管理岗），不给"请检查"式空话

class SemanticCI:
    def __init__(self, 指标注册表, 术语注册表, 本体注册表, golden_store, redteam_cases, repository):
        # 依赖全部是公开面注入：m16 三域注册表（L2 引用对账 + L4 治理字段读取——只读，防环纪律）；
        # GoldenStore + RedteamCases（L5 回归素材，m18/m19 公开面）；m3（gate_report 与裁决留痕落库）
        ...

    async def validate_change(self, change) -> [gate_report]:
        # ★ 判定序是卡面注释锁死的：L1 → L2 → L3 → L4 → L5，签名里没有"选级"参数——
        #   跳级在接口上不可表达（同设计稿 23 "字符串比对在接口上不可表达"的论证法，捣乱输入 B 的结构半边）
        报告 = []
        报告 += await self._L1_结构合法(change)
        if 本级有红(报告):
            return 报告                  # L1 红短路：结构都不合法，L2+ 的对账无从谈起（对账对象不存在）
        报告 += await self._L2_引用一致(change)
        报告 += await self._L3_指标模板与安全(change)
        报告 += await self._L4_治理(change)
        if 本级有红(报告):
            return 报告                  # L2-L4 有红不进 L5：静态检查便宜（纯读内存），L5 跑批贵
                                         #   （每案例一次问数链公开入口调用）——贵闸永远最后，且只在便宜闸全绿后烧
        报告 += await self._L5_行为回归(change)
        await self._repo.save_audit({"类型": "五级 CI 裁决", "变更包": change.id,
                                     "结论": "放行" if 全绿(报告) else "打回", "红项数": 数红(报告)})
        return 报告
        # 裁决语义（本设计稿交付物）：放行 = 五级全绿 **且** Owner 审批已带（审批证据在 L4 判过）；
        #   任一红 = 打回，报告即修法清单。发布动作（写回+重载）不在本卡——CI 只裁决不发布，
        #   流转归设计稿 43（卡 m18 mr_flow 注释："合并 = SemanticCI 全绿 + Owner 审批"）
        # 异常去向：m16 注册表未装载/变更包为空 → 结构化上抛（装配缺失非门禁红）；L5 被评链故障
        #   → 该案例记"执行失败"行并计红（跑不出证据=放不了行，fail-closed 与设计稿 36 白名单同哲学）
```

**为什么级内逐项不短路、级间才短路**：L2 的三病、L3 的四病常常同源于同一份 AI 起草稿——只报第一处，提交人修一处跑一遍门禁再撞第二处，来回跑闸比闸本身还耗治理带宽（门禁的产能是稀缺资源：每次全量 L5 都是真金白银的跑批）。所以便宜级（L1-L4，纯静态读）一次报全修法清单；贵级（L5）只在前面全绿后才进。短路点只有两个：L1 红（后续无对象可查）与进 L5 前（贵闸前置条件）。**捣乱输入 B：能不能"只跑 L5，前面省了"——跳级**

```text
伪代码（时序推演，非代码）

t0  有人提议："L5 是真回归最狠的一级，直接跑它不就行了？前面三级是手续。"
t1  三个层面的否决：
    接口层：validate_change(change) 签名只有变更包一个参数，没有"选级"开关——跳级在接口上不可表达；
```

### 主干二：L1 结构合法——收编 v2 装载闸，语义不回退（W-F20 的第 0 级）

```text
伪代码 — app/eval/semantic_ci.py:SemanticCI._L1_结构合法（m18 私有件；判据=设计稿 22 装载闸同名收编）

    async def _L1_结构合法(self, change) -> [gate_report]:
        报告 = []
        for 文件 in change.diff:                     # 变更包=diff 文本清单（每文件：路径+新文本全文）
            raw = yaml.safe_load(文件.新文本)
            #   ↑ 收编第 0 条：safe_load——口径/术语/本体文件"是数据不是代码"（设计稿 22/35/36 同一纪律），
            #     门禁装载变更文本用同一把锁，不因"只是检查一下"降低装载纪律
            报告 += 逐条判([
                必备字段齐(raw),                     # 收编第 1 条：八字段齐（设计稿 22 装载闸原文判据）
                owner 非空(raw),                     # 收编第 2 条：无主资产不得生效（设计稿 22 捣乱 B 的闸）
                status_in_权威态(raw),               # 收编第 3 条：approved 才收——权威目录无非审定文件
                                                     #   （glossary 侧收编 {approved, deprecated} 两态，设计稿 35）
                version 为正整数(raw),               # 收编第 4 条
                模板首词 SELECT 初检(raw),            # 收编第 5 条：完整性初检（真闸在 L3，此处只查形状）
            ], 级="L1", 文件=文件)
        return 报告
        # 收编声明（本主干的存在意义）：L1 的判据集 = v2 装载闸（MetricRegistry.load / GlossaryRegistry.load /
        #   OntologyRegistry.load 的校验段）逐条同名——**L1 是装载闸的超集闸，语义不回退**：
        #   同一份缺 owner 的文件，v2 时代走 Registry.load 拒载（设计稿 22 捣乱 B），v3 走门禁 L1 拒包，
        #   两条路径同一判据、同一结论；判据单点维护——L1 判据就是各 Registry.load 校验段的同一份规则，
        #   不在门禁里抄第二份（判据漂移比没有门禁更糟，设计稿 23 "判据不写第二份"同款）
        # 对照锚：手工路径为什么也安全——边界规则表例外行要求手工改文件"须走 Registry.load 全量校验"，
        #   即手工路径保底也有 L1 半边的闸（对照段详表）
```

### 主干三：L2 引用一致性——闭包断裂/循环引用/废弃引用逐项报出（W-F20-1）

```text
伪代码 — app/eval/semantic_ci.py:SemanticCI._L2_引用一致（m18 私有件；只读 m16 公开面——防环纪律）

    async def _L2_引用一致(self, change) -> [gate_report]:
        报告 = []
        # 对账对象 = **变更应用后的全量语义资产图**（现有资产 + 变更包 diff 合成），不是单个文件——
        #   同包内 A 改了 id、B 还引旧 id，两文件各自合法、合起来断裂：单文件检查看不见这种病（走查推演 1 的①）
        全量图 = 现有资产(m16 公开面装载态) ⊕ change.diff

        # ── 判据① 闭包断裂：每条引用边逐一解析，解析不中即报 ──
        for 引用 in 全量图.引用边():
            #   glossary_id / related_metrics → 指标 id 逐个经 MetricRegistry.get 解析（设计稿 35 主干三
            #     "CI 的 L2 引用闭包按 glossary_id 对账报出"的兑现位）
            #   ontology 关系端点 → 实体名经 resolve_entity 解析（设计稿 36 装载闸端点闭包的 CI 收编位——
            #     前稿原话"设计稿 38 CI L2 的装载期前置半边"）
            #   playbook steps[].uses 的 metric 引用 → 指标域已登记（设计稿 37 引用闭包同款收编）
            if not await 解析(引用):
                报告 += gate_report(级="L2", 项="闭包断裂", 结论="红",
                                    修法=f"{引用.来源资产} 引用的 {引用.目标键} 不存在——"
                                         f"改 id 或先补被引资产；收件人：{owner路由(引用.来源资产)}")

        # ── 判据② 循环引用：引用图 DFS 找环，报出环上完整路径 ──
        for 环 in 引用图(全量图).找环():
            报告 += gate_report(级="L2", 项="循环引用", 结论="红",
                                修法=f"解析链成环：{'→'.join(环)}——环上每一条都解析得到，但解析不终止；"
                                     f"指定其中一条为现行叫法、其余降为别名，收件人：术语域 Owner")
            #   环的特殊危害：每个节点单看都合法（都能对上现行登记），合起来解析无限递归——
            #   装载闸的"能对上现行登记"判据查不到它，只有全量图上的环检测能报（与判据①互补的教科书案例）

        # ── 判据③ 废弃引用：引用目标存在但 status=deprecated——闭包不只查"存在"，还查"活着" ──
        for 引用 in 全量图.引用边():
            目标 = await 解析(引用)
            if 目标 and 治理字段(目标).status == "deprecated":
                报告 += gate_report(级="L2", 项="废弃引用", 结论="红",
                                    修法=f"引用了已废弃条目（{目标.id}，2024 年废弃禁用词，设定书 §6）——"
```

### v2 对照场景：手工改文件+重载路径——边界规则表例外行的保留与边界

> 边界规则表 v3 增补行原文（modules.md §边界规则末行）："语义资产文件绕过『Lifecycle 变更包 + 五级 CI + Owner 审批』链路被直接修改 | **例外**：治理者手工改文件+立即重载（对照场景，须走 `Registry.load` 全量校验）| 理由：版本 2 既有手工路径保留为对照；生产路径只认门禁"。

**为什么保留**（两条）：
1. **对照价值**：设计稿 22 走查推演 4 的"手工改 YAML+重载"就是 v2 时代的口径发布方式，W-F13-4 的断言（重载后全量引用一致）在手工路径上成立过。保留它，才能呈现"门禁前后"的对照——同一个完成率变更，v2 手工重载只过了装载闸一级，v3 过五级安检；没有旧路，新路的贵就显不出道理。
2. **应急通道**：生产热修（线上口径事故需要分钟级止血）时，治理者手改+立即重载是兜底路径——但例外行的但书"须走 `Registry.load` 全量校验"意味着手工路径保底仍有 L1 半边的闸（带病文件连应急都进不去），且事后必须补变更包走门禁留痕（补包纪律归设计稿 43 的流程语义，本设计稿只立原则）。

**为什么平时不走**（门禁不是手续，是检查本体）：

| 检查面 | v2 手工路径（改文件+重载） | v3 门禁路径（validate_change） |
|---|---|---|
| L1 结构合法 | 有（Registry.load 校验段——例外行但书保底） | 有（同一判据收编，主干二） |
| L2 引用一致 | **无**——装载闸只查单文件形状，跨文件引用病/环/废弃全看不见 | 逐项报出（主干三，走查推演 1） |
| L3 模板与安全 | 仅首词 SELECT 初检（装载闸收编第 5 条） | 四判据逐项（主干四） |
| L4 治理 | **无**——手改不需要审批，高影响变更可静默上线 | 高影响强制 Owner 审批（主干五） |
| L5 行为回归 | **无**——改完即生效，金标对不对得上没人知道 | 全量+负样本全绿才放行（主干六） |
| 证据 | 重载成功即一切 | gate_report 留档+审计行（裁决可追溯） |

结论一句话：手工路径 = 一级闸的应急道；门禁路径 = 五级安检的生产道。应急道的存在不稀释生产道的纪律——例外行的措辞是"对照场景"，生产路径只认门禁（边界规则表原文）。

## 关键判断的取舍记录

1. **五级判定序：级内逐项不短路、级间设两个短路点（L1 红短路、L5 前短路）——贵闸永远最后。** 备选一"每级命中第一处即打回"：提交人修一处跑一遍门禁撞下一处，治理带宽消耗在重复过闸上，且修法清单永远只见冰山一角；备选二"五级全部无条件跑完"：L1 结构不合法时引用图根本合成不出来（对账对象不存在），L5 烧全量跑批的钱去买静态检查十毫秒的结论。落定：L1 红（对象不存在）与进 L5 前（贵闸前置）两处短路，其余逐项报全。五级互不替代的论证见捣乱输入 B——L5 绿不蕴含 L2 绿（金标册子覆盖不到引用病），跳级在接口上不可表达（validate_change 无选级参数）。**换边条件**：变更包规模大到 L2 全量闭包对账成为瓶颈——按变更影响面裁剪对账子图（受影响资产的一跳邻域），判定序不变。
2. **L1 是收编不是重写：判据集=v2 装载闸校验段逐条同名，语义不回退。** 备选：门禁自带一套"更严格"的结构判据。否决理由：两套判据两处维护，漂移之日就是"门禁绿了装载炸了"（或反之）之时——绿灯说谎比没有绿灯毒（设计稿 23 主干七"判据同一份代码，两处判据漂移比没有 CI 更糟"的同款论证）。落定：L1 判据与 Registry.load 校验段同一份规则（缺 owner/八字段/approved 才收/safe_load），同一份坏文件在两条路径同拦（设计稿 22 捣乱 B 的文件进 L1 同样红）。"更严格"的真实含义不是新判据，是**不可绕过**：v2 判据只在启动装载时跑，v3 让每次变更发布都过同一道闸。**换边条件**：装载闸判据升级（如新增字段契约）——改 Registry.load 校验段一处，L1 自动跟随（判据单点维护的收益即在此）。
3. **L5 复用 GoldenStore 不重写评估：册子、grader、注入缝三件全沿用设计稿 23 交付物。** 备选：门禁内置一个"轻量版"行为检查（抽几条 golden 跑跑）。否决理由：轻量版的抽哪几条、怎么判，必然是第二份判据——门禁语义与评估链一旦分叉，"评估全绿、门禁打回"（或反向）的扯皮无解；且 W-F20-3 明文验收"门禁语义与 v2 评估链衔接不回退"。落定：L5 的册子=GoldenStore 全量、判据=ResultGrader.compare 同一函数、被评链=设计稿 23 的公开入口注入缝、金标纪律=手算出处不豁免（走查推演 3 t3：口径改版金标重算，出处仍是手算）。负样本半边借 m19 红队用例（卡面签名引用，设计稿 25 真身）——正负双边对冲（报告一 "One-sided evals create one-sided optimization"）在门禁语境下同样成立：只跑正例的门禁会放过"新资产把红队拦住的路径重新放开"这类病。inconclusive 不算绿（设计稿 23 三出口沿用）：跑不出证据=放不了行，fail-closed。**换边条件**：册子上百题后 L5 按影响面抽测（受影响指标相关 case 全跑、无关 case 抽检），"全量"口径随档位配置走——闸与判据不随规模变。
4. **gate_report 四元组与 fix_hint 收件人纪律：修法=可执行建议+收件人，打回即工单。** 备选：报告只给"级+原因"两元组（"L2 检查未通过"）。否决理由：打回的价值在修法不在否决——设计稿 24 Verdict 已立"拒绝带段与改法"的先例，fix_hint 的收件人纪律（给到能改的人）在这里升级为 Owner 路由（设定书 §1 责任链：产量口径→开发室/措施→采油工艺所/经营→销售计量站/平台语义→阿强+数据管理岗）；"问题单工作流：分发→认领→整改→复核→关闭"（设定书 §4 闭环流程，[孙福街/陈绍凯]）的行业原型里，分发的前提是修法说清了改什么、谁改。落定：四元组（级/项/结论/修法）逐条自带收件人；报告结尾给汇总行（红项数/待审批态）。**换边条件**：报告接入设计稿 42 三源建议池时，gate_report 项可直接转建议池条目（统一字段：证据/置信度/优先级/状态）——四元组形状兼容，只加字段。
5. **放行=五级全绿+Owner 审批，两件独立条件；CI 只裁决不发布。** 备选一：CI 全绿即自动放行（全自动发布）；备选二：Owner 审批在 CI 之前（先批后验）。否决一：高影响口径变更的"该不该"是业务决议，机器没有投票权（捣乱输入 A 三层论证；锚 DataBuddy"自动化止于提案，责任归于 Owner"）；否决二：先批后验让审批人批一个没验过的东西——审批该发生在"确定改得对"之后，门禁给审批供给证据。落定：审批证据随包过 L4（判"带没带、人对不对"），五级全绿+审批齐才达放行态；发布动作（写回+重载）归 m16 生命周期，流转/合并/回滚归设计稿 43（卡 m18 mr_flow："合并 = SemanticCI 全绿 + Owner 审批 → 版本发布可回滚"）。**换边条件**：低影响变更（同义词增补档）量大到审批成为瓶颈——按影响分类走 Owner 例行批量签认（仍不豁免，只是节奏变），高影响档永不批量。
