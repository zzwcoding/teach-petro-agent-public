```text
class McpServer:
```

### 主干二：Elicitation 映射——缺参问询是 server-initiated 的闸（W-F28-2）

```text
伪代码 — app/agents/tools/mcp_server.py:call_tool 缺参分支（m8；elicitation 请求形状按
         "Server-initiated requests for additional information from users"（MCP 官方规范）；
         ★ 缺参判据=schema 必填检查，m8 自有判据——零 import m7，clarify 是语义映射不是代码依赖）

    async def call_tool(self, caller, name, arguments, 应答源=None) -> MCP响应:
        spec = self._registry.lookup(name)
        if spec is None:
            # 未注册：不进缺参分支——unknown_tool 同形状拒绝（捣乱 A），elicitation 不救未知工具
            return 出门封装(await self._executor.call(构造调用(name, arguments), caller))
        # ── 缺参判据：schema 声明的必填参数缺失（代码闸；语义歧义不在此判——取舍 2）──
        缺参 = [r for r in spec.parameters.get("required", []) if r not in arguments]
        if 缺参 and 应答源 is not None:
            # ★ server-initiated 问询：服务器主动问，不是把参数空洞丢给远端模型瞎猜——
            #   m7 clarify 语义的协议面："信息不足先反问"（设计稿 14 主干三）的问法逐构同源
            问询 = {"kind": "elicitation_request",
                    "message": f"{'、'.join(缺参)} 必填——您想查哪个区块、哪段时间的什么数据？",
                               # 反问话术映射 m7 三要素语义（设计稿 14："您想查哪口井？想看哪段时间的
                               # 什么数据？"）——问"缺什么"列清单，与 clarify 的 missing 列表同构
                    "requested": {r: spec.parameters["properties"][r] for r in 缺参}}
            补参 = await 应答源.问caller的用户(问询)      # 设计演绎为同步往返；真实协议有声明-应答流程
            if 补参 is None:                             # 对端拒绝补参（无人在对端或用户不答）
                return 出门封装(ToolResult(生成call_id(), name, ok=False,
                    error_code="param_invalid",
                    content=错误文本({"error_code": "param_invalid",
                                      "message": f"缺少必填参数：{'、'.join(缺参)}",
                                      "hint": "补齐后重试"})))
                # fail-closed：拒答与普通校验失败同形状（同内部拒绝形状；无应答源时同样落到这里）
            arguments = {**arguments, **补参}             # 合并补参 → 继续走同一五步
        result = await self._executor.call(构造调用(name, arguments), caller)
        return 出门封装(result)
```

## 关键判断的取舍记录

1. **三映射只包装不复制——mcp_server 是"第二种叫门方式"，不是第二扇门。** 备选：为外部调用方单独维护一份"对外工具清单"、或直接调用工具的 func 绕开执行器（"协议路径更短更快"）。否决：卡 m8 v3.1 注释"只包装 m8 注册工具，外部调用同过 Permission 闸（协议层不加权）"与边界规则表 v3.1 行把"绕过注册与权限闸"明文列为禁止——清单复制品会与注册表漂移（新工具上线/权限调整不同步），第二条执行路会让标准错误三分法与拒绝入轨迹全部失效。机制含义：`list_tools` 的数据源就是 `Registry.tools_for`（清单函数没有绕开过滤的参数），`call_tool` 唯一的执行行就是 `Executor.call`（五步内含 `assert_allowed`）——"同权同闸"不是约定，是注入面锁死后的结构属性。代价：协议侧不能享受"免过闸的快捷方式"——但这正是本节要讲的：暴露面扩一圈，闸一寸不移。换边条件：无（边界红线，不设换边）。
2. **Elicitation 只为 schema 声明的缺参开门，语义歧义不开门；m7 clarify 是语义映射不是代码依赖。** 判据=必填参数检查（`m8` 自有，零 import text2sql）；m7 的贡献是"形"——反问话术（缺什么列清单+三要素问法）与"反问是硬路径不是软约束"的闸语义。语义级歧义（"产量"指完成率还是日产油？）不归 elicitation 管：那是问数链的 clarify/指标裁决职责（设计稿 22 多候选回澄清、设计稿 39 S6 资格级），协议出口只补参数空洞，不替内部链路做业务裁决。远端拒答或无应答源→与普通校验失败同形状拒绝（fail-closed：问不到就不执行）。备选：把 m7 clarify_intent 直接接进协议出口做全量语义澄清。否决：m7 不在设计范围 Touches（只读消费），且把问数图的入口语义塞进工具协议层=越界代管。换边条件：出现"工具级语义澄清"的真实需求时扩卡（如 ToolSpec 增声明式澄清要素字段），本节不预支。
3. **Tasks 映射同队列同 worker——受理即回+句柄是既有受理帧形状的协议面，不新造队列。** 备选：为外部任务单开队列、单开权限级、或给外部任务更高的资源档位（"商业客户优先"）。否决：边界规则表 v3.1 行"协议层不加权"——两套队列=两套打捞语义=两套丢任务模式（设计稿 02/21 的消费组闭环只守一条队列）；外部任务与内部任务唯一差异是收据的形状（受理帧 vs tasks 受理），不是排队与资源的差异。句柄不越权：`task_status` 校验 caller 与句柄的归属，外部拿别人的任务号查不到状态（同权同闸在句柄上的延伸）。换边条件：出现外部任务 SLA 分级需求时归治理/运营层（队列外），协议形状不动。
4. **沙箱模式对协议侧不开放；大结果出门是出口信封的统一负载协议（兑现设计稿 29 钩子的裁决问句）。** 设计稿 29 遗留"沙箱模式对协议侧是否开放归设计稿 30 裁决"——裁决：不开放。沙箱是剧本（Owner 审批资产）授权的执行模式（设计稿 27 取舍 1），其入口是剧本驱动方的编排调用，本就不在 Registry 公开面上——协议侧经 `call_tool` 结构上进不了沙箱腿；自由协议调用撞大结果时 200 行收口先斩（设计稿 12 主干五），3,600 行全量在自由路径（内/外一致）上不存在。协议侧的大结果诉求由本节出口信封承接：任何 >50 行负载一律折成句柄+5 行预览出门——句柄四字段/顺序闸/截断纪律与设计稿 29 逐字同源（形状复用），但不 import sandbox.py 内部件（那是沙箱腿的内部件）——两处常数同源声明，改协议时两处一起改（设计演绎的诚实代价，比静默复制可查）。换边条件：出现"协议侧合法发起剧本任务"的需求时，走 Tasks 映射交内部剧本链（本节走查推演 3 已是此形状），仍不为 tools/call 开沙箱直通道。
5. **AgentCard 是文本交付物——最小字段集+一句话关系声明。** 备选：完整规范字段复刻（含安全方案明细、流式能力位全集）+ 真实端点地址。否决：设计范围只要求"技能/端点/认证声明可复述"——三问能答即达标；真实端点与端口属图纪律与零代码红线双禁区；完整规范复刻会把设计重心从"发现文档干什么"挪到"字段背记"。与 MCP 的关系压成一句话（"A2A complements MCP"+不包装原话注源）：协议之争（谁吃掉谁、网关放哪）不在本节展开，设计稿给事实与分工，不给站队。换边条件：要做"动手验证"时，以最小集样例为骨架补真址与托管——设计稿不预支。

## 锚点对照精要

**MCP 2026-07-28 规范形状（references/data-agent-frontier.md）**：原文要点——架构三角色 Host/Client/Server，JSON-RPC 2.0；服务器能力 Resources/Prompts/Tools；客户端能力 **Elicitation**（"Server-initiated requests for additional information from users"——服务端反向向用户要澄清）；opt-in 扩展 **Tasks**（长任务异步执行：轮询、mid-flight input、durable handles）；安全原则写进规范——工具描述/annotations 视为不可信、调用任何工具前须用户同意。落点：三映射对照表的概念列与主干一/二/三的形状注源；安全原则的设计注记——本 server 包装的是**自有** Registry 的描述（描述契约经设计稿 12 注册闸"适用：/不要用："两段结构检查），"第三方不可信描述"风险在本平台结构上弱化，"调用前须用户同意"对应的对端确认流只留概念位（应答源参数），不展开。
