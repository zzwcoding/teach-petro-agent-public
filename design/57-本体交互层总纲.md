笔记一 §9.2 五层原文（引用主位——逐字，主干一各层的信源底座）：

> 1. **Context Layer**：每次发消息时系统**自动**把相关背景准备好——不是等 AI 决定要不要查
> 2. **Query Layer**：AI 自己判断需要查什么，主动去查——支持过滤、聚合、沿着关系链深层探索
> 3. **Logic Layer**：调用封装好的业务函数——关键设计：不让 AI 自己拍脑袋，把专业计算交给专业函数
> 4. **Action Layer**：执行受控的业务变更——到这里 Agent 从"问答助手"变成"业务操作员"；高风险操作要人确认，低风险可自动执行
> 5. **Governance Layer**（最重要的一层）：权限、审计、安全约束贯穿前面四层——这是 Palantir 跟普通 Agent 框架最核心的差异

正文解释：五层的记忆抓手是**触发方式**这一列——L1 是全模型里唯一的确定性触发（系统级，LLM 零参与），L2/L3/L4 都是 LLM 决策（差别在后果：查/算无副作用，动有副作用所以要人确认），L5 不在触发序列里（贯穿配置面）。确定性 vs LLM 决策的分界原则（笔记一 §9.5）："**确定的内容走 Context，允许 Agent 探索的内容走 Query Layer**"——这句原则的书侧同构是智能体化 RAG 的范式转变（原书第三章 :546 实测）："知识库检索不再是自动化的前置步骤，而是一个可供 Agent 随时调用的**工具**"——前置步骤=Context 的确定性装配，随时调用的工具=Query 的 LLM 决策；两处信源在"触发方式是第一设计变量"上会师。放错位置的代价两侧都在（笔记一 §9.5 对照表）：Context 塞太多→token 浪费与噪声；Query 配置太窄→"LLM 可能查不到你想要的信息，它就开始编"。
