**差异扫描的确定性边界**（主干二尾注）：扫描器只做**token 级清单命中**——原文与错误定位附近查 SKILL.md 差异清单条目的触发形状（`CONNECT BY`/`START WITH`/`(+)`/`ROWNUM`/`?` 占位符/`''` 比较……），命中则 fix_hint 引该条目名与建议改法，未命中给通用改法。它**不做**：语义判断、自动改写、函数注册表校验（sqlglot 对未知函数解析为匿名节点不报错——拦不住，推演 3）。扫描投影与清单逐条对账由校验脚本构建期完成（主干四），闸运行时只读投影——文档真源与运行时行为不同步是配置错误，校验脚本的对账职责。

## 关键判断的取舍记录

1. **近似方言只拦不修——fix_hint 是建议文本，闸不做方言自动改写。**（设计范围点名）备选是"拦下后用 sqlglot transpile 自动转译成目标方言再放行"——被否：sqlglot 的 transpile 在**官方方言对**之间可信，而金仓≠postgres 100%、达梦≠oracle 100%（官方核实结论），近似方言间的自动转译没有正确性凭据，错译比拦截贵一个量级（拦截只费一次重试，错译是错数据进决策）；这与设计稿 24 取舍 1 的切换条件同构——改写升级为"另一种生成"时必须换确定性凭据。fix_hint 因此定位为"指路不代写"（设计稿 24 取舍 4 的收件人纪律）：结构族差异给出确定性改法文本（CONNECT BY→WITH RECURSIVE），语义族差异指回差异清单条目。**切换条件**：出现官方迁移工具背书的确定性转译规则集（金仓 KDTS 类工具的 SQL 重写规则可程序化引用）时，才评估"拦+有凭据转译"的升级。
2. **方言映射表放部署配置而非代码。**（设计范围点名）方言是环境属性：同一镜像要在金仓/PG/达梦三处部署（F11 国产化故事），映射写死在代码里=换库改码发版，与设计稿 03 `build_engine(url)` 连接串外置的既定世界观冲突；且映射条目必须与**金仓兼容模式对账**（initdb 期固化，PG/Oracle/MySQL/SQL Server 四选一）："金仓=postgres"只在 PG 兼容模式部署成立，Oracle 兼容模式的金仓该登记 oracle——这个对账字段天然属于部署登记物，不属于代码常量。**未知库类型 fail-closed**：没有近似凭据不猜（错配近似比拦截潮危险），折 `dialect_parse_fail` 并把"登记映射表"写进 fix_hint——修一次永久生效。**切换条件**：单环境多库联邦查询出现时，映射从"库级"升级为"语句级路由"——PRD 明确不做跨库联邦，届时空谈。
3. **SKILL.md 渐进披露，不全量塞进系统提示。**（设计范围点名）九条差异清单若全量进生成系统提示：每轮问数都付这笔 token（多数查询永远用不到方言差异），且动态拼接差异文本违反 F12 三铁律（系统提示词冻结——前缀失稳=提示词缓存命中率崩，首字延迟暴涨，设计稿 16 有对照数据）。渐进披露三段式（Agent Skills）：description 常驻承担"何时用+反例"的发现职责（工具描述的艺术同款写法），差异清单正文按需加载（方言错误出图后、国产化适配时），校验脚本不进上下文即可离线执行（"用 token 生成远比直接跑排序算法贵"——差异扫描这种确定性活就该代码干）。**切换条件**：方言失配成为回灌/拒绝的主因（命中率数据反转）时，才把清单的**精简触发表**（非全文）装配进生成提示词冻结段——那是 m7/m13 装配侧的设计稿，本节只交付载体。
4. **方言失配单列 `dialect_parse_fail`，不混入 `parse_fail`；链身两行预留位接线如实备案。** `parse_fail` 在设计稿 24 的语义是"结构不可确证"——最严拒绝、固定话术、不喂回模型、fix_hint 不出图；而近似方言下失配的语句多数在目标家族合法、有确定性改法，混用会让 fix_hint 出不了图（W-F14-6 落空）。单列新码后 m7 零改动：check_sql 的兜底分支本来就是"一切未来新增拒绝码"的预留位（设计稿 24 原文注释），原样携带 rule+fix 出图。代价是设计稿 24"换真身只动本函数体"的字面承诺修正为"函数体+链身两行"（fix_hint 偏好行、注记透传行——均为同模块数据装订，设计稿 24 Verdict 注释"方言近似（设计稿 26 起）"与 reason 码透传通道皆是预留位），主干三逐行备案，不静默。

## 锚点对照精要

**sqlglot 官方调研**：原文核实——sqlglot 支持 34 种方言、极活跃（open issues 仅 1），**Dameng/Kingbase 均不在任何一层方言清单**，GitHub 搜 `kingbase sqlglot`/`dameng sqlglot` 为 0 结果（2026-09-14 实查）；但 README 明确社区方言可继承子类/entry-point 插件扩展。借鉴归纳：AST 闸用 sqlglot 无悬念；金仓走 postgres 近似、达梦走 oracle 近似是当前最务实路线，但必须叠加自维护方言差异清单做二次校验，且近似解析只用于**闸前规范化与危险语句拦截**，不能替代真实库试跑/EXPLAIN。落点：主干二调用序列与解析失败路径即按其官方 API 形状；近似红线声明与差异清单（SKILL.md）即其"叠加二次校验"结论的兑现。

**sqlfluff**：原文核实——sqlfluff 为 SQL linter/格式化器、28 种方言、含 Greenplum 但**无金仓/达梦**。落点与边界：Greenplum≠金仓，**不得把 Greenplum 方言冒用为金仓近似**（SKILL.md 差异清单第 9 条显式警告）；lint 层是风格补充不是执行前闸——本节闸的判据只有 sqlglot 近似解析+清单投影，sqlfluff 不进执行路径（可选依赖，设计范围外不讲）。

**Agent Skills**：原文——skill 是"指令、脚本与资源的文件夹，agent 可发现并动态加载"，最小形态是含 YAML frontmatter（name+description）的 SKILL.md；"渐进披露是让技能灵活可扩展的核心设计原则"——启动只载 name/description，用到才读全文，"技能可捆绑的上下文量实际上不受限"；技能可含代码供酌情执行，"用 token 生成排序列表远比直接跑排序算法贵"。落点：SKILL.md 三件套逐项对应（frontmatter 前置/差异清单正文按需/校验脚本说明），取舍 3 的渐进披露论证即其原文引用。差异：Anthropic 的 skill 由 agent 自主加载，我们的差异清单第一消费者是**确定性闸**（只读投影不读文档）与人——agent 装配侧按需加载是第二路径，载体先行。

**金仓/达梦既有考察**：原文要点——金仓兼容模式 `initdb` 期固化（PG/Oracle/MySQL/SQL Server 四选一，不能运行时切换）；Oracle 模式下 `ora_input_emptystr_isnull` 等参数使空串语义与 PG 不同；达梦 dmPython 绑定占位符是 `?`、对象寻址 `模式名.表名` 类 Oracle；金仓 Oracle 兼容模式提供 ROWNUM/ROWID 伪列；SQLAlchemy 需金仓官方方言包。落点：SKILL.md 差异清单的一手素材（第 1/2/6/7/8 条逐条溯源），主干一映射表的"依据=兼容模式"对账字段即"initdb 期固化"的运维化。
