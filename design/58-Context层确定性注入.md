### 主干五：最容易搞混的一对——Retrieval Context vs Object Query（W-F44-3 后半）

笔记一 §9.5 原文（引用主位——逐字）：

> | 维度 | Retrieval Context | Object Query Tool |
> |---|---|---|
> | 触发方式 | 每条用户消息自动触发 | LLM 自己决定是否调用 |
> | 可靠性 | 确定性更强 | 依赖 LLM 判断，存在漏查风险 |
> | 适合内容 | 当前业务对象、关键背景、必须看到的信息 | 探索性分析、临时查询、多轮追问 |
> | 风险 | 配置不当带来 token 浪费或上下文噪声 | LLM 可能忘查、错查、查不全——**LLM 可能查不到你想要的信息，它就开始编** |

> - 放错的后果：Context 塞太多 → 浪费 token、噪声干扰模型（需要超长上下文模型才能处理，成本上升）；Query 配置太窄 → LLM 查不到就开始编
> - **一条原则：确定的内容走 Context，允许 Agent 探索的内容走 Query Layer**
> - 类比：Retrieval Context 是固定在工位上的监控大屏——永远开着，永远显示关键指标；Object Query 是手里的对讲机——需要时才拿起来问一句"3 号仓现在什么情况"

## 关键判断的取舍记录

1. **确定性分界画在"层触发"，不画在"三路全开"。** 备选 A"确定性=每条消息三路全装配，不做任何路由"：否决——预算装不下（路 2 的 token 账），且 笔记一 §9.5 风险行明写"配置不当带来 token 浪费或上下文噪声"，全开=把配置不当做成默认。备选 B"路由交给模型理解意图"：否决——触发层引入 LLM 判断=确定性承诺破防（路 1）。落定：层触发确定（每条消息必跑 assemble）+路开关走确定性规则（page_state 绑定/预设注册表/文档指称形态三判据，主干二绑定三规则）——"确定"的是机制，"配置"的是规则，两者都是人事前写的，不劳模型临场判断。换边条件：无——笔记一 §9.3/§9.5 字面双向锁定。
2. **Document Context 全文模式只立输入输出契约，全文拼回机制注记设计稿 64。** 备选 A"本节自造一个'读取文档全文'函数签名把路走通"：否决——公开签名自造=伪代码红线（签名唯一来源是模块卡）；且全文从块拼回（重叠去重）是设计稿 64 Wiki 管线的既有合同位（`Reconstructor.rebuild(doc_id) -> FullText`——卡 m27 公开接口），本节重讲=跨线抢戏。备选 B"全文模式不做，只讲片段"：否决——W-F44-2 断言字面要两模式各有适用场景可复述。落定：t4 全文模式立契约（输入=文档指称，输出=整份文本入包过预算关），拼回机制注记设计稿 64 零展开；PRD F44"复用 m6 检索"字面落在片段模式（`Retriever.search` 只读引用）——两处复用各归其位。换边条件：若后续设计稿把全文读取扩进 m26 公开面，走新设计稿改卡，不在本节就地造签名。
3. **预算裁剪=固定优先级+整块裁+注记可见，不截半块、不调模型摘要。** 备选 A"超预算把最低优先级块截一半"：否决——截半的合同条款/断章的产量序列比没有更毒（模型拿半段当全段），且"截多少"又是一个临场判断；备选 B"超预算调 LLM 把块摘要压缩后塞入"：否决——装配路径上引入模型调用，确定性触发漏底（与路 1 同罪），且每条消息付一次摘要钱，常开成本失控。落定：t5 三条纪律——优先级固定（Ontology＞Function＞Document：绑定对象是"必须看到的信息"最低限，§9.5 适合内容行字面）、整块裁剪、clipped 注记随包可见（模型知道自己没看到什么，可建议改片段模式）——三件都是人事前写的规则，逐字节可复现（主干六位置注记的资格条件）。换边条件：无。
4. **治理先裁再装（t1 在三路装配之前），不装完再滤。** 备选"三路先装满 ContextPack，出口处按 CapabilitySet 过滤一遍"：否决——装了再删，白花的装配成本照付；更本质的是两种状态的防幻觉强度不同："接触过再隐藏"是软隔离（实现漏一处就泄），"结构上不进流水线"是硬隔离（笔记一 §9.8"根本接触不到"的 L1 落点——设计稿 57 已立口径，本节是它在装配时序上的机械兑现）。落定：t1 先裁，无权域候选在装配前即空；矩阵本身（角色×五层全表）零展开归设计稿 62——本节只消费 `Governance.matrix(user) -> CapabilitySet` 一个签名（卡 m26 逐字）。换边条件：无。
5. **ContextPack 恒垫底+旧包不改写；不提供"绑定对象不变就把包前移进前缀"的优化。** 备选"井详情页会话里 N-02 不变，ContextPack 内容也不变——不如前移进冻结前缀拿缓存命中"：否决——前缀稳定性要求**逐字节**不变（设计稿 16 铁律一机制事实：前缀匹配是字节比对），而 ContextPack 的字节面受预算裁剪、信任标措辞、去重结果影响，任何一处演化都是前缀抖动；且 m19 打标措辞按在场素材裁决（设计稿 25），装配件的字节稳定性没有冻结段的资格。落定：包恒在 dynamic 段垫底；会话级纪律=旧包留在历史原位不改写、新包只追加（append-only——设计稿 16 铁律二在会话维度的应用）；同 page_state+同裁剪规则→同字节，同页追问的增量稳定可预期。换边条件：无——这是推理服务物理机制约束，不是实现选型。
6. **token 账全部替身化：量级直觉，非性能断言。** 备选"给预算账配一套'实测'数字增强说服力"：否决——零代码设计稿无实测口径，编造实测数=发明业务事实（取材红线对数字同样生效）；PRD F44 不做什么字面"塞太多的 token 账算给读者看"要的是**账的算法可见**（每块多少、怎么加总、超了怎么裁），不是数的权威性。落定：全部 token 数字（预算 4 000/一页纸 920/片段 1 536/全文合同 12 000）标注替身（主角数据④），账的加总与裁剪分支真实可走查——读者拿走的是算法，不是数。换边条件：无。
