## 1. 分层总览

四层架构，层间依赖**单向向下**，禁止跨层旁路：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 接口层  app/api/                                                            │
│  20 个前缀 router（chat/wells/change-tickets/kb/wiki/graph/faq/semantics/     │
│  proposals/ci/gateway/security/quality/checkup/keys/expose/retrieval/        │
│  observe/ingest/eval）＋ SSE 端点（/api/chat/asks 续推同路径）                 │
│  职责：参数解析·鉴权依赖注入·统一错误包·序列化（snake_case·时间/数字形状·       │
│  分页计数信封）·SSE 帧信封拼装。路由是薄壳：只调应用层公开接口，不碰仓储。       │
│  ※ HTTP 前缀 ≠ 模块归属：路由按合同前缀建文件、自由组合到模块                  │
│    （如 /api/observe/budget 路由调 gateway.budget()——见 gateway 卡）。        │
└──────────────────────────────────┬──────────────────────────────────────────┘
                                   ↓ 只调公开接口
┌─────────────────────────────────────────────────────────────────────────────┐
│ 应用层 + 领域层  app/domains/<模块>/（每模块一个包：用例编排薄、领域聚合厚）     │
│  组A 会话问答与知识面（6）：chat · wells · faq · kb · derivatives · retrieval   │
│  组B 治理与测量面（5）：semantics · governance · approval · assessment · dataops│
│  组C 平台底座（3）：gateway · security · expose                               │
│  模块间只走公开接口 + 领域事件（§8）；依赖无环（§6 禁令逐条可进 import-linter）  │
└──────────────────────────────────┬──────────────────────────────────────────┘
                                   ↓ 只经 adapter
┌─────────────────────────────────────────────────────────────────────────────┐
│ 基础设施层  app/infra/                                                       │
│  db（双库连接层：开发 PostgreSQL / 生产金仓，EncryptedField SM4）              │
│  object_storage（MinIO/对象存储 adapter：预签名 PUT/GET·HEAD 核实·两桶          │
│    reports/artifacts）· queue（异步任务骨架：受理 202＋轮询＋终态＋重入 409，    │
│    11 处合同先例的统一承载）· sse_channel（事件缓冲 ≈200 帧·Last-Event-ID 续推） │
│  eventbus（领域事件）· clock（ISO 8601 东八区）· scheduler（cron：体检周期/     │
│  卡住巡检/水位刷新）· crypto（SM4 字段加密/SM3 摘要）· config（config.yaml      │
│  装载与热加载）· llm_client（OpenAI 兼容上游客户端，供 gateway 编排）           │
└─────────────────────────────────────────────────────────────────────────────┘
```

- **应用层/领域层不拆两套目录**：每个模块包内 `service.py`（用例编排，薄）与 `domain.py`（聚合与领域规则，厚）——深模块的"厚"在 domain 层；拆成两个顶级层会诱导"服务类转调领域类"的浅文件瘟疫。
- **接口层不许出现业务判断**：`405`（C1 纯读面兜底）、`409`（状态机/重入）、`422`（业务规则拒绝）等状态码语义由模块抛出的领域异常映射（统一错误包 `code/message/detail/trace_id`，00 册 §3）。
- **总架构与中间件（ADR-0003 选型落盘批）**：本四层即**主平台模块化单体**的分层（Python 3.12＋uv，明示——98 划分仍只覆盖主平台）；主平台单体外另有**独立数据面服务**（数据面服务仓 v2——进料/清洗/出汇总层/质检/报水位），经公开 HTTP 合同对接（`/api/ingest/*` 四端点＝主平台调数据面 API 拉投影，零共享库）。中间件五件：PostgreSQL／Redis（缓存＋任务队列＋SSE 通道＋事件通道）／MinIO／Neo4j（图存储）／Langfuse（自部署可观测——挂接口径归 D1 册「观测（Langfuse）入口与五信号统计源口径」节〔D1 v0.2〕；原 D5 端点 7 开关挂接，随页撤除）。各 adapter 实现选型逐行落 §4。

### 分组理由（与任务书建议分组的差异逐条交代）

| 任务书建议 | 本设计稿处置 | 理由 |
|---|---|---|
| 会话与问答编排（chat/SSE/澄清/审批 interrupt/产物） | 组A `chat` | 采纳。wells/retrieval/faq 一并归 A：wells 是 page_context 的生产页、retrieval 是问答检索瀑布的配置权威源、faq 是六路匹配器之一——三者都是问答链的直接协作方，聚在 A 使"改问答行为"的关注点集中在一组内。 |
| 知识库与索引（kb/wiki/graph/faq） | 拆为 `kb` + `derivatives`，faq 归组A | **wiki+graph 合卡、faq 不合**：B4/B5 合同各自论证"不并入 /api/kb 前缀"是 HTTP 资源语义（产物文档域/图谱域 vs 入库管线域）——本设计稿尊重该边界，但两条管线产物共享同一生命周期（四开关派生·入库定型·批准后派生物刷新），合为 `derivatives` 一卡两子域，避免两张 3–5 端点的薄卡。faq 与 kb 虽同属知识域，但 FAQ＝服务资产（chunk 直入、三态状态机、挖掘管线），与入库管线无共享聚合，硬合会把接口撑到 30+ 方法（违窄接口），故独立。 |
| 语义资产与治理（semantics/proposals/ci） | 组B `semantics` + `governance`，approval 并入组B | **C2+C3 合卡**：提案单主单与流水线 run 是"主单 1—N 执行记录"（C3 工单关系 v0.2 定稿）——送检（C2→C3）与状态回写（C3→C2）双向，拆两模块必成依赖环；批准事务（m16 `Lifecycle.approve`）横跨两者，合卡后是模块内一个事务。approval 归 B：变动单与提案单是"单据分流"（A3 合同：两套单据两套状态机互不投影），不合卡，但同属单据治理域共居 B。 |
| 考核评估（eval/基准） | `assessment`（E1+E3 合卡） | **E1+E3 合卡**：两者同为"测量域"（体检是测量不是修改＝E3 行为约定 1，与考核"评产出不评路径"同教义）、同为 C2 产生通道（考核没通过/自动体检发现）、同为 C3 Verify 站的两个执行器（考题重跑＋体检复扫）——合卡后 Verify 站只对接一个模块。E3 单独成卡虽深（5 方法背后是四维评分引擎），但与 E1 合并可获得 Verify 闭环的 locality；卡内分"考核面/体检面"两个子面表达。 |
| 数据接入与质量（ingest/quality/checkup） | `dataops`（D6+E2），checkup 移入 assessment | D6 是 4 端点纯读元数据管理面（背后是映射卡/清洗路径注册表，与 E2 同一套生产 8 表与 §4 规则库——D6 合同"规则一份两用"原文），单独成卡是浅模块；并入 dataops 作"数据资产注册表读面"，E2 作其质量治理子域。 |

## 3. 模块卡（14 张）

> 格式照 开发流程 卡。公开接口是 **Python 层接口**（不是 HTTP 端点照抄）；HTTP 路由归接口层。签名中 `Actor`＝服务端会话解析的身份（00 册 §2.2 who 纪律），`actor: Actor | None` 出现在写接口必填位。

### 3.1 `chat` —— 问答编排引擎

- **职责一句话**：把一句问话变成一路可续推的 SSE 事件帧流——安检、六路装配、模型裁决、17 链执行、澄清/审批 interrupt、产物生成，全部藏在一个 `ask()` 背后。
- **深模块检验**：接口 8 个方法，背后是四层流水线（F56）、19 类事件帧（A1 合同值）、断线三收场与 ≈200 帧缓冲续推（PRD F1/F4）、澄清有界循环（两跳终态）、双入口审批 interrupt（A1↔A3 状态机单源）、大结果落盘顺序闸（F27）、产物四步任务链（F10）、工具注册表与执行器（注册/可见性过滤/沙箱三闸/外发闸）——实现与接口比约两个数量级。
- **公开接口**：

```python
def ask(question: str, *, session_id: str | None, page_context: PageContext | None,
        anchors: list[str], actor: Actor) -> SseEventStream            # POST /api/chat/asks；统一入口无旁路（F56①）
def resume(run_id: str, decision: ClarifyChoice | ApprovalDecision,
           last_event_id: int | None, actor: Actor) -> SseEventStream  # interrupt 回流/断线续推（同路径携 resume_run_id）
def list_scenarios() -> ScenarioRegistry                               # 23 场景注册表（演示 kw/pri 不入真实路由）
def list_sessions(actor: Actor) -> list[SessionSummary]                # 服务端持久会话（换设备不丢）
def replay_messages(session_id: str) -> list[Message]                  # answer 与 SSE answer 帧同形 DTO（一份两处消费）；citation.locator.fragment_id 可选＝B2 片段回跳锚（A1 挂账收口批，B2 开放问题 6 兑现）
def panel_view(actor: Actor, q: str | None, asset_type: str | None) -> AssetPanel  # @资产：各注册表 panel_view 投影，现取不建仓（F56）
def enqueue_artifact(message_id: str, kind: Literal["ppt","img","audio"],
                     actor: Actor) -> ArtifactTaskHandle               # 202 受理即回（art-task-，R5 子型声明）
def artifact_progress(task_id: str) -> ArtifactTaskView                # 五态/四步/ready 才带产物卡
# 领域内核（非 HTTP，供 expose/D3 复用）：
def tools_registry() -> ToolRegistryView          # 工具注册表（名称/schema/权限级别/可见性过滤——同一函数同一结果，lesson 30）
def execute_tool(name: str, arguments: dict, actor: Actor) -> ToolExecutionResult
def sandbox_run(script: SandboxScript) -> SandboxOutcome   # 沙箱三闸（50,000 行/512MB/60s，F57）
```

- **依赖模块**：`retrieval`（waterfall_settings 运行时装载）、`semantics`（六路匹配器之术语/指标/工作流三路、口径支澄清、Join 白名单判据）、`faq`（FAQ 索引直出）、`kb`（报告索引/问题块检索）、`derivatives`（图谱问答链遍历）、`wells`（page_context 确定性注入 ContextPack）、`approval`（action 类 interrupt 主单）、`gateway`（模型调用与记账）、`security`（安检三道/行级权限/审计）

### 3.14 `expose` —— 对外暴露门面

- **职责一句话**：外部 Agent 与平台对话的三映射门面——清单即注册表同一过滤、缺参即既有澄清问答、长任务即既有任务队列，过同一套安检，协议层不加权。

## 9. 与设计版划分的差异

设计版 `specs/modules.md` m1–m27 是**伪代码示意卡**（按技术组件横切切分，服务于逐卡走查讲解）；本设计稿是真实系统划分（按业务域聚合纵切，横切技术件全部沉入基础设施 adapter）。最大差异点：

1. **m6 问答管道一张大卡 → 四个业务域模块**：kb（生产管线）/derivatives（百科+图谱产物域）/faq（服务资产库）/retrieval（配置面）；检索瀑布**执行**归 chat 领域内核，配置**权威源**归 retrieval——设计卡里"管道"是一个组件，真实系统里它是四个页面合同的四套聚合。
2. **m1 底座 → 三处归位**：鉴权/权限/审计/国密→security；SSE 会话通道→chat 域内＋infra.sse_channel；请求日志/健康→gateway 观测子域。设计版"底座"是技术分层叙事，真实划分里横切关注点各有业务归属（凭证、安检、留痕都是合同面）。
3. **m16 语义层 → semantics＋governance 两模块**：设计版语义层管"YAML 注册表"，真实系统多出治理闭环（提案池状态机＋发布流水线＋批准事务的汇入编排）——纯读面与正门写口分离是 C1 合同的核心裁决，必须落在模块边界上。
4. **m18 评估 → assessment（测量）＋governance（CI 面）**：设计版评估证据链一张卡；真实系统里五级 CI 是发布门禁（挂提案工单）、跑批/基准是测量资产（单一基准单例）——两种生命周期。
5. **m2＋m12 → gateway 一域**：设计版网关与可观测分卡；真实划分合并，因为"账本唯一/阈值判据/别名同源"三项合同裁决都要求它们同域（§2 分组理由）。
6. **设计版没有的模块**：approval（变动单域，A3 合同产品化后立）、expose（对外三映射门面，F1 v0.2 后立）、wells（对象档案域，A2 拍板"产量统计不落档案页"后立）——三页合同都是设计版之后的增量，真实划分按合同补位。
7. **方向相反的一处**：设计版把"检索协议"立为 m21 独立组件；本设计稿保留 retrieval 为独立模块但定位是**管理面**（配置权威源），执行器在 chat——设计版强调协议本体，真实划分强调"配置治理与运行时装载"的接缝。
