## DTO 定义

### 1. GET /api/quality/rules → 200

```json
{
  "items": [
    { "no": 1, "kind": "重复", "rule": "同一口井同一天每个班次只能有一条日产记录——A/B 班手抄重复行即命中",
      "crit": "班次三元组（井,日,班次）唯一；重复/缺失行进问题单人工复核，不静默去重", "enabled": true, "action": "告警", "autoFix": false }
  ]
}
```

- `kind` 枚举（查什么分类）：重复 / 缺失 / 准不准 / 两本账打架 / 超范围 / 迟到 / 写法不统一 / 假数嫌疑 / 账对不上 / 引用完整 / 跨表一致 / 枚举合法 / 正则格式 / 极值 / 波动率 / 钩稽 / 洗数规则。
- **v0.5 实施范围注记**：规则 1–12 挂具体判据（本册 DTO 与本体 M3 双源）；**规则 13–20 为"仅登记不实施"**——设定书 §4 只收八个名字（引用完整/跨表一致/枚举合法/正则格式/极值/波动率/钩稽/scrub 规则），判据在提取件二 §三（Owner 素材，仓内无全文）；V1 质检任务只跑 1–12，13–20 在规则库列表呈现但恒不参与执行，判据补齐走治理批。
- `action` **命中动作三档**（v0.2，业界 expectations 语义）：
  - `隔离`——坏行不进湖，落隔离区待整改（行级，可追溯）；
  - `整批拒收`——批次级故障整批拒绝入湖（schema 级故障专用档；**v0.4 起补录超窗不再用此档**——规则 6 改 T-5 不拒收转问题单，见变更记录）；
  - `告警`——不拦行，通知人工核实（恒值/零值/对账类，规则原文即"告警让人看"；**v0.4 起含重复行〔规则 1〕与矛盾行〔规则 5〕**——本体裁决清单制：出清单交业务核实，不静默处置）；
  - 规则 13–20 为通用规则族，`action = "—（总册）"`，动作定义见规则库总册。
- `autoFix`（v0.2；v0.4 收窄）**安全类自动修复**：`true` 仅限写法归一 / 枚举映射（规则 7/8）——自动修复只作用于派生层，原始坏行永留隔离区；**去重保首条随 v0.4 撤出白名单**（本体 RULE-BOHAI-030＝班次粒度各行真实、不静默去重）；金额 / 口径 / 歧义类一律 `false`，绝不自动修。

### 2. PATCH /api/quality/rules/{no}

请求 `{ "enabled": false }` → 200 `{ "no": 1, "enabled": false }`。
**停用语义：质检任务跳过该条，规则不删除。** 启停写操作审计留痕（操作人/时间）。规则新增/阈值变更属"规矩变更"，走治理流程（C2 提案），不在本端点范围。

### 3. POST /api/quality/tasks → 202

```json
{ "taskId": "QT-20260928-01" }
```

- 任务号规则 `QT-YYYYMMDD-NN`（当日序号递增）。
- 异步执行四步：扫描生产库 8 张表 → 逐条跑规则（N 条启用）→ 命中开问题单 → 按责任岗自动分发。
- 同一时刻最多一个任务进行中，重入返回 409。
- **重跑语义：先清上一轮动态生成的问题单再开新单；预置问题单不受影响；任务历史不清。** **v0.5 修订（在途单保护）**：只清「分发且未认领」的单；「认领/整改/复核中」的在途单**不清**——新命中按（规则＋对象＋数据日期）**挂到既有在途单**（hit_count +1，挂单语义复用），避免责任人处理中的单被重跑清掉重开。
- 真实实现注记：数据接入层（数据面服务仓 dp3）中质检随进料管道自动触发，每次进料即一份报告——本端点是"手动补扫"入口，与管道自动触发共用同一报告实体。

### 4. GET /api/quality/tasks/{id}

进行中 → 200：

```json
{ "taskId": "QT-20260928-01", "status": "running", "step": 1 }
```

完成 → 200：

```json
{
  "taskId": "QT-20260928-01", "status": "done",
  "task": {
    "id": "QT-20260928-01", "time": "2026-09-28 19:58", "rules": 12, "hits": 3,
    "report": {
      "range": "生产库 8 表", "scanned": "12,604 行",
      "quarantined_rows": 2, "rejected_batches": 1,
      "hits": [ "① 规则 1：…" ],
      "verdict": "——已全部开成问题单并按责任岗分发（见「问题单」页签新卡）。"
    }
  }
}
```

- `quarantined_rows`（v0.2）：行级隔离坏行数；`rejected_batches`（v0.2）：整批拒收批次数。命中数＝问题数（单据粒度），隔离/拒收数＝数据粒度——两个口径分开报。
- 完成时服务端副作用：任务记录入库、合规报告生成、**隔离区落行**（坏行 payload + rule_id + batch_id + report_id，append-only）、命中问题逐条自动建单（初始态「分发」，责任岗按规则配置自动分派）。
- **幂等与挂单（v0.2）**：同一问题按（规则＋对象＋数据日期）去重——重复命中**不新建、不忽略，追加到既有问题单**（单上命中次数 +1），设定书 §4"两次质检结果由工具自动比对、问题状态动态更新"。

### 6. GET /api/quality/issues → 200

```json
{
  "lanes": ["分发", "认领", "整改", "复核", "关闭"],
  "items": [
    { "id": "p8", "lane": 0, "rule_no": 8, "hit_count": 1,
      "title": "规则 8 · 停机原因码旧码未映射",
      "desc": "equip_status 旧码 R3 未按映射表换成 BELT", "owner": "责任：作业区资料员",
      "qrows": [ { "loc": "设备状态 equip_status", "note": "停机原因旧码 R3 未按映射表换成 BELT" } ],
      "ai_note": null, "verify": null, "close_note": null }
  ]
}
```

- `lane`：0–4 对应五态；`owner` 为责任岗展示文案（含环节前缀）。
- `rule_no`（v0.3）：关联规则号——表格管理页签的"规则"筛选与 # 列消费。
- **分页预留（v0.5）**：问题单列表入参/响应随 C3/A1 同款预留 `page`/`pageSize`（`page_size` snake 按 00 §14-R1）＋`total`——V1 数据量小整表返回，字段先预留防接线期形状变更。
- `hit_count`（v0.2 契约 / v0.3 落 mock）：命中次数——同类失败挂同单，>1 即有挂单。
- `qrows`（v0.2）：**隔离/拦截明细**——该单对应的坏行/被拒批次（位置 loc + 说明 note），与隔离区表关联；告警类规则无 qrows。
- `ai_note`（v0.2；**v0.5 降级**）：**诊断说明 V1＝规则自带判据说明**（服务端从规则投影——"哪行违反了哪条规则的哪个判据"，零 LLM 调用、零幻觉面）；v0.2 的"LLM 归因草稿·AI 起草责任人确认"语义**冻结挂观察**（与规则自带说明价值重复，且 LLM 关联归因〔多规则同根因〕待真需求再立项）。字段保留、V1 返回规则说明文本。
- `verify`（v0.2）：整改与复验——`{ batch: 修正批次标识, note: 复扫结论 }`；`close_note`（v0.2）：不经修正的关闭原因（如告警类核实为真实关井）。

### 7. POST /api/quality/issues/{id}/transitions → 200

`{ "id": "p8", "lane": 1, "state": "认领", "verify": null }`
状态机：分发 → 认领 → 整改 → 复核 → 关闭；**关闭为终态，再流转返回 409**。每次流转写操作留痕（操作人/时间/前后态）。

**复验关闭语义（v0.2 调研定标；v0.5 降级修订）**：
- **V1＝人工触发复扫**：推进到「复核」仅登记待复扫状态（`verify` 仍空）；责任人（或质量管理员）在单上点「**复扫**」动作——`POST /api/quality/issues/{id}/transitions` 请求体加可选 `action: "rescan"`——服务端对**该单关联的修正批次重跑命中规则**（增量复扫，走数据面质检通道），回填 `verify`（复扫结论：全绿／仍有命中＋明细）；
- v0.2 的"推进到复核即自动复扫"语义**降级挂观察**（自动复扫依赖数据面增量复扫能力，待数据面质检重建后再评估启用）；
- 推进到「关闭」时校验：`verify` 复扫全绿，或存在 `close_note`（告警类核实免修路径）——二者皆无返回 422 拒绝关闭；
- 问题单与修正批次的关联（"问题 → 修正 → 复验"可追溯链）为自研增量，业内无现成品。

### 8. GET /api/quality/freshness → 200

```json
{
  "items": [
    { "layer": "原始层", "to": "到 2026-09-14", "promise": "T-1", "tag": "达标（承诺 T-1）", "color": "green" },
    { "layer": "清洗层", "to": "到 2026-09-14", "promise": "T-1", "tag": "达标（承诺 T-1）", "color": "green" },
    { "layer": "汇总层（问数用）", "to": "到 2026-09-11", "promise": "T-1", "tag": "落后 3 天 · 超期", "color": "gold" }
  ]
}
```

- 承诺水位 T-1＝昨天的数今天要能看到；状态判定由后端按 `data_date` 对 T-1 基准计算（达标 / 落后 N 天·超期）。
- 汇总层为问数用表，其水位是 A1 问数口径的上游依据（落后即"最近三天产量"答不齐）。

### 9. GET /api/quality/quarantine → 200（v0.2 新增）

```json
{
  "items": [
    { "batch_id": "QT-20260928-01", "rule_no": 1, "action": "隔离",
      "loc": "生产日报 · N-02 · 2026-09-14", "payload": { …原始坏行… },
      "issue_id": "d1", "created_at": "2026-09-28 19:58" }
  ]
}
```

- **隔离区 append-only**：坏行带原始 payload + rule_id + batch_id 落表，永不改写（与湖表同教义）；整批拒收的批次也落一条批次级记录（`action = "整批拒收"`）。
- 过滤参数：`batch_id` / `rule_no` / `issue_id`。页面当前以问题单详情抽屉内嵌呈现（按 issue_id 过滤），独立查询页留位。
- 告警类规则不产生隔离行。

## 行为约定（后端必须实现的语义）

1. 规则启停即生效：任务按发起时刻的启用集执行；规则新增/阈值变更走治理流程。
2. 任务历史累积保留；报告与任务 1:1；命中数（单据粒度）与隔离/拒收数（数据粒度）分开上报。
3. 隔离区 append-only、可追溯到批次与规则；schema 级故障整批拒收，行级质量问题走隔离。
4. 问题单自动建单按责任岗分发；跨次质检按（规则＋对象＋数据日期）挂同单不重复开；**v0.5：在途单（认领/整改/复核中）跨轮不清、新命中挂同单**（重跑只清未认领的分发单——见端点 3 重跑语义）。
5. 五态状态机：复核**人工触发复扫**（v0.5 降级，自动复扫挂观察），关闭须复验全绿或记录免修原因；终态锁定；全部写操作（启停/发起/流转/关闭/复扫）审计留痕，与 A3 变动单审计同口径。
6. 自动修复白名单（归一/枚举映射/去重保首条）只作用派生层，且必须留下"原始值 → 修正值"痕迹；金额/口径/歧义类禁自动。
7. 诊断说明 V1＝规则自带判据说明（服务端投影，v0.5 降级——LLM 起草语义冻结挂观察，理由：与规则说明价值重复＋幻觉风险；多规则关联归因待真需求）。
8. 水位由定时汇总任务刷新（原始/清洗层来自入湖水位，汇总层来自数据面加工水位——v0.4：原表述"D6 加工水位"随 D6 撤页改指数据面报水位件，承载＝water_line 表＋E2 端点 8 消费；与数据面梳理方案 C5 衔接）。
9. **规则语义权威源（v0.4）**：20 条规则的判据/处置以本体仓 bohai 域 M3 规则（ontology/bohai/m3-rule-model.yaml，RULE-BOHAI-*）为权威源——接线批从本体投影规则种子，本册不再二次维护规则判据文本。
