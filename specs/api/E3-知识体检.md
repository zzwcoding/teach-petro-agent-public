## DTO 定义

### 1. GET /api/checkup/objects → 200

```json
{
  "dims": ["资料全不全", "逻辑顺不顺", "数据覆盖够不够", "关系健全不健全"],
  "items": [
    {
      "key": "bo-zhong", "label": "渤中", "name": "渤中区块", "type": "区块",
      "scores": [86, 84, 80, 82], "grade": "亚健康",
      "sugg": [
        { "tag": "孤儿关系", "text": "有井没挂上\"井—隶属→区块\"关系——按区块汇总时会漏井",
          "confirmed": "已进 C2（提案：渤中孤儿关系补全）" },
        { "tag": "缺负责人", "text": "区块级数据负责人未指定" }
      ]
    }
  ]
}
```

- 对象清单来自平台四本账（业务术语 / 指标口径 / 对象与关系 / 分析工作流 → C1 指标与术语库）；`type` ∈ 井 / 区块 / 指标。
- `grade` 三档：健康（绿）/ 亚健康（琥珀）/ 需补课（红）；四维低于 70 分前端标黄。
- 建议标签 `tag` 枚举：缺来源 / 缺负责人 / 口径待裁决 / 逻辑打架 / 孤儿关系 / 资料缺项。
- `confirmed`（非空=已确认转提案）：值为确认后的归一说明（含 C2 提案指向）。**分数与建议为演示种子，接真值后由体检引擎产出替换。**

### 2. POST /api/checkup/runs → 202

```json
{ "runId": "KC-20260928-01" }
```

- 运行号规则 `KC-YYYYMMDD-NN`（当日序号递增）。
- 异步执行四步：扫描四本账 → 逐对象四维评分 → 生成补全建议 → 归一体检发现单。
- 同一时刻最多一个运行中，重入返回 409。
- **同库同数语义**：评分与建议结果不变，运行记录与"上次体检"刷新——体检是测量，不是修改。

### 3. GET /api/checkup/runs/{id}

进行中 → 200：

```json
{ "runId": "KC-20260928-01", "status": "running", "step": 1 }
```

完成 → 200：

```json
{
  "runId": "KC-20260928-01", "status": "done",
  "finishedAt": "2026-09-28 22:40（人工）",
  "totals": { "objects": 10 }
}
```

- `step`：0–3 对应四步进行位。完成时服务端副作用：体检运行记录入库、状态行"上次体检"回填。
- 触发三路§五）：周期调度为主入口（cron，不经本端点）；变更触发=汇入 Verify 站内嵌增量体检；本端点=人工立即跑。

### 4. POST /api/checkup/suggestions/confirm → 200

请求 `{ "objectKey": "N-11", "suggIndex": 0 }` → 200：

```json
{ "objectKey": "N-11", "suggIndex": 0, "confirmed": "已进 C2（提案：N-11 · 逻辑打架）" }
```

- **确认 · 转提案**：确认后该建议归一成体检发现单进 C2 提案池（source＝自动体检发现），建议上标记"已进 C2"；重复确认返回 409。
- **红线**：确认只归一（生成提案草案、留确认人/时间痕），**平台不自己改台账**——改不改由人在 C2 提案池走治理流程（F24/F25）。
- 体检发现归一诊断 schema：来源 / 对象坐标 / 现象 / 证据 / 证据形态 / 去向（E3 页样张）。

### 5. GET /api/checkup/status → 200

```json
{ "lastCheckup": "2026-09-28 02:00（周期）", "nextPlanned": "2026-09-29 02:00", "totalFindingsToC2": 7 }
```

- 状态行三字段：上次体检（含触发方式后缀 周期/人工）、下次计划（调度器 cron 排程）、累计发现（历次体检确认进 C2 的发现单总数）。
- 端点 3 运行完成时更新 `lastCheckup`；`nextPlanned`/`totalFindingsToC2` 当前为演示常量，接调度器与审计库后替换。

## 行为约定（后端必须实现的语义）

1. 体检是测量不是修改：只出评分与建议，台账变更唯一入口是 C2 提案池治理流程。
2. 触发三路：周期调度（主入口，全量）、人工立即跑（本合同端点 2/3）、变更触发（汇入 Verify 站内嵌增量）。
3. 运行历史累积保留；同库同数重跑结果不变。
4. 建议确认留痕（确认人/时间），重复确认拒绝；确认产生的提案草案与来源建议双向可追溯（建议↔提案关联）——mock 演示不含留痕字段呈现，真实实现补 confirmer/at 并在建议上呈现。
5. 四维分数为演示种子；真实实现由体检引擎按三类来源评分：**代码规则**（资料=字段登记率、覆盖=底层表行覆盖率、关系=本体边 anti-join、逻辑=一致性规则——语义矛盾由 LLM 辅助比对起草、人确认立案）+ **配置阈值**（各维合格线与总评三档分界）+ **本体参照**（应登记字段与必须关系边来自本体定义，本体扩展则标准自动增加、不写死代码）。阈值与总评线变更属改规矩、走治理流程。
