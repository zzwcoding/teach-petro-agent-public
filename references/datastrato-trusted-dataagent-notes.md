# 演讲笔记：从元数据到 Data Agent——企业如何从"能问数"走向"可信取数"

> 来源：刘镔辉（Datastrato 解决方案架构师）分享，2026-09。素材为演讲截图解读（23 张）与中文转录（.srt，约 33 分钟+答疑）。本笔记是内容沉淀版，所有内容归属原演讲者；引用格式"演讲 [n]"。
> 定位：这是目前唯一一份"乙方在真实企业现场把问数 agent 推到生产"的**一线复盘**，与报告一（官方方法论）、报告二（开源轮子）、报告三（商业产品/协议/安全）、报告四（Analytics Engineer/语义层运动）互为印证。

## 1. 演讲的主线判断

1. **概念演进**：Text-to-SQL（语法转换，靠 schema）→ ChatBI（报表入口，靠语义层）→ Data Agent（端到端任务闭环：理解-发现-校验-执行-解释-回归，靠血缘/权限/审计/回归）。**问题边界越往后，对数据上下文要求越高。**
2. **核心判断**：先解决"能不能信"，再扩大"能做什么"。错误放大链：取错数 → 错指标 → 错归因 → 错策略 → 信任崩塌。**取数是生产化的第一道门槛；SQL 能跑 ≠ 业务正确。**
3. **上线之山**：Base Camp（能返回结果）→ Camp1 口径正确 → Camp2 权限可控 → Camp3 数据新鲜 → Camp4 可解释/可追溯 → 山顶（高频任务 ~95% 准确）。最后 5% 拼的是**透明化**（用了哪个指标/哪个版本/哪些表/哪些过滤/什么权限/血缘）+ 工程闭环——"专业用户不怕答案有问题，怕有问题还是黑盒"。
4. **榜单证据**：BIRD-SQL 人类 92.96% vs 榜首 ~82%（含脏数据，人类也非 100%）；Spider 2.0 企业级 workflow：Snow 单组件 96.7%、Lite 跨组件 73%、**DBT 实际任务榜首仅 65%**。**Text-to-SQL ≠ 生产级可信问数。**
   - Q&A 补充：BIRD 榜首 AT&T 团队用的是上一代 GPT-4o（讲演当天 GPT-5 刚发布），裸模型 GPT-5 只排第 31 名——**榜首和裸模型的差距就是上下文工程，不是模型代差。**
5. **行业把答案放在哪**：OpenAI（data context/eval）、Anthropic（context & verification）、Databricks（Genie/Unity Catalog）、Snowflake（Agent Context Layer/Semantic Views）、OSI（开放语义交换）——抽象出通用三层：**Agent Context Layer → Governed Semantic Layer → Eval & Harness**。企业落地缺口：**上下文不是没有，而是散落在 Catalog、BI、指标平台、权限系统、文档和历史 SQL 里。**

## 2. 六轮收敛方法论（从 Demo 到生产）

> 每一轮不是加新模块，而是**收敛一种自由度**（自由搜索/解释/生成/执行/修复 → 变成可治理的选择）。"方案不是一次设计出来的，是被问题一轮一轮逼出来的。"

| 轮次 | 现场问题 | 收敛的自由度 | 关键产物 |
|---|---|---|---|
| 1 材料投入 | Schema/SQL/文档/BI 报表全接入，答案仍不稳（召回一堆旧表/旧口径/个人 SQL 习惯） | 先做**失败分型**，别急着补工具 | Badcase 初始分类：资产/口径/生成/执行/回归 5 类 |
| 2 可信资产 | 同一业务对象十几张表（ods/dwd/ads/bi/tmp 字段雷同）；历史 SQL 频次高 ≠ 适合生产问数（高频命中的常是底层明细大表） | **自由搜索** → 收窄可信资产空间 | 可信资产评分卡：owner/production-deprecated/domain-tier/lineage/freshness/policy-tag/usage/quality——"不是静态白名单，是随数据持续更新的信号组" |
| 3 语义映射 | 用户说黑话（有效销售额/大盘转化/老客复购），系统无同名字段；**文档能召回解释但不能裁决生产口径** → 必须人工 double check | **自由解释** → 映射到受治理的语义对象 | 文档库/术语表/历史 Query/BI 报表 → Knowledge Indexer → 向量库 → **Semantic Object IDs**（Jargon → governed object） |
| 4 verified metric | 同一指标每次问出来都不一样（概率性选不同字段） | **自由生成** → 复用 verified metric | 命中 → 弹窗确认后走**固定 SQL 模板**（LLM 只做意图识别，不重新生成 SQL）；未命中 → AI 候选生成 → 编译校验/冲突检测/**人工审核** → 发布 verified metric → 写回语义目录（稳定/一致/可追溯/可复用/可审计） |
| 5 执行校验 | SQL 有结果但业务不能直接用：mandatory filter（行列权限、必要 LIMIT——"注意力窗口机制导致过滤条件漏掉"）可能缺失 | **自由执行** → 执行前校验链 | **先校验再执行**：policy check → freshness check → lineage check → audit log → execute；SQL 编译走 MetricFlow 类工具 |
| 6 回归闭环 | 按 case 改 Prompt，换问法又错；字段变了旧口径还在用 | **自由修复** → 错误资产化进回归 | Badcase 绑定 query/metric/table/owner/version → owner 修复 → 语义/策略/文档更新 → Regression Suite；漂移五型：Schema/Table/Policy/Business/Freshness Drift |

## 3. 元数据与语义层的实现路线（演讲的选型地图）

- **Agent 要的元数据 ≠ 表结构**：传统元数据"给人看"（表/字段/location/数据字典）；面向 Agent 的新型元数据"给 Agent 看"——业务含义/owner/生产废弃状态/字段级与指标级血缘/行列权限与脱敏/工具调用边界/freshness-quality-usage-drift，并最终暴露为 **discover / describe / validate / audit** 四个 API。**"Agent 时代元数据要变成执行前上下文。"**
- 元数据控制面路线：云托管 Catalog（Glue/Purview）、REST Catalog（Polaris/HMS）、Data Catalog（DataHub/OpenMetadata）、平台原生（Unity Catalog）、自研中台、**Federated Metadata Lake（Apache Gravitino：多云多引擎多格式联邦）**——各有边界，企业按数据栈分布选。
- 语义层路线：BI 原生（LookML）、Metric Store（dbt Semantic Layer/MetricFlow/Cube）、开放规范（OSI——演讲口述"目前已改名 OCE"， YAML/JSON 交换规范）、自研指标平台、Semantic Catalog（语义对象与资产/权限/血缘/审计绑定）。**"语义层不是只管定义指标，还要让 Agent 复用、校验和追溯。"**

## 4. 组织与落地（生产化的另一半）

- **责任链闭环**：指标口径→Metric Owner；数据资产→Data Owner；权限策略→Security/Governance；Badcase 修复→Agent Owner + Data Owner；生产发布→Review Board。流程：提交问题 → 自动归因 → owner 分派 → 审核发布 → 回归验证 → 审计归档。**"生产化的难点不只是模型，也不只是 harness 和语义层，而是责任链是否能闭环。"**
- **第一条可信取数链路的最小闭环**：选一个业务域 + 一个核心 Catalog + **5-10 个 verified metrics + 10-20 个真实问题**；验证五类场景（权限拦截/指标冲突/新鲜度/漂移/Badcase）；目标产出五种能力（能回答/能解释/能拦截/能追溯/能修复）。**"不是做万能问数，而是把一个业务域先跑通。"**
- 客户案例（头部金融机构）：权限严格/数据敏感/结果需解释/查询需审计；第一版"能跑"（表连上+SQL 能跑+文档检索+历史 Query 召回）**不等于可信**；上线前必须回答 7 问：哪张表可信/哪个指标是标准口径/当前用户能不能看/数据是不是最新/结果能不能追溯/错了谁来修。**"客户不是缺少数据，而是缺少一条 Agent 可以安全、准确、可审计调用的数据链路。"**

## 5. Q&A 精华（转录独有，截图版没有）

1. **哪些环节交给 LLM、哪些交给程序**：意图识别是 LLM 最擅长的；语义映射 = AI 辅助生成（paraphrase 扩展、别名生成）+ **人工审核定稿**（确认生产口径、所属域、适用范围）；执行环节 = 规则化/工程化。**"语义资产需要业务参与；大模型主要用在语义资产之前的链路。"**
2. **评测集怎么建**："一定不能自己写"——自己写的评测集"太全面"但脱离真实问法。正确姿势：业务给 10-20 个真实问题 + AI 扩写生成到 ~100 题 = 初始评测集；**每题必须有手算的结果**；第一目标 = 召回对问题 + 结果与手算一致；第二阶段才谈降本与性能。
3. **指标歧义的澄清交互**：用户问"总资产"，系统检索出 3 个近似指标（普通账户/信用账户/合计）→ **把 3 个候选各算一遍、把结果差异摆给用户选**；用户也说不清就按默认口径出数并标注。修饰词（限定语）本质上定义了不同指标——这是指标建设体系的一部分。
4. 归因类问题（"为什么下滑"）依赖元数据做归因逻辑——先有可信指标，归因才是后续话题。

## 6. 对本项目的十条直接启示

1. 项目设计主线可借演讲立论：**"从能问数到可信取数"**——取数是生产化第一道门槛，这条与某头部海上油公司"权限严格/数据敏感/需审计"的央企场景完全同构。
2. 六轮收敛 = 现成的设计叙事骨架，且项目已有大半对应物（澄清闸/选表/AST 闸/指纹熔断，评估集）——升级不是推倒重来，是**补齐每一轮缺的"资产化"半边**。
3. 可信资产评分卡（8 信号）→ 项目 Schema Linking 缺的前置层。
4. verified metric 的治理闭环（弹窗确认/人工审核/写回/owner/version）→ 项目"指纹熔断"只有缓存半边，缺治理半边。
5. 执行前校验链（policy→freshness→lineage→audit）→ 项目 sql_guard 可升级为四段校验。
6. Badcase 资产化 + 漂移五型 → 评估迭代缺的回归闭环半边。
7. 评测集方法论（业务真实 10-20 题 + AI 扩写 + 手算金标）→ 直接替换/升级 RAGAS 为主的评估路线。
8. 澄清交互具体化（N 个候选指标各算一遍差异）→ 项目意图澄清闸的产品化细节。
9. 最小可信闭环（1 域/5-10 指标/10-20 题）→ 第一条可信取数链路的设计模板。
10. 责任链（owner/review board）→ 治理设计的高阶框架，央企组织语境加分。
